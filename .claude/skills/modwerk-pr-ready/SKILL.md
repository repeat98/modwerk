# /modwerk-pr-ready

Follow `docs/DEVELOPER_WORKFLOW.md#make-it-mergeable`.

1. **Merge** current `origin/main` into the branch. Never rebase: catalogue rows pin the pull request's own commit.
2. **Regenerate** generated files rather than resolving them by hand: `npm run modules:generate`, `npm run licenses:generate`, `npm run machines:generate`.
3. **Check once.** For a new commit, stage the intended files and run `npm run pr:ready -- --commit "Message"`. For an existing commit, run `npm run pr:ready`. For a registered author, use `npm run pr:ready -- --author <login>` and include the same `--author` option when committing. Let each command manage its own machine slot so other worktrees can run while you push or watch GitHub. Not before draft pushes: between fixes, run the tests you touched or `npm run check -- --base origin/main --rerun-failed`.
   - On a replay assignment, read the printed TASK.md, attempt it in its snapshot and repeat the same command with `--eval-agent "<tool and model>"`. Do this yourself on the first attempt, including when you could only partly solve it. The score stays on this computer ([agent evals](../../../docs/AGENT_EVALS.md)).
   - It also claims on the agent board what the branch adds (a new module, hook or table index, migration) and stops when someone else holds one. Never work around a claim: renumber, rename or ask its holder yourself. Signed out, it asks for `npm run board -- login` first. When it notes questions or replies in the developer's board inbox, read them (`npm run board -- inbox`), answer them yourself from what you can check, close your settled ones, and tell the developer what you said; only a decision about their own work goes to them first. When it offers a finding, post it yourself.
4. **Push.** For base work, find the draft from `base/<machine>-next`, push the commits directly to its branch and update its description. A contributor working from a fork links their commits there for a maintainer. Start the machine’s cumulative draft only when none exists. The owner marks it ready after extensive unit testing ([Change a base](../../../docs/DEVELOPER_WORKFLOW.md#change-a-base)). For other work, update the pull request or open it as a draft (`gh pr create --draft`), which should have happened early ([Open a draft early](../../../docs/DEVELOPER_WORKFLOW.md#open-a-draft-early)). If it changes what runs on an instrument (a `.mwrm` package or `.elemod` base), mark it ready only after the developer has tested that exact build on a unit; the description then names it on a line of its own ("Tested on a unit: base 8d1db124, MKII, what ran", or "Not tested on a unit: <why>"). Draft or ready, it lists the change's edge cases under a line "Edge cases", as the table `npm run test:procedure` writes, or "Edge cases: none, because …" (`docs/TEST_PROCEDURE.md`). CI checks both. Ready from pr:ready means the checks pass, not that it was tested. A change outside a module is titled `Fix: …`, `Improvement: …` or `Docs: …`. Write the description in the template's shape: what changed, how you checked it, and a line that answers the guides question ("Guides: nothing" is fine). CI checks it.
   - **Finish the GitHub handoff yourself.** After pushing a finished contribution and passing full `pr:ready`, read `gh pr view <URL> --json state,headRefOid,isDraft`. Check that the open PR has the tested head. With the required testing recorded, run `gh pr ready <URL>` if it is a draft. Read the PR again and confirm the same head shows `isDraft: false`. If the head changed, check the new commit first. If it stays a draft, name the remaining task and its owner. This also applies to a contributor PR targeting `base/<machine>-next`. The owner promotes the cumulative PR from that branch into `main` after extensive unit testing.
   - Watch `gh pr checks <URL> --watch` until green. For a red job, read `gh run view <id> --log-failed`.
   - If `main` moves before the merge, start again at 1.
5. **Answer what pr:ready asks:** a guide edit for what you learned, or "nothing" in the pull request.
6. **Review the session** when pr:ready prints the session-review line: run `npm run session -- review`, add what its figures cannot show, and tell the developer at most three things that cost time, each with its fix. A concrete fix goes in its own `Workflow: …` pull request (`docs/AGENT_SESSIONS.md#review-the-session-first`).
7. **Offer to share the session** when pr:ready prints the session-sharing line: ask the developer once whether to share this session with the owner, say why it helps (what slowed it down stays in the session unless shared, and the owner turns it into a guide edit, a check or a fix), and on a yes run `npm run session -- share --note "…"` with a few sentences on what got in the way. "Always" or "never" from the developer goes into `npm run session -- prefer always|never` (`docs/AGENT_SESSIONS.md`).
