Use when a developer wants to try, test or qualify a module or base on hardware or in the emulator, or another command needs a build tested on the unit.

# /modwerk-test-on-unit

The order is fixed: the steps of `docs/TEST_PROCEDURE.md`, your tests on the unit, then the developer's. A build that fails your stage is fixed and run again; the developer never gets it to find out.

1. **One session at a time on the unit.** Every session on a computer shares its one connected unit, and the device commands take turns on it by themselves: `device:test`, `device:qualify`, `device:price`, a RAM boot, the steps that drive it and the MCP's trial wait in line and go ahead when their turn comes, so run them in the background. `npm run unit -- status` shows who has it; `npm run unit -- hold --note "…"` keeps it across several commands until `release` (`docs/OCTATRACK_DRIVING.md#taking-turns-on-the-unit`). Emulators need no turn: each session may run its own, with its own socket path, card copy and MCP (`--data-dir`, `--device-socket`); never attach to one another session started. On the owner's computer, sessions share one emulator (`docs/OWNER_OPERATIONS.md`).
2. **Prepare.**
   - Derive the change's own edge cases from what it touches, before you test (`docs/TEST_PROCEDURE.md#edge-cases`).
   - Tell the developer what you will run on their unit, edge cases included, and get their OK for this run (on the owner's computer it stands, `docs/OWNER_OPERATIONS.md`). Read `docs/OCTATRACK_DRIVING.md` and keep its rules.
   - Start one session with `npm run device -- serve --share /tmp/modwerk-share.sock` on a development base, transport stopped, on a bank and Part whose working copy equals its saved one.
   - Leave the CF card in: a twin ignores the developer's card set and a trial never writes it (`docs/OCTATRACK_DRIVING.md`). Never ask them to pull the card or power-cycle for a trial; return to their flashed base with `npm run device -- boot <flashed image>`.
3. **Stage 1: your tests on the unit** (Octatrack; the Rytm below). Run them yourself; do not ask the developer to press anything. No Keep in this stage.
   - **The procedure:** `npm run test:procedure -- <id>` (a base: `--base`), in the background, reading its log. It runs the software checks, names the build (revision and package SHA-256), rehearses in the emulator when you give it one (`--emulator-socket`), then reads the unit, runs `device:test`, the soak and `device:price`, and checks the inventory came back. It stops at the first failure and writes the record. Every result is about that build; a rebuild starts again at step 1.
   - **By hand, what no script covers,** inside a trial (`npm run module:dev -- <id>`, undone when it ends; or the developer MCP's `device_review`, `device_trial`, `device_undo`, `docs/FRONTEND_MCP.md#then-test-the-connected-device`): every control and screen by the README's button steps, with a `png:` screenshot of each to compare with the README and its UI claims; MAIN and CUE recorded over USB (`rec`) with a sustained sound, checked for dropouts. This finds faults; it does not judge the sound. Then put it back: Undo, reload the Part, and check the active identity, the inventory and the Part against the start.
   - **The edge cases:** run each one and fill its row in the record's table, "not run: why" included.
   - **The release run** is `npm run device:qualify -- --keeps-ok --testing-entry run.md <package>`. It Keeps each install and removal, which rewrites the card's kept set: only with the developer's OK for exactly that (standing on the owner's computer, `docs/OWNER_OPERATIONS.md`), after noting the flashed set.
   - On the flashed base the driving steps are refused: run what the MCP offers (status, trial, load, Undo) and list the rest as not run.
   - **On the Analog Rytm MKII** the same procedure runs on its own tools (`docs/TEST_PROCEDURE.md#every-machine`): the link is SysEx in development bases, and `device:test` and the MCP do not reach it yet. Write a case for each README claim in `sdk/machines/analog-rytm-mkii/tools/cases/<id>/` and have them reviewed independently, then `npm run test:procedure -- analog-rytm-mkii:<id> --stock STOCK.syx --elemod DEV.elemod --label XX01 --emu DTBOOT --link` (a base: `--base analog-rytm-mkii`) in a scratch project: it links the image, runs the cases on rytm-emu, RAM-boots it (`rytm_link.py ramboot`, nothing written to the flash), runs `rytm_test.py unit` and checks the flashed label at the end (`sdk/machines/analog-rytm-mkii/TEST_RUNNER.md`, `LINK.md`). Tell the developer beforehand how many restarts are coming; a power cycle brings the flashed base back.
   - A failure stops the stage: put the unit back, fix it, and start stage 1 again on the new build.
4. **Stage 2: the developer's test.** Only after stage 1 passed on this build. Say in a few lines what it showed and what it could not.
   - Then give them the record's list of what only a person at the unit can judge, plus the edge cases left to them and anything particular to this module, each with the exact button steps and what they should see or hear. Leave out what stage 1 already settled.
   - The Keep, the power cycle and listening are theirs: never Keep without their OK, never power-cycle or flash yourself. The order stays review, trial, then an explicit Keep or Undo, bound to the exact version. On a RAM-booted test base a Keep replaces the owner's kept set (`docs/OCTATRACK_DRIVING.md`).
   - Record what they report, as they report it. A fault they find is fixed, and both stages run again on the new build.
5. **A machine without a USB link yet:** stage 1 is the same procedure (`npm run test:procedure -- <machine>:<id>`, a base `--base <machine>`): it runs the steps the machine's tools reach and records the rest as not run with what is missing, and stage 2 carries all the hardware evidence. Recommend building a link, as the recipe lays out (`docs/MACHINE_RECIPE.md`, `sdk/runtime/loader/README.md#porting-to-another-machine`).
6. **The emulator** (`ot_emu` from `npm run upstream:tools`, digiemu, rytm-emu) is for fast iteration, UI captures (`docs/MODULE_UI_CAPTURES.md`) and rehearsing stage 1 before touching the unit: the procedure with `--target emulator` runs the same unit steps against an emulator session (`docs/TEST_PROCEDURE.md#one-set-of-cases-two-targets`). It never counts as hardware evidence.
7. **Record** both stages in the module's `TESTING.md` (a base: `docs/verification/`), apart and on the named build: the procedure's record with its edge-case table, what you did by hand, then what the developer observed. "Not tested" is a valid result.
   - Your stage is evidence for what it measured, never for the sound or for persistence across a power cycle; software tests prove neither, nor rendered pixels.
   - The hardware report and the release boxes stay the developer's: never attest for them.
   - When this run completes testing for a contribution the developer is submitting, update its PR with the exact build and results, then finish the GitHub handoff in `/modwerk-pr-ready`. If testing is still open, report who owns the next step.
