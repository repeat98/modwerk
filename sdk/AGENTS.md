# Working in sdk/

You are about to write or change a module: an Octatrack module under `octabam/modules/`, a Digitakt or Digitone mod under `digitakt/modules/` or `digitone/modules/`, or a draft under `drafts/`. Read the rules first.

@../docs/module-guides/README.md

1. Find the module's `category` in its manifest and read `docs/module-guides/<category>.md`. The index above lists them. Anything that acts in time also follows `docs/module-guides/sequencing.md`: use the instrument's own transport, tempo, track speed and swing, as Euclid does, and never keep a clock of your own.
2. Follow `docs/ADD_A_MODULE.md` for the folder, the manifest, the packages and the comparison with native octabam. Before releasing or updating a module version, add matching release notes to `src/community/module-changelogs/<key>.json` (Octatrack key `<id>`, Digitakt/Digitone key `<machine>-<id>`). Preserve history; describe actual behaviour, fixes and compatibility limits. Documentation-only updates must be identified as such and do not require a firmware version bump.
3. For new FX, plan the DSP budget before implementation and aim for the same ballpark as worst-case stock SPRING REV. Benchmark expensive Spring types/settings, moving controls and trigger splits under matched conditions on both cores. Treat this as a design target without a fixed ratio or hard per-effect ceiling; substantially higher cost needs optimization and review. Walk the category guide's checklists. Tick an item only when you did it; write "not tested" in TESTING.md for what you could not verify. Never record a hardware behaviour you did not observe.
4. Run `npm run module:doctor -- <id>` until every line is green, then `npm run pr:ready` (an author update: `-- --author <login>`) until it says Ready, before every push. Documentation-only edits run the lightweight validation path; native compilation is reserved for firmware source/build changes.
5. Octatrack DSP or ColdFire code: read `octabam/AGENTS.md` (the assembler and hardware traps) before writing it.
6. Keep a module PR to the module. A finding for every developer goes in the matching guide, and a bug fix or improvement to the SDK, tools or site goes in its own small PR titled `Fix: …`, `Improvement: …` or `Docs: …`; inside a module release it would end automatic publication ([Fixes and improvements](../docs/DEVELOPER_WORKFLOW.md#fixes-and-improvements)).
7. For reported module bugs, follow [the full issue-fix flow](../AGENTS.md#finish-the-issue-fix-flow): a request to fix issue numbers includes the release, required PR checks and authorized owner merge, live deployment and saved firmware-download verification, issue closure/report synchronization, and verified subscriber notification fanout. Continue through the whole flow in the same task. A draft, source commit or merged draft-only PR remains staging. Keep hardware limits honest; an explicit owner waiver permits only its named scope and must be bound to the new version/source. Close an unverified symptom only when explicitly authorized, with its limitation stated. Existing version-specific qualification/owner exceptions still apply; never silently broaden them. Do not ask again for steps already authorized in the session.

Never commit firmware, extracted stock code or tables, memory dumps or built images.
