# Working in sdk/

You are about to write or change a module: an Octatrack module under `octabam/modules/`, a Digitakt or Digitone mod under `digitakt/modules/` or `digitone/modules/`, or a draft under `drafts/`. Read the rules first.

@../docs/module-guides/README.md

1. Find the module's `category` in its manifest and read `docs/module-guides/<category>.md`. The index above lists them. Anything that acts in time also follows `docs/module-guides/sequencing.md`: use the instrument's own transport, tempo, track speed and swing, as Euclid does, and never keep a clock of your own.
2. Follow `docs/ADD_A_MODULE.md` for the folder, the manifest, the packages and the comparison with native octabam. Before releasing or updating a module version, add matching release notes to `src/community/module-changelogs/<key>.json` (Octatrack key `<id>`, Digitakt/Digitone key `<machine>-<id>`). Preserve history; tell players in at most five short lines what changed for them, and keep test evidence in the pull request. Documentation-only updates must be identified as such and do not require a firmware version bump.
3. Share the instrument. Never patch a stock site another module or the base patches: look at the machine's hooks first and subscribe where one fits. On any machine but the Octatrack, read the Modwerk stack section of its guide (`sdk/machines/<id>/README.md`): what its planned base will own, such as a send bus or an FX list, is never built inside one module ([recipe](../docs/MACHINE_RECIPE.md)). Agree with the developer how the module is reached and how later modules will hook in beside it, and propose a new hook only when several modules will need that site; a site only this module needs it patches and declares ([choose how a module hooks in](../docs/module-guides/README.md#choose-how-a-module-hooks-in), [Octatrack](../docs/module-guides/README.md#propose-a-hook), [Digitakt, Digitone and Digitakt II](../docs/module-guides/README.md#propose-a-hook-on-the-digitakt-digitone-or-digitakt-ii)). Declare the gestures and screens you take in `compatibility.uiClaims` and a deliberate clash in `compatibility.conflicts`. A module never depends on another and never shares another's state or code; two features that must share ship as one module.
4. For new FX, keep one effect per module: a MODE select may switch between ways of doing one job, never between different effects ([one effect per module](../docs/module-guides/effects.md#one-effect-per-module)). Plan the DSP budget before implementation and aim for the same ballpark as worst-case stock SPRING REV. Benchmark expensive Spring types/settings, moving controls and trigger splits under matched conditions on both cores. Treat this as a design target without a fixed ratio or hard per-effect ceiling; substantially higher cost needs optimization and review. Plan compatibility at the same time: Analog BD, the stock FX and the common custom companions on both DSP cores, by actual contiguous openings and shared tenants rather than total free memory; any necessary incompatibility has a documented resource reason and owner review. Walk the category guide's checklists. Tick an item only when you did it; write "not tested" in TESTING.md for what you could not verify. Never record a hardware behaviour you did not observe.
5. A new Octatrack module delivers the base/USB lifecycle alongside the card build (install, self-test, Keep, Undo, removal and persistence through the Modwerk base), so a beta module set never falls back to a card-only build ([USB lifecycle](../docs/ADD_A_MODULE.md#octatrack-base-and-usb-lifecycle)). Do not tie a module to the base firmware: its DSP engine, tables and controller code belong in its own package, and a module update must not need a base rebuild ([plan](../docs/OCTATRACK_PACKAGE_DSP_HOOKS.md#owner-decision-and-plan-22-october-2026)). Until that lands, Analog BD, Sidechain Compressor and Output Matrix are base inputs: say so before starting an update that touches their DSP or controller code.
6. Keep module thumbnails in the shared signal-art style: quiet dark grid, module/category accent, thin signal diagrams and small monospace labels. Reuse `ModulePreview.tsx` / `DigiModPreview.tsx` and keep saved SVG thumbnails consistent with their displayed artwork ([thumbnail style](../docs/ADD_A_MODULE.md#module-thumbnail-style)).
7. Run `npm run module:doctor -- <id>` (a draft: `-- --draft <id>`) until every line is green, then `npm run pr:ready` (an author update: `-- --author <login>`) until it says Ready, before every push. Documentation-only edits run the lightweight validation path; native compilation is reserved for firmware source/build changes. `pr:ready` also asks what the guides lacked or got wrong while you worked: answer it in the pull request, and fix the guide where a reader would look. "Nothing" is a fine answer; a lesson left in the session is not.
8. Octatrack DSP or ColdFire code: read `octabam/AGENTS.md` (the assembler and hardware traps) before writing it.
9. Keep a module PR to the module. A finding for every developer goes in the matching guide, and a bug fix or improvement to the SDK, tools or site goes in its own small PR titled `Fix: …`, `Improvement: …` or `Docs: …`; inside a module release it would end automatic publication ([Fixes and improvements](../docs/DEVELOPER_WORKFLOW.md#fixes-and-improvements)).
10. For reported module bugs, a registered author follows [docs/MODULE_AUTHOR_UPDATES.md](../docs/MODULE_AUTHOR_UPDATES.md): diagnose and fix the report, bump the version and release notes, give the author concrete hardware steps for the exact private build and record only their actual results. The owner's complete release flow, from the fix to live download verification, issue closure and follower notification, is in [docs/OWNER_OPERATIONS.md](../docs/OWNER_OPERATIONS.md#finish-the-issue-fix-flow).

Never commit firmware, extracted stock code or tables, memory dumps or built images.
