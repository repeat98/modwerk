# Analog Rytm MKII SDK

**Platform:** elemod · **OS:** 1.74 · **Core:** Modwerk's base, from elekloader core-ar2 0.7's source · **Modules:** [`sdk/analog-rytm-mkii/modules/`](../../analog-rytm-mkii/modules/) · **Status:** preview

The Analog Rytm MKII runs on the same ColdFire platform as the Digitakt mk1, and its OS entry and bootstrap loader match the Digitakt's instruction for instruction. Its core is elekloader's Digitakt mk1 core (`core.s`, `settings.s`, `render.s`) built with the Rytm's addresses. The core hooks eight shared sites and calls every subscribed mod's handler, in order, from tables the linker builds, so any set of mods that fits the budgets combines. From 0.2 it also keeps mod storage: fields a mod declares, saved with sounds, kits, global slots and projects (below). Cores from 0.3 on are for OS 1.74 only; new core versions drop old OS support, so Modwerk supports the Rytm on OS 1.74 alone. Every core 0.3 hook below has run on a unit; core 0.7 has not yet run on one from Modwerk's builder, so its parameter pages are not tested on hardware here. Modwerk's linker builds Rytm modules. Filter Hz is the first library module, so the machine is in preview: the browser builds the core with library modules on OS 1.74, with downloads off until the owner turns them on.

## Modwerk stack

Today the core is Modwerk's base, built from elekloader's core-ar2 0.7 source, and mods reach the unit as a full OS file sent with Transfer. The Rytm is to get the Octatrack's stack ([recipe](../../../docs/MACHINE_RECIPE.md)) on a Modwerk base (owner, 27 October 2026). The base starts from core-ar2 0.7's source, copied unchanged into [elekloader/](elekloader/README.md), where `npm run machine:base -- analog-rytm-mkii` builds it with the reviewed toolchain and checks its identity (29 October 2026). The plan was agreed with the owner on [#878](https://github.com/repeat98/modwerk/pull/878).

The base carries the send bus (29 October 2026): per-track sends, the return to the mixer, the SEND and SEND FX pages, the effect chooser, per-kit state and the FX track's p-locks, and an FX list each send effect joins as its own module ([Send effects](#send-effects)). Development bases carry the USB link, SysEx over USB MIDI ([LINK.md](LINK.md), 14 November 2026): an agent reads the screen and memory, presses keys, turns encoders, and flashes or RAM-boots a test image with no hand on the unit. Release bases do not carry it. The link behind the MCP's device tools, the loader, base installs and updates from the site and the machine page follow.

The site builds every Rytm set on this base (30 October 2026, as studied on [#878](https://github.com/repeat98/modwerk/pull/878)), in one of its two variants, each identified in [base-binding.json](base-binding.json): **send-bus** when the set holds a send effect (a module listed in [fx-ids.json](fx-ids.json)), and **plain**, core-ar2 0.7's source with the machine list's sections ([below](#machine-list-sections)), otherwise, so a set with no send effect keeps today's RAM and kit storage. Both use core-ar2's mod storage, so a configuration's storage lockfile carries over from irpina's release and between the variants: adding a send effect keeps every module's fields in place and adds the bus's. The full OS file sent with Transfer stays the fallback.

## Send effects

A send effect is a module that adds one record to the base's FX list; the base owns everything around it. The record, `struct mw_fx` in [`include/modwerk/fx.h`](include/modwerk/fx.h), gives the effect's id, its name, eight controls (label, icon, default, bipolar), `reset` and `render`. The module's `build.json` contributes a pointer to it: `{"to": "mw_fx", "order": 10, "data": "00000000", "relocs": [[0, "abs32", "sym:my_fx", 0]]}`, with no subscriptions and no sites.

- **Its id** comes from [`fx-ids.json`](fx-ids.json): take the next free number, 1 to 63, and never reuse or renumber one, because a kit saves the chosen effect by its id. `npm run modules:check` refuses a record whose id is not its entry there.
- **`render`** runs once per audio block (32 frames at 48 kHz, or 16 at 24 kHz with `MW_FX_24K`) with the sum of the sends, the eight values after p-locks, and a work area the base lends, the `work` words its record asks for, at most 8,192 (32 KB). The base reserves none: it lends the mod RAM the set leaves free, so a set whose modules leave less than an effect asks for does not list that effect, and `scripts/link-image.mjs` refuses to build it. `reset` clears the effect's state when it is chosen and when a project loads. Use `mw_fx_rate`, `mw_fx_onepole` and `mw_fx_tempo` rather than tables of your own. An effect that acts in time (a delay in note values, a gate on steps) reads the Rytm's sequencer through `mw_fx_clock()` and `mw_fx_step()`, only in a render that needs it, and never keeps a clock of its own ([sequencing](../../../docs/module-guides/sequencing.md)). Its grid swings every second step by the pattern's SWING, as if every odd step had a swing trig: the pattern's own swing trigs are not read.
- **What the base keeps:** the sends, the return and LEV, the pages, the chooser (FUNC + A on SEND FX), A-H at random (SRC held + YES, + NO undoes it once), the CPU reading, p-locks, and the kit's effect and values (62 of the kit's 64 storage bits; the sends take 7 sound bits, LEV 7 project bits). A kit whose effect is not installed shows MISSING, keeps its values and plays no return. With no effect installed, AMP and DELAY step over both pages, as on stock.
- **Budget:** the base with the bus takes 28,702 bytes of `.run` and 2,708 of `.bss`, leaving about 97 KiB of the 128 KiB area for the modules and the largest effect's work area together (CHORUS and FLANGER ask for 16 KB each, PHASER none). Keep an effect's CPU at or below CHORUS's, and say in TESTING.md what you measured with the base's CPU reading.

CHORUS, FLANGER and PHASER (ids 1-3) are the first, taken from Send FX with the same samples on the host.

## Machine list sections

OS 1.74 files each machine in the machine list under a section, a byte per machine id from a 34-byte table at `0x40257d70` (ids 0..33) that function `0x400df664` reads, giving 0 to any higher id: 1 BD, 2 SD, 4 CP, 5 BT, 6 RS, 7 HH, 8 CY, 9 CB, 10 UT, 11 SY, 14 DISABLE. A mod machine (slots 34..43) has no entry, so without help it sorts above every stock machine of its group. Two SY machines are ordered by a map of SY DUAL VCO, SY CHIP and SY RAW (ids 28, 29, 32) in the two sort comparators (`0x400bdc5e`, `0x400bde1c`), which throws for any other id. The `home` byte of `core_machine` does not file the machine in a section: it picks the group. A track's list (built by `0x400bebce`) holds the machines its voice may run in three groups: those whose `home` is this track, sorted; then those whose `home` is another track, sorted; then those with `home` -1 (XT CLASSIC, UT NOISE, UT IMPULSE, DISABLE), in machine-number order and not sorted. So a mod machine with `home` -1 comes after DISABLE, in slot order, whatever its section (MIDI Engine, slot 42); one with a track's `home` takes its section's place within that group. A section also brings what stock draws for it: the callers of `0x400df664` (`0x400de6d8`, `0x400dee34`, `0x400df19e`) use it as a jump-table index and to group the list under a header, so a filed machine sits under its section's header and is drawn as that section's items are, where an unfiled one sits above them with none.

Both base variants take the three entries (`base/sections.c`). A machine module names its slot's section with a table entry of four bytes and no code, in `build.json`:

```json
{"to": "mw_machine_sections", "order": 50, "data": "290b0000", "relocs": []}
```

The bytes are the slot (here 0x29, 41), the section (here 11, SY) and two zeros. Offered sections are the ten above except DISABLE. A slot with no entry keeps today's place at the top of its group; the first entry for a slot wins. `npm run modules:check` refuses a malformed entry, a slot that is not 34..43, a module that adds no machine through `core_machines`, and two entries for one slot; it cannot read the machine's own slot from the compiled code, so keep the entry's slot the machine's. Within the SY section a mod machine sorts after stock's three (SY DUAL VCO, SY CHIP, SY RAW); the comparators order by section and, for SY, by that rank, and nothing else. A module whose slot is already taken by another cannot link anyway (`machine:<slot>`).

## Amp envelope record

Once an audio block OS 1.74's `amp_env_commands` (`0x40109940`) runs each of the eight voices' amp envelope state machines and then stores the voice's record for the amp: a rate word and a level word, each twice (`0x40109c24`..`0x40109c34`, 18 bytes). Anything that changes how a voice's amp moves (an envelope curve, a pre-fade before a trig) needs those stores, so both base variants own them (`base/amp.s`, `include/modwerk/amp.h`) and no module patches them. An assembly entry subscribed to `ev_amp_record` runs once a voice a block, lowest `order` first, with d0 the rate word and d2 the level word in and out, d3 the voice, a2 its state (+0 state, which it may write, +4 hold counter), a3 the frame at its record and a4 its track's sound slice (+0 ATK, +2 HLD, +4 DEC). It may use d1, d4 and a0 and keeps every other register. Entries that rewrite the record take orders 10-39; entries that follow the voice's level take 60-89, so they see the record the amp gets; 40-59 is for entries that do both, such as one that rewrites the attack's rate and follows the level (`amp.h`).

A rewriter (10-39) and a later entry that shapes or follows the envelope (40-89) see each other's records, so both keep to these rules:

- **A rewritten record passes through.** An entry at 40-59 that rewrites stock's records leaves a record it does not recognise as stock's as it is. Tell records apart by both words. Stock's levels are `0x4000007f` (the attack, at the trig), `0x0000007f` (the attack held on, in the gate and hold states), `0x00000080` (the decay), `0x40000080` (a choke's fade), and 0 with the rate word 0, which leaves the level where it is (idle, and a decay at DEC 127, INF). Stock's rate words are `0xb0000000` | rate at the trig, `0x30000000` | rate while held, `0xb0100000` | rate in the decay and `0xb01748fa` for a choke. A pre-fade's ramp to silence has the decay's level but a rate word without bit 20.
- **A follower follows the record sent.** An entry that follows the voice's level reads a rewritten record by its own words (a pre-fade's: a fall to silence), not as the stock state it replaced, so it knows where the voice is when the next trig's attack starts from there.
- **Stock's state machine runs underneath.** A rewritten record does not change stock's state machine: the state (a2+0) and the hold counter (a2+4) move as stock moves them; only an entry that writes +0 changes that. An entry that ends a hold or a gate itself keeps counting through blocks whose record a rewriter replaced, and writes only stock's state values (-1, 0 to 4).
- **Holding the hold.** An entry that ends a timed hold itself, instead of stock's compare, decides the end only in a block whose record is stock's held attack (level `0x0000007f`). A rewriter that replaces that record for longer than a pre-fade's few milliseconds before a trig keeps such a hold from ending, so it lists the module with that entry in `compatibility.conflicts`.

For example Improved AMP (#1419) has both in one module: a pre-fade at 20, and at 50 its envelope entry (the attack's rate, the hold's end, a level follower).

The registers are stock's at `0x40109c24`: the loop head sets a4 to the track's slice (`0x4010998e`, 84 bytes a track from `0x8000f7ea`) and nothing before the stores changes it, and no stock branch lands inside the 18 bytes taken. With no entry a voice costs one table read and one test more than stock. In rytm-emu (base built from this tree, no modules) the analog model's output and every DAC word matched main's base sample for sample over a run of pad hits, and a test module's entries ran in order (20 before 80). On a unit: Improved AMP's images, its entries at 20 and 50 on the plain base (`1c14b6b0`) and on development bases, loaded to RAM on the author's MKII (its TESTING.md).

To keep a track silent, don't hold its amp: a held voice still takes a shared voice (CH/OH, RS/CP, MT/HT, CY/CB) from its partner, and the partner's level leaks through the fade. Drop the track's trig in the audio block instead. Its trig loop (`0x4011ff48`..`0x40120ac6`, d2 the track, d3 four times it) runs each track's sequencer slots, pad mailbox and retrig series, and leaves the block's command in `0x8000e508[track]` (1 trig, 2 release). The voice allocation after it (`0x4012106a`) takes a voice only for a 1, and the amp, sample layer, machine, LFO and slide all key on it. The series is per track, so it keeps counting, and its hits still record. Stock's release does not check who owns the voice, so drop the dropped note's release too. The command is final at `0x40120a66` (`lea 0x8000e508,%a3`, six bytes, a branch lands only on its start), where nothing has acted on it yet. A dropped trig leaves the pad dark: a pad's light is its voice's own sound, a running mean of the voice's square at `0x419ca178[track]`, stored at `0x4012155a` for the voice's owner only and drawn as log2 by the pad view (`0x400c987e`), so a module that drops trigs stores a light of its own there (Silent Pad+Trig 0.8.0 does).

## Digital voices

A machine that makes its sound in software (as stock's CP CLASSIC does) adds one record to the base's list `mw_voices`, `struct mw_voice` in [`include/modwerk/voice.h`](include/modwerk/voice.h), and its `core_machines` engine calls `mw_voice_run`. The module gives `hit` and `render`: 32 samples a block, Q31 at full scale, before LEV. The base owns everything around them:

- **The hit:** a new trig is a voice state of 0 with its timer reset (the boot state of 0 is not one). The base silences the voice's analog circuit with stock's own routine (0x4011e4c2, what DISABLE calls) and reads the hit's velocity (0x800067c4 + 2 x track, 8.8) and the note's pitch ratio.
- **The knobs:** the eight live words, read signed (modulation can take a word below 0) and held to 0..127.
- **The stream:** LEV squared into the voice's digital stream (0x80006bf8 + 128 x voice), which stock's mixer sends through the voice's filter, AMP and OVR. `ev_render_out` clears it after the mixer, so a voice another machine takes over plays no stale block. A hit ends after 64 blocks below -102 dB, measured before LEV.
- **The type:** up to eight variants of a machine in a 3-bit field of the sound. A tap of the record's encoder on the machine's SYNTH page steps it and that knob's label follows; `ev_sound_applied` keeps each track's type exact through kit and sound loads and a trig's sound lock.
- **The EMAC:** `render` runs in fractional mode with all four accumulators clear; the base keeps stock's MACSR and all four accumulators around it, as stock's mixers rely on them. [`include/modwerk/dsp.h`](include/modwerk/dsp.h) has the multiply, sum and table helpers, and a host model for testing the same C off the unit.
- **Cost on the unit:** the core runs at twice DTIM0. A `mac.l` whose accumulator is read by the next instruction waits 3 cycles (5 for the pair, 2 with three independent instructions between, measured on a MKII), so a voice's hot loops spread independent products over ACC0-ACC3; GCC's `qmul` pairs cannot. Stock's audio work evicts a voice's code and tables between blocks, so every block pays their cache refill (about a third of a bass drum voice's render, measured, before it was trimmed): keep per-block code and tables small, and pass settings in place rather than copying records. rytm-emu counts instructions only; its ticks match the unit's warm cost, not the stalls or refills. A routine in assembly saves every register it uses of d2-d7 and a2-a6 (the caller's under GCC's convention); one that did not corrupted its caller without a fault. Budget against what is left: on a MKII with the base (send bus, no send effect) the whole audio block, ev_render_in to ev_render_out, takes about two thirds of its 88,000 ticks with nothing playing and three quarters at its dearest, so digital voices hitting together share about a quarter of the block.
- **The meter:** `mw_voice_meter` keeps each slot's blocks, DTIM0 ticks (88,000 a block) and dearest block.

The base's voices are in the send-bus variant and take about 4 KB of `.run`. A module that adds a voice machine lists its id in [`voice-modules.json`](voice-modules.json) (`npm run modules:check` asks for it), so the site builds its sets on send-bus.

**Test a voice on the unit** with [`tools/voice_rig.py`](tools/voice_rig.py): it plays track 1 over MIDI (USB is enough: the unit's USB audio carries MAIN OUT), sweeps each knob from a plan the module keeps (JSON: the machine, its knobs' CCs and defaults, the sweeps and a host model; the script's docstring has the fields), measures every hit and judges each sweep's trend against the module's host model, and checks silence on choosing the machine, no repeated block after a machine change, and dropouts on several voices. Run it in a scratch project: it sets the track's filter and AMP and puts the machine on several tracks.

## Create a mod

```sh
npm run module:new -- my-mod --machine analog-rytm-mkii --author your-github-login
```

A new module goes into `modules/<id>` and is live once its pull request merges, so the pull request carries everything the library needs, as on the Digitakt ([Digitakt and Digitone](../../../docs/ADD_A_MODULE.md#digitakt-and-digitone)): `tests.documentation` with the README's tutorial and rytm-emu screenshots and their capture record ([UI captures](../../../docs/MODULE_UI_CAPTURES.md)), its release notes in `src/community/module-changelogs/analog-rytm-mkii-<id>.json`, and its source-only `.elemod` package, built in the pinned toolchain, committed under `sdk/imports/packages/<id>/` and pinned in `sdk/imports/elekloader-<id>-<date>.json` ([source-only release objects](../../../docs/ELEMOD_SOURCE_BUILDS.md#source-only-release-objects)). `npm run module:doctor -- <id>` names what is missing. `_submissions/` takes no new modules or changes, because nothing there reaches the library, and `npm run check` refuses them; a module still waiting there enters the same way, moved into `modules/`.

This creates `modwerk.module.json` (contract v3), `build.json`, `src/main.c`, README, TESTING, licence and a placeholder thumbnail. See [the SDK guide](../../../docs/SDK.md) for the contract and evidence tiers. The core's contract is [core-profile/interface.json](../../analog-rytm-mkii/core-profile/interface.json), and `npm run modules:check` rejects modules that use anything it does not provide.

## Core hooks

Handlers use the C calling convention: arguments on the stack, d0–d1/a0–a1 free, the result in d0. Subscribe in `platform.events` and name each handler in `build.json`.

| Hook | When | Handler |
| --- | --- | --- |
| `ev_tick` | the UI compose check, about 20 Hz (the Digitakt's runs at 30) | `void f(void *ctrl)`; set `ctrl + 0x20` to 1 to request a redraw. Not an audio-rate clock. |
| `ev_draw` | after the OS composes the 128 × 64 screen | `void f(void *bmp, void *ctrl)`; y counts up from the bottom row (0) to the top (63), x runs left to right |
| `ev_key` | a UI key event | `int f(void *brain, void *event)`; nonzero consumes it. `event + 12` is the key id (trig keys 0x00–0x0f, BANK A–H 0xc0–0xc7, FUNC 0x80, NO 0x45), `event + 16` the flags: bit 0 set while down, clear on the release (stock tests that bit; 0x10 is missing when another key went down during the hold, so never test it for a release); a held key repeats with 8 set (a 2 s BANK hold gave 15 events); `brain + 32` is the view manager, for stock's popups |
| `ev_enc` | a UI encoder event | `int f(void *brain, void *event)`; nonzero consumes it. `event + 12` is the encoder, 0–7 for A–H (not 1–8 as elekloader's ADAPTING.md gives for the Digitakt), `event + 16` the count after the encoder's acceleration, which can be 0 for a slow first turn, `event + 20` a byte set while the knob's own button is held (the UI loop reads `is_key_held(knob + 0x70)`, 0x400a4858). It is not FUNC: read FUNC with `is_key_held(0x80)`, as stock's sound pages do |
| `ev_settings` | building the SETTINGS menu | `void f(void *menu)`; add rows with `core_additem(menu, row)` |
| `ev_render_in` / `ev_render_out` | entry and exit of the ColdFire's audio block: 32 frames, about 1,500 blocks a second | `void f(void)` |
| `ev_project` (core 0.3) | after CREATE NEW or the project reset (`how` 0), and after every project load, at boot too (`how` 1); the project and its mod data are in place | `void f(int how, unsigned dropped)`; `dropped` flags the global, track, pattern and project scopes that loaded as zeros. Keep it short, and start no load or save from it. |
| `ev_sound_applied` (Modwerk base, send-bus variant) | stock applied a sound to a track (0x4011f60a): a kit or sound load, a trig's sound lock, a SOUND SETTINGS change; after the track's machine byte is written | `void f(void *sound, int track)`; read the sound's mod storage here. Keep it short: a trig's sound lock reaches it from the sequencer. |

On the Rytm, y = 0 is the bottom row of the screen: a rectangle at y 48–63 lands at the top, as hardware photos and rytm-emu both show. Drawing code written with y = 0 as the top row, such as the hooks-check example ported from the Digitakt, needs y flipped (63 − y).

The render hooks cover the digital path only: this block renders the delay and reverb and mixes their returns. The analog voices are not rendered by this code, so a mod cannot change a voice's own sound; it can read each voice from the codec's receive buffer and add a return of its own ([The audio block](#the-audio-block)). Like the Digitakt mk1 core, the core uses DTIM0 and claims `timer:DTIM0`.

Traps found while writing a C mod for OS 1.74 (rytm-emu `3c4c42c`, October 2026):

- **Stock returns pointers in d0.** Debian's `m68k-linux-gnu-gcc` expects a pointer result in a0, so a C mod that declares a stock routine as returning a pointer (`project_singleton`, `kit_track_sound`, a vtable getter) reads garbage and can jump to 0 at boot. Declare such routines as returning an integer and cast the result.
- **`is_key_held` does not cover the BANK keys.** They are not in stock's key-scan list, so it reads them as up; follow a BANK hold through `ev_key`'s press and release events instead, and ignore its repeats.
- **FUNC + turn drops its first detent, then jumps.** The sound page's encoder handler (`0x40039f3c`) tests FUNC with `is_key_held(0x80)` and calls `param_apply_delta` (`0x400378a6`) with func 1, but stock drops the first turn event after FUNC goes down (flag `0x417e32b8`, armed again after each jump), so a single FUNC turn seems to do nothing. The value then comes from the parameter's jump function, a std::function in its RAM record (`0x419a4888 + 84 * id`: manager `+0x4c`, invoker `+0x50`, called with the functor, value, delta, min, max and default, all 8.8, its result stored) or, with none, a normal step (`0x400a9648`). Stock's: octaves (`0x400ffe40`, manager `0x400fe3ea`; the TUNE ids), LEV's 0/100/127 (`0x40100198`, `0x400fe6cc`), min/centre/max (`0x400fb422`, `0x400fe5d6`), DELAY TIME's note lengths (`0x401000f4`, `0x400fe628`). A mod machine gives its knobs jumps by writing a manager and invoker into its records, as the draw function (`+0x2c`/`+0x30`) picks a knob's picture; `core_params`' `delta` sees func 1 from the second detent on.
- **SETTINGS is the GLOBAL menu.** The rows `ev_settings` adds come after SYSTEM in the menu the GLOBAL key opens. The menu calls a row's label callback again when it redraws the row, so the label can show the row's state: a row whose select callback flips a value and whose label reads it shows the new value at once.
- **Where keys go.** `ev_key` runs before any view. Views sit in a stack (view manager + 24 is the top node, node + 4 the one below, node + 8 its view), and a key walks down until a view takes it. Screens differ: the GLOBAL menu takes its arrows, YES, NO and pushes and passes the rest, so stock's QPER view opens above it. A list menu takes everything but FUNC, a yes/no dialog everything, a popup only NO. So a gesture in `ev_key` fires over every screen unless it reads the top view, and a site in a view does not keep it out of a menu that passes the key. A screen that takes a release also hides it from the views below: release QPER on the save kit screen (FUNC + TRK) and stock's QPER view stays open behind it, unless the mod closes it from `ev_key`.
- **Replaying a key.** A module that holds a key back and plays it later should call the core's exported `core_key(brain, event)` (core.s), which runs every `ev_key` handler in order and then `Brain::key`, guarding its own handler against the replay. Calling `Brain::key` (0x400a0336) directly skips every handler after the caller, so a mod that follows pages by their keys (Loop Sync, the base's send pages) misses the key. Replayed from inside the release's dispatch, play the press and the release and take the real release, so the handlers before yours do not end on a press. Quick Mod Assign's LFO tap does this (rytm-emu). A key that stands for something else, such as an input's PLAY for the transport, stays on `Brain::key`: a mod may take that key as part of its own gesture (QPER Live Rec takes PLAY while QPER is held), and the transport would never start.
- **Writing into stock's lock box.** While a locker is set, stock draws each knob it has as a box with a whole number, the value in the knob's own units: a 27 × 7 box over a label knob's label (x 3 + 32 per column, rows 25..31 or 47..53 from the top) and a 19 × 15 block over a widget knob such as OVR, DEL, REV, PAN or VOL (x 7 + 32 per column, rows 10..24 or 32..46). A mod that needs another format finds that box in `ev_draw` and draws over it with stock's text, `0x4007154c(bmp, font, x, y, centred, 0, width, fmt, …)` with the font from `0x40071be8(0x417e389c)` and y the text's bottom row counted from the bottom, in white, then inverts the box. It checks first that its own locker is the one set: a pad, a trig or QPER sets stock's, whose boxes are its locks. DEP's own format is a sign and the hundredths of the 8.8 value, cut (`0x400fbbe8`), with 0 as (0). Quick Mod Assign's LFO depth does this (rytm-emu and a unit).
- **CHROMATIC pads keep two notes.** ChromPadsView holds each pad's layout note (view + 404 + 4 × pad, rewritten by UP and DOWN, -1 past the top) and the note a press played (view + 308 + 4 × pad, -1 after the release). Its MIDI note on and note off send the played note less 24; stock 1.74 sends the pad's poly pressure on the layout note, unchanged (Pad Pressure Fix, was Chromatic Aftertouch Fix). In rytm-emu, `--raw 9pvv` streams pad p's pressure while `--press` holds it, and `--midi-out` records what MIDI out sends.
- **A retrig roll takes pad pressure.** Pressure (UI message type 2) goes down the view stack until a view's pressure method returns nonzero. With RTRG (key `0x85`) held or the track ALWAYS ON, and VEL.CUR 0, KeyboardView (`0x400c74d4`) and ChromPadsView (`0x400c6196`) write it to the roll's velocity (`0x4011f262`) and return before the aftertouch setter (`0x4011f490`) and MIDI poly pressure (`0x400850f4`). The RETRIG menu RTRG opens has its own method (`0x400e27cc`), which returns nonzero for every pad pressure event, so with RTRG held no view below gets pressure, VEL.CUR or not, and in PERF mode the performance pads' pressure freezes. A trig's RETRIG menu (trig + UP or DOWN) passes it on. Pad Pressure Fix sends it on in each case.
- **Trig times in rytm-emu.** `DTEMU_FRAME_TRACE=160,162` prints the analog voice frame's trig switches (BD byte 161 bit 4, SD byte 160 bit 0, RS byte 163 bit 4) with their sample number whenever they change: exact trig timing without reading audio. The sequencer's timing words are in [sequencing.md](../../../docs/module-guides/sequencing.md#analog-rytm-mkii-os-174).
- **A popup takes NO by default.** A `PopupWindow` sits on the view stack for 35 UI ticks. Plain NO closes it, and NO goes no further, so a gesture on NO does not run while one shows and the press does not count as held. Stock's reload messages call the popup's method at vtable + 84 with 0 to let NO through; do the same for a module's own message.
- **A full-screen menu hides the windows under it.** While the KIT menu (FUNC + PLAY MODE) is up, stock sets byte +23 of every window under it to 1, the page's view included, and drawAll skips them; a notice such as KIT 1 SAVED! sets nothing (rytm-emu, OS 1.74). A page a module draws itself in `ev_draw` must not draw while its view's byte is set, or the menu shows mixed with the page.
- **Views above the page can let keys through.** The RECORDER (vtable `0x40234800`) leaves FUNC + NO to the page and main views, so a gesture patched in them also runs there. The manager's last list node (`+24`, view at node `+8`) is the top view.
- **Whether LIVE RECORDING is on.** Byte + 361 of the record state object at `*(u32 *)0x419f28d8`, set by RECORD + PLAY; `0x40036370` returns it only while the sequencer plays. In rytm-emu RECORD alone while playing turned it off and toggled the byte before it, + 360, instead.
- **FUNC + NO belongs to LIVE RECORDING.** On a sound page, while LIVE RECORDING runs, stock holds it to erase the active track's locks step by step (`0x40036370` is true only while the sequencer plays). Outside that it does nothing, with or without a held trig, so a module may take it there; test that state first.
- **The sequencer builds a step ahead.** Per track, `0x4009b0b4` builds step N, locks included, when its tick divider is 0, stamped to fire one step's ticks later. When the divider wraps it publishes N (`0x4009a7e2`) and posts the UI event, and the UI's live-record tick `0x400c7ef6` then acts on N. So the lock erase and the held-note wipe reach a step already queued: it plays once as it was. An edit meant for the step being played has to land before the build.
- **Writing a step lock.** `0x400c058c(track, step, word, value, fine)` sets one, with its change notice, where `track` is `0x400ab29e(0x400af0ac(project), index)` and `word` is a performance lock's parameter index; `0x400bfbbe(track, step, word, 0)` reads one, -1 for none. Values are the kit word's units, and the fine flag is one byte per track and word, so pass the parameter's own (`0x400071a6(id)`). Live recording turns a step with no trig into a lock trig first with `0x400c2698(track, step, 1)`; its tests `0x400bff7e` (a trig that plays) and `0x400c000e` (a lock trig) answer in d0's low byte only. A lock on a trig with a condition plays only when the trig does.
- **72 lock rows a pattern.** A saved pattern keeps a row of 64 steps for each track and parameter with a lock, and a second for a fine one. Stock fills 71 (`0x400094de`): past that, a new lock plays but is not stored, and LOCK MEM FULL! shows. The live locks are a matrix, 5674 bytes a track, 88 a step, 2 a word, with the fine flags at + 5632.
- **Stock's saved pattern and kit differ.** Pattern save fills one RAM buffer that every pattern change refills; kit save overwrites the kit's saved copy and links the kit to the active pattern. On a unit the saved kit and the active kit's edits both survive a power cycle. A module's static state does not, nor does the saved pattern: after a power cycle the pattern keeps its edits and pattern reload changes nothing. A project save keeps edits and saved copies apart, for the pattern and the kit: load that project and both come up with their edits, and the stock reloads return to the saved copies.

## Trig conditions and held trigs

OS 1.74, read from the code; the values and the fill behaviour were checked in rytm-emu.

- **Where a condition lives.** One signed byte per step at track + 576, -1 for no lock, with the track's default at + 713. `0x400c0396(track, step)` reads it and `0x400c03d6(track, step, value)` writes it and sends the change notice. A trig's removal leaves the byte; placing the trig again clears it.
- **Values.** TRC's text for value v is entry 175 + v of the name table at `0x401ec460` (formatter `0x400ff36c`): 0 to 21 name the probabilities 1% to 100%, 22 is FILL and 23 NOT FILL, 24 to 29 PRE, NEI and 1ST and their negations, and 30 to 64 the ratios in the knob's order, 1:2, 2:2, 1:3 … 8:8: N:M is 28 + M(M-1)/2 + N, M from 2 to 8. The evaluator `0x40099520` returns true to skip the trig, so read its branches upside down: its case for 23 is true while fill is on.
- **Trig held + UP, DOWN or RTRG.** The view under the pages sends all three keys to one case (`0x4003d368`): if any held step is inside the pattern (`0x400367c6`), it opens that trig's RETRIG menu, the view at `view + 176`. In the menu, with retrig off, the first UP or DOWN only switches retrig on; later ones step RATE (rytm-emu).
- **Held trigs.** The editor at `view + 108` masks the steps held in GRID RECORDING at + 344 (32-63) and + 348 (0-31), and only there. A view above can take a release (QPER does) and leave a bit behind, so check `is_key_held` too. Entering LIVE RECORDING ends grid editing.
- **A trig's release.** Stock acts on it unless the hold was an edit. To count as one, as a knob turn does, call `0x4003613a(editor, 1)` and `0x40036238(editor)`. That mark ends when the mask empties, so a stale bit keeps it and tapped trigs stop coming off: drop stale bits with `0x400368c0(editor, step, 0)`.
- **Euclidean mode.** Track + 714 is on, and + 721 maps a step to its pulse, -1 for none. `0x400c0e6e` and `0x400c12ae` read them. Stock's held steps, and the step bytes, are then pulses.
- **STEP RECORDING.** RECORD + STOP toggles editor + 362 (`0x400363bc`); it needs its own gate, as the held mask still fills.
- **FILL.** Key 0xb2, handled only in the key routine `0x4003cc94` of the view under the pages. Press sets `0x4193c020`; release ends that and any latch, so a module that takes the press has to lose the release too. `EVENT_TAKEN` does: the OS drops that key's release. A press whose event flags carry bits 1 and 2 (FUNC held, double press: FUNC + FILL FILL) latches instead, and a release flagged bit 1 keeps the latch; a plain release ends it. A module latches fill by dispatching those two events through `KEYDISP` (seen in rytm-emu).
- **A page change ends every hold.** `0x400b7d10` clears the mask, and PAGE moves the page on its release, so with PAGE held the hold stands. A pattern of one page does not end it.
- **rytm-emu.** A hold of about 80M counts as a long press and a trig stays, so tap for 20M. Two keys released on one clock leave one held.

## Queued trigs: looking ahead

OS 1.74, read from the code for Improved AMP's fade before a trig (#1419: its `src/pre-fade.c` has the detail, its TESTING.md what was checked in rytm-emu and on a unit). A module that must act before a trig fires reads the sequencer's queue:

- **Three slots a track.** The sequencer queues a track's next trig a step ahead, its probability already rolled (a trig that will not play is not queued: rytm-emu at 50 %, a unit for FILL and 2:2), in the lowest free of the track's three event slots (`0x4009b5f2`): state at `0x42ac5fb0 + 224 * track + 56 * slot` (0 free), the time it fires at `0x8000fd50 + 12 * track + 4 * slot`, on the clock at `0x8000fe54`, which moves 2 x tempo (`0x40287ffc`, BPM x 120) a block. A trig queued while an earlier one still waits (swing, micro timing) sits in the second or third slot, so read all three. A fourth slot takes pads and MIDI notes at once: those cannot be seen ahead, nor can the first trig after PLAY.
- **One event a track a block.** Stock fires the lowest due slot (`0x4011fe82`, `0x4011ff54`..`0x401204fa`); two events due in one block take that block and the next. Count blocks as stock does, not clock time.
- **Queued is not played.** A mute and a track's held word are applied when the trig fires (`0x4012001e`, `0x40120018`): the trig is queued all the same and dropped. An event restarts the amp envelope only when its flags (slot + 0x14) have a bit of 0x180; a lock trig without a note has none.
- **The sound it will play** is picked when it fires (`0x401201f8`..`0x40120308`): a sound lock (slot + 0x18, -1 for none) plays that pool sound, otherwise the slot's kit (+ 0x1c) plays its sound for the track, and stock skips the copy while the track still holds that kit's sound.
- **Retrigs are not queued.** A series runs on its own tick counter, stepped once a tick (`0x4012089a`); it ends when its length runs out or when the track's next note trig fires. A queued event that fires takes its track's turn for that block, so a retrig tick due then is stepped a block later.
- **Not read to the end:** a pattern change clears queued events from the change on (`0x4009bc60`, `0x4009b6e0`). On external MIDI clock the clock can move less than a block's worth, or stand.

## Performance locks and the QPER knob

OS 1.74, read from the code unless marked.

- **Lock table.** 48 slots of 5 bytes in the kit, shared by all 12 performances: s16 value (8.8), track, parameter index, performance. Performance locks are offsets. They add on top of scenes.
- **Where locks land.** The audio interrupt's loop at `0x40120fc8` adds each slot's lock times its performance's amount to the engine word array `0x8000f774`, entry 26 + 42 * track + index (the FX track's word w at `0x8000fb98` + 2w). A module that plays its own parameter from a real word reads it there, after stock's loop, to follow performance locks.
- **Amount.** Each performance's amount is a u16 at `0x8000e57c`, written through `0x400b2c6a`. The QPER knob and PERF pad pressure both write it, with no priority: the last write stands. The knob only writes to performances linked when it moves. Releasing a pad writes nothing: only a pressure byte of 0 from the panel brings its amount back.
- **Scale.** The knob's value is one panel byte, times 128, so at most 32640. The audio interrupt runs the MAC in fractional mode, so a lock adds lock * amount / 32768. Full QPER is at most 99.6% of a lock. Pad pressure is the panel's byte times 128 too (`0x400a476e`), so it also stops at 32640.
- **Range.** Stock lets a lock pass its parameter's range. Writing the sum to the kit stops at the limit (`0x400a906c`, ranges in the id table at `0x401bfbc8`), so baking such a lock changes the sound.
- **Lock edit.** The parameter pages edit through a locker at offset 440 of the object `0x401816f4` returns; its vtable slots run from +8 (has any) to +36 (lockable). A module can install its own while a key is held.
- **What locks reach.** Performance and scene lockers both refuse a parameter whose category (row +0 of the id table) is above 60 (`0x40006eec`), and the TRIG and EUCLIDEAN rows are 61. With a locker set, a knob on such a row writes nothing (`0x40038650`). Do not answer yes from a locker's own lockable slot: a lock's parameter index (row +4) names a live word, 26 + 42 * track + index, and indices repeat across domains, so Velocity's 1 lands on LFO Multiplier. Note, velocity and length live per step: the sequencer (`0x4009aa28`) reads them from the track at +128, +192 and +256, with -1 falling back to +704 to +706, and never reads the live words.
- **Clear, copy, paste.** `0x400ad56a`, `0x400ad74a` and `0x400ad800`, with undo at `0x400ad652` (kind 1 clear, 2 paste). Stock drops the undo after a later edit [reported].
- **Whole-kit changes.** `0x400a65a4` runs after each one: load, reload, SysEx receive and restores. Writing amounts directly from it and from `ev_project` left the kit blank at boot [measured, the two not separated]. Set a flag in both and act on the tick.

## The audio block

What follows was read and measured for Send FX on OS 1.74 (`src/gate.s` on branch `module/rytm-chorus`, commit `bf62ba19`, [repeat98/modwerk#878](https://github.com/repeat98/modwerk/pull/878)).

- **Where the returns are.** The FX returns routine takes the output slot in d2, runs the PRE return mixer (delay and reverb into the analog mixer, before distortion and the compressor), then the POST one, and ends with `move.l #32,%macsr` at 0x4010ee66 (6 bytes) before it returns. Every send effect needs this site, so it is shared: the Rytm's Modwerk base owns it as the send bus, and a send effect adds a record to its FX list rather than detouring the instruction itself ([Send effects](#send-effects)). The PRE words sit at `0x80000030 + slot × 2048`, left and right on a 64-byte stride, 24-bit values in the low bits. The codec's receive buffer at 0x80007440 holds MAIN, the eight voices and AUDIO IN, 12 words a frame.
- **The converters' names.** OS 1.74 names them at 0x401f881c (ADC) and 0x401f884c (DAC). ADC 0-7 the voices, 8 and 9 `ADC_EXT_IN_L/R`, 10 and 11 `ADC_MAIN_MIX_L/R`. DAC 0-7 the voices, 8-10 the BT, LT and MT trigs, 11 `DAC_DIST_OFFS` (DIST's SYM, as DC), 12 and 13 the PRE returns, 14 and 15 the POST returns, right first. `ADC_EXT_IN` is the pair the receive buffer calls AUDIO IN, in words 10 and 11, despite its name: on a unit the sampler's meter moved for the AUDIO IN jacks and stayed still for the rear EXT IN jacks. EXT IN has no channel of its own and joins after DIST as an analog sum, and none of the control frame's 64 switch bits moves it.
- **Feeding the sends.** The send mixer at 0x4010e6bc runs after the receive routine in the same block: it fills the delay's send at 0x80007a44 and the reverb's at 0x80007b44, 32 stereo frames in the receive words' scale, then calls the delay at 0x4010da24. Add to them at that entry. The PRE words of the output slot in 0x42f92124 can still be written there; they are 24 bits with the top byte clear, so sign extend before adding.
- **The EMAC.** Stock's mixers use the EMAC, and `#32` is its fractional mode, so a mod hooked there can use the EMAC too if it leaves it as stock had it. Read the accumulators it will use (Send FX: ACC0, ACC1 and ACCEXT01) into registers while MACSR still holds 0x20, which neither rounds nor saturates the reads. Then set its own mode, for example 0x80 (signed integer, saturating). Before returning, set `#32` again, then write the accumulators back, ACCEXT01 last.
- **What it buys.** `mac.w` with a parallel load sums the eight voice words in one instruction each: each multiplies a word's upper half by its gain while it loads the next word. To add a 16-bit return to a 24-bit PRE word with 24-bit saturation, shift the word up 8 bits, `move.l` it into an accumulator, `mac.l` the sample by the gain, read it back with `movclr.l` and shift it down 8. In the emulator Send FX's output loop fell from about 40 to about 20 instructions a frame, and the eight voices from about 60 to about 16.
- **Measure it on the unit's own clock.** core-ar2 starts DMA timer 0 free running. Read its counter (0xFC07000C) as the mod's block starts and ends, and divide by the time since the previous block, as Send FX's CPU meter does. In the emulator one instruction executed per 48 kHz frame cost about 0.023 % of the block period.
- **rytm-emu's profiler does not see mod code.** `dtboot --profile-after N` (revision `3c4c42c`) samples only the blocks it runs from its code window, the stock code from 0x40000400. A mod's code, high in RAM (0x47BE0000 on), runs on the stepped path and is never sampled. Measuring Send FX needed a local change to `src/cpu.rs` that samples the stepped branch too, at a jittered interval (33 to 96 instructions) so a loop's period does not alias with it, and a dump of every sampled PC in an address range. Propose such a change to [rytm-emu](https://github.com/trigcondition/rytm-emu) upstream; do not commit emulator code here.
- **`ev_project` comes before the kit is built.** Walking the kit's track sounds inside it at boot left the unit on a different page in rytm-emu (base build for digital voices, 4 November 2026). Set a flag and read the sounds at the next `ev_tick`.

## Sample playback

What follows was read and measured on OS 1.74 while fixing Pipo Loop's turns.

- **STA and END to frames.** Both are 8.8 values of 120. Stock's routine at 0x4011bf44 truncates: the frame is floor(frames * value / 30720), and only a fraction within 1/256 of the next frame rounds up, which on most lengths is about 1 value in 260. Take this from a running voice's position (rec + 4 at 0x80005b30 + 92 per voice) rather than working the instructions by hand: an earlier reading by hand said ceil.
- **The sample DMA aligns to 8 frames.** The prefetch starts its window and its wrap on `frame & ~7`. A mod that follows that window has to use stock's frame: one frame off across a multiple of 8 expects a window 8 frames away, at every pass of that point.
- **Calling that routine from audio code.** It runs before the prefetch sets its MACSR when called from the audio hook at 0x40121134, so set 0xA0 and put the old value back around the call. It expects empty accumulators, as the prefetch does, and leaves them empty. Whether the interrupt saves the accumulators over UI code was not checked, so Pipo Loop's UI uses the formula in plain integers.
- **SMPL WAVEFORM's playhead is the voice's position.** SamplePageView's tick (0x400d1ef6) sets the line, 20 times a second, from `0x4011cfb8(voice)`: rec + 4 over rec + 20 >> 8, across the whole sample. A mod that changes how a voice moves gets a playhead that follows for free; nothing to hook ([Sample RATE's TESTING.md](../../analog-rytm-mkii/modules/sample-rate/TESTING.md)).
- **SMPL WAVEFORM's knob texts and its waveform's area.** SamplePageView's draw (0x400d2004) clears rows 12..52, then for each knob (x 16 + 32 per column, y 61 and 24 from the bottom) calls the view's knob-text routine (vtable +148, or +152 with a trig held) as (view, bmp, x, y, id, value, entry, lock, turning, bare) at 0x400d20ee; turning shows the value in place of the name, and lock adds a 27-wide XOR box (x ± 13, y - 14..y - 8). Holding a page key sets the view's byte +376, which shows every knob's value (stock's own values view). The waveform widget at view + 400 keeps its area in RAM, read at each draw: x0 +28, y0 +32 (from the bottom), width +36, height +40, set to 2, 16, 123, 32; a module can resize it with no code site. Improved SMPL 0.5.0 does both (one row of values, a 37-row waveform).
- **The waveform's sample slot follows parameter changes only.** The widget draws the slot in its +0, which the page's callback 0x400d253a(view) sets from SMP, STA and END when a parameter or the track changes, and sets to 0 (centre line only) while SMP's slot has no sample name (0x400b8192). A slot gets its name (0x41942350) only when the sample loader (0x4009df72) has read its file whole, and the project's pool loads slot by slot (0x400b739c) from background jobs a few seconds after boot. Stock's SAMPLE page opens on its knobs at boot, so this never shows there; a page that shows the waveform from boot calls 0x400d253a(view) again while the slot reads 0 (seen on a unit, Improved SMPL 0.5.0).
- **Test on an odd sample length.** At 24,000 frames every whole STA or END is a multiple of 200 frames, where truncating and rounding up agree. A 23,777-frame ramp showed clicks that 24,000 frames never could.

## A sound's own setting

What follows was read on OS 1.74 and run in rytm-emu while writing Sample RATE; the row, the tap and the turn were then used on a unit.

- **A row in SOUND SETTINGS.** `core_additem` works in any stock menu, not only from `ev_settings`. SoundSetupMenuView's constructor adds its `SMP:` row just before 0x400ef51c, with a4 the view: jump there and add the row, as MIDI Mute does in PORT CONFIG, and replay what you displaced. Stock's checkbox is `0x400716e0(bitmap, glyphs, x + 11, y, 0)`, with the glyphs at `*0x419f0910`, 28 bytes each.
- **Reach the selected sound.** The project (0x4017fa0a), the track selection at its +48 (0x400ae492), the index (0x400b693e, above 11 on the FX track), then 0x400a67ca(project + 352, track), a wrapper whose vtable +40 returns the live sound or 0. Vtable +16 takes stock's change notice, {0x401cb88c, byte 1}, as ENV RESET's setter sends it.
- **A setting the audio code reads.** Don't walk the kit from the interrupt, and don't poll from `ev_tick`. Stock copies a sound's settings to per-track bytes in 0x4011f60a(sound, track): kit load, the row's change notice and, by the code, a sound lock on a trig all go through it. Past its checks, at 0x4011f642 (a2 the sound, d2 the track, d0-d1/a0-a1 free), read your field with `core_store_get` into a byte per track. A byte, not a mask: it is written from the UI and the audio interrupt.
- **A knob's press.** Keys 0x70 to 0x77 are the presses of knobs A to H. Stock's sound page handler reaches 0x4003a5fc with d4 the knob's parameter id, d2 the event and a2 the view, on the press and the release, so an id check there picks the page by itself. A press shows the parameter and changes nothing, and with NO held it clears locks. Stock writes the header at the press, so a change made at the release has to write it again (0x400a9022 for the name, 0x40035fe8 to show it). A real click nudges the encoder: an `ev_enc` handler that takes a tap's press and any turn as a turn misses clicks, so ignore a couple of events during the press. On a unit that alone made a tap reliable; no debounce was needed.
- **Scene and performance mode.** They stay on with no key held, as views on top of the page: read `*(*(*(view + 44) + 24) + 8)` and its vtable, 0x401e305c for scene, 0x401e26c4 for performance. A pad held there edits; the keys alone don't. `0x40036636` on `view + 108` (the lock editor) does not cover this. They hold on every track, the FX track included (rytm-emu, the top view read through `ev_key`'s view manager at `*(brain + 32)`, whichever of FX or PERF was pressed first). A pad pressed in either mode puts an edit view on top until it is let go: PerformanceView's key handler (vtable + 8, `0x400ce17e`) constructs PerformanceEditView, 0x401e2a54 (constructor `0x400ceaaa`; its pad pressure writes the amounts as PerformanceView's does), and SceneView's (`0x400d1798`) constructs 0x401e2ee8 (`0x400d07c0`), both on pad keys 0x90 to 0x9b. A gate on the top view that tests only 0x401e305c and 0x401e26c4 therefore lets go while a pad is held; add the edit views if it must hold then too, or walk the stack from the top node (+24) through each node's previous (+4) to the list (+20). A second routine, `0x401a2d02`, also constructs both edit views and has not been read.
- **A parameter's names.** 0x400a9000 and 0x400a9022 are param_short_name and param_long_name(obj, id), the knob's label and the header. The strings are in the id table at +48 and +40.
- **A setting that stores beside a parameter.** `core_store_set` writes through to the stored copy at once; a stock parameter edit waits for the kit save. Stock's kit reload (NO + PLAY MODE) copies from the RAM saved copy, which the write does not reach, so the two came back together in rytm-emu, power cycle included.
- **Reversing a voice.** Swap the effective STA and END before the prefetch, at 0x4012112c. Stock rebuilds the array every block before that (0x40120e56), so a swap lasts one block: never "put it back", which can match a value by chance and lose the voice's direction. A voice reads 14 frames lower going down: move the position by that much, the way stock's direction byte (rec + 42) says. Wait near the loop's edges: a voice just past an edge sent back over it wraps by a whole loop.

## Control inputs (EXP/CV IN 1 and 2)

The MKII has two EXP/CV IN jacks: -5 V to +5 V on the tip, +5 V supplied on the ring (manual OS 1.72, rear connectors and specifications). Stock reads them as CV or an expression pedal and plays them as a kit macro (KIT > CONTROL IN 1/2 MOD), set up in GLOBAL > CONTROL > CONTROL INPUT 1/2. Read in OS 1.74, 2 November 2026, nothing run yet:

- **Footswitch mode is hidden.** The menu code has a fourth MODE, FSW, with FOOTSW DEST and FOOTSWITCH LEARN rows, but the MODE turn handler (0x40131b48) and the settings setter (0x400fa858) clamp MODE to 0-2 (OFF, CV, EXPR), and the input routine does nothing for mode 3. A footswitch needs a module.
- **The input routine** 0x4013f394 (called from 0x40120f00, the engine update that also plays the performance macros) reads the ADC result words at 0xFC094012 + 2 × port, smooths them into `0x419f0310 + 4 × port` (signed, upper word), whatever the MODE, then scales by MODE into the macro's source at 0x8000fcf8 + 4 × port: EXPR from the learned range to 0-32767, CV from ZERO to MAX, which 0x40120f74 turns into a signed source (ZERO gives no modulation, below it negative). OFF clears the source; mode 3 leaves it as it was, so a module that unhides FSW zeroes it. 0x4013f5ac(port) returns the smoothed level calibrated to millivolts, as the learn screens show it. Port settings live at 0x405c8e54 + 14 × port, read through 0x400fa7e4.
- **The menu's names** are each one `pea` of a stock string, so a module renames a row by pointing that `pea` at its own text: MODE's FSW at 0x40131332, the FOOTSW DEST label at 0x401304f2, FOOTSWITCH LEARN at 0x40131aba, and FOOTSW DEST's list entries 1-5 at 0x401313ee, 0x401313fe, 0x40131412, 0x40131422 and 0x40131432 (its turn limit is the `moveq #5` pair at 0x401309bc). REVERSE DIRECTION's text is shared with EXPR's menu.
- **The CONTROL INPUT view** (draw 0x40130510, update 0x4013092e, both on the view itself) holds the port at +432 and its own copy of the settings record at +436, so +456/+460 are the footswitch levels; +468 is 2 while EXPRESSION LEARN runs and 3 while FOOTSWITCH LEARN does. Turning MODE or FOOTSW DEST changes only the copy: stock saves it (0x401314fc) on leaving the menu, on REVERSE DIRECTION and on a learn's YES, so code reading 0x400fa7e4 sees a menu change only then. A learn's NO leaves the learned levels in the copy, unsaved, and leaving the menu then saves them (seen in rytm-emu for EXPRESSION LEARN); the view method 0x4013153a, which saves and then runs a View base method 115 classes share, is most likely that save.
- **The view redraws only when asked.** The update calls 0x40078580(view + 56) to draw again, and runs when the converter reports, so in rytm-emu the bars never move; a module drawing its own bars invalidates the view itself. The draw tests MODE at 0x4013077c (2 goes on to EXPR's bars at 0x40130784, anything else ends at 0x4013091a) with the view in a2, the screen in d2 and the level in d3. Its primitives take (screen, ..., colour 1): outline 0x4007050a and dithered fill 0x40070a38 (x1, y1, x2, y2), lines 0x4006fbd8 (x1, y, x2) and 0x4006fdc0 (x, y1, y2). FOOTSW DEST's names come from the table at 0x419f000c through one lookup, `lea` at 0x40131462, and the stored choice is a byte nothing limits, so a module grows the list by pointing that `lea` at its own table and opening the turn limit. FOOTSWITCH LEARN's message is two `pea`s at 0x40131e30 and 0x40131e4c; the second line's text is shared with EXPRESSION LEARN.
- **STOP ends live recording** (seen in rytm-emu): the live flag the app's 0x40036370 reads is clear after STOP, so an action that leaves live recording with PLAY checks the flag first or it starts a stopped sequencer.
- **rytm-emu does not model the ADC** at 0xFC094000, so a module that reads these jacks is tested on the unit, or in the emulator through a poked value.

A module can treat a jack as a switch, with hysteresis, but not from `ev_tick` if timing matters. 0x4013f394 smooths the result by 2% a block, so the calibrated level crosses a switch point 5/8 of the way between two levels 49 blocks (about 33 ms) after a clean edge, and the tick adds up to 50 ms more. Control In Actions 0.1.1 reads the result word itself in `ev_render_out`, against thresholds the tick converts from millivolts with 0x4013f5c6(port, mV), the inverse of 0x4013f5ac's conversion, and holds off 15 blocks after each edge for a switch's bounce. To act on the UI task at once, it posts a key message to the UI task's queue from the interrupt, as the converter report does (0x4013f53e): 0x4011fb56() returns the queue and 0x400013b2(queue, message) adds to it; the UI loop (0x400a46f0) reads a message's first byte as its type, and type 0 is a key, with the key at +4, flags at +8 and time at +12, played through the core's `ev_key` site. A key code no panel key uses, taken back in `ev_key` at a low order, runs module code on the UI task within about a block (rytm-emu: 0.02 to 1.12 ms against 4 to 49 ms from the tick). Stock's own panel path is `Brain::key` (the core's `KEYDISP`, 0x400a0336) with a KeyEvent built by 0x40071e7c, as the UI loop does at 0x400a482c; the mode keys are MUTE 0x11, CHRO 0x12, SCNE 0x13, PERF 0x14 and PLAY MODE 0xb5. Live recording is the app's byte +361 (read by 0x40036370, set by 0x4003638a, both on the app singleton), honoured while the record state at 0x4009a88e is on.

## Parameter pages (core 0.4 and later)

From 0.4 the core takes the four routines every parameter page goes through, and the page keys' lists. A mod adds its own page behind a stock page key, or answers a stock page's parameters, by contributing entries to `core_pages`, `core_params` and `core_view_pages` (0.6 adds `core_page_fns`, a page's own info function). Several mods share one key: the key steps through stock's pages, then each mod's, in `core_view_pages`' order. The structures and the view numbers (`CORE_VIEW_AMP`, `CORE_VIEW_DELAY`…) are in [`include/analog-rytm-mk2/pages.h`](include/analog-rytm-mk2/pages.h); elekloader's ADAPTING.md, "Parameter pages (core-ar2 0.4)", has the full contract. A stock page can take knobs too: `core_page_fns` answers its id, as Audio In FX adds D and E to DISTORTION (page 10), whose stock ids are 90, 91, 80, 0, 0, 0, 81, 89. A hidden TEST id gets its names by `ptr` sites at +40 and +48 of the table at 0x401bfbc8, 52 bytes an id, and -1 at +4. Prefer these lists to a page key gesture of a mod's own: a second press only one mod can hold is a dead end ([Choose how a module hooks in](../../../docs/module-guides/README.md#choose-how-a-module-hooks-in)). 0.5 adds mod machines in the hidden machine slots ([`machines.h`](include/analog-rytm-mk2/machines.h)), 0.4 the audio block's load in `core_audio_load` ([`load.h`](include/analog-rytm-mk2/load.h)).

Mods built for 0.3 that patch a page's entry or a page key's list themselves (rytm2_mods v1.2's lfo-rnd, voice-dac, euclid-accents, velocity-humanise and comp-preview 1.0) overlap core's page sites and are refused at link with 0.4 and later; their 0.4 versions contribute entries instead. Mods with only events and storage, and mods that hook deeper in those routines (filter-hz's text, ctrl-all's turn), link with 0.7 as with 0.3.

## Mod machines (core 0.5)

A mod machine takes a hidden machine slot through `core_machines` ([`machines.h`](include/analog-rytm-mk2/machines.h)). Kits store the slot (a kit naming it loads as DISABLE on a build without the mod), so the module claims it as `machine:<slot>` in `platform.claims` (`machine:42` for slot 42): elekloader refuses two mods with the same slot, and `pr:ready` claims it on the [agent board](../../../docs/AGENT_BOARD.md) (`analog-rytm-mkii/42`). What stock does around it, read for OS 1.74 and checked in rytm-emu; the analog figures were measured on a unit:

- **Knob positions are the slot's.** Each slot's SYNTH page shows fixed sound indices: slot 40 A10 B13 C12 D11 / E14 F16 G15 H9, slot 41 A10 B13 C15 D11 / E16 F14 G12 H9, slot 42 A10 B12 C13 D11 / E16 F14 G15 H9. Give a meaning to an index, not to a knob. `machines.h`, an unchanged elekloader copy, says `knobs[]` run "LEV, then A..H's order": that is the record order (`knobs[k]` is sound index 9 + k), not the order of the knobs A..H on the panel, so find each knob's index in this list. Indices 9 (LEV), 10 (TUN) and 11 (DEC) keep stock's MIDI CCs, and stock puts TUN top left, DEC top right and LEV bottom right (manual, Appendix D).
- **Values can show bipolar.** A hidden slot's records may display -64..+63 whatever the core's `centred` says: give such knobs a `core_params` text.
- **Pictures and jumps come from the parameter's RAM record** (`0x419a4888 + 84 * id`), not from code. Its draw std::function (manager `+0x2c`, invoker `+0x30`, called by `0x400a85e8` as (functor, value 8.8, bitmap, x, y, 1)) draws the knob: point it at a stock picture, such as SY DUAL VCO's CFG (`0x400fc1ec`) or SY CHIP's WAV (`0x400febf2`), or a function of the mod's, with no code site. FUNC jumps work the same way at `+0x4c`/`+0x50` ([Core hooks](#core-hooks)). The words can be set again on each `ev_draw`.
- **The title bar shows the long name** in the OS image's record (`0x401bfbc8 + 0x34 * id + 0x28`), drawn before the knob in a frame. Other screens list it too (`0x4004a800`), so a name changed for the title goes back afterwards.
- **`home` picks the list group, the section the place in it** ([Machine list sections](#machine-list-sections)). With `home` 0 and no section entry a machine tops the BD track's list (seen with slots 40 and 41); with `home` -1 it follows DISABLE (slot 42 in MIDI Engine's capture, #1152).
- **The machine list loads as it scrolls.** `MachineListView` (vtable `0x401e5ea4`, built by `0x400def76`) sends UP, DOWN and a turn of any knob A-H (encoder routine `0x400df5b2`, through stock's knob accumulator `0x4006f1fa`) as -1 or +1 to a step function at view + 464, which loads the next machine of the track's list at once (`0x400d4110`, `0x400bedce`, `0x400bd1ba`). Its key routine (`0x400df49e`) never tests FUNC, so FUNC + UP or DOWN moves one machine too. The list widget sits at view + 76, its items (8-byte shared pointers) from + 4 to + 8, each item's value at + 4: a machine, or -1 for a section's dotted line. `0x400dea5e(view, machine)` moves the outline (view + 432) without loading and shows Confirm? Y/N; view + 412 is the machine the list opened with. YES only shows Confirmed! and closes the list: stock keeps no undo for a machine change. NO restores the sound the list opened with.
- **Driving a dual-oscillator voice** (BD, SD, RS; the control frame `0x800063c0` holds their TUNE1, TUNE2, LEVEL1, LEVEL2 at `+90`, `+98` and `+106`, as SY RAW `0x4011aa4c` writes them):
  - A tune word is 16 x Hz after stock's trim `0x401197f4`; call it every block and force it on the trig (without it the oscillator crawls at a few Hz). Below about 40 Hz osc 1 runs sharp and osc 2 flat.
  - A LEVEL word acts within its block. Its loud end saturates mostly after AMP VOL, so it is no drive control.
  - An amp record at -128 still passes about -45 dB: write the LEVELs to 0 when a note ends.
  - Stock's amp envelope state (`0x41329b54 + 32 * v`) stays 3 after its decay and is -1 only after a choke. To end with it, time its decay with `segment_length` (`0x4011e86e`) of AMP DEC's coefficient (`0x401ee61c`).
  - A trig takes two blocks, as stock's machines: the reset bit, then the amps open.
  - Ring mod at 1:1 cancels the fundamental (DC and 2f); an octave up keeps it (f and 3f).

## Mod storage (core 0.3)

Declare each field in `build.json`, then read and write it through the core with elekloader's `analog-rytm-mk2/store.h`. Modwerk's source builder finds it in [`include/`](include/analog-rytm-mk2/store.h), copied unchanged from elekloader's `core-ar2-v0.3` tag (`sdk/imports/core-ar2-store-header-769d9aa.json`); elekloader's own builder uses its SDK's copy:

```json
"storage": [{ "sym": "my_accent", "scope": "track", "bits": 4 }]
```

```c
#include "analog-rytm-mk2/store.h"
STORE_FIELD(my_accent);
unsigned v = core_store_get(STORE(my_accent), live_pattern, track);
core_store_set(STORE(my_accent), live_pattern, track, v + 1);
```

`scope` is `sound` (56 bits a sound), `kit` (64), `global` (40 a slot), `track` (at most 16 bits a pattern track), `pattern` or `project`; `bits` is 1 to 32, and `sym` is a C name no other mod uses. Zero is the default everywhere. The linker places every field from the build's lockfile, as elekloader's `store.ts` does, and appends the lockfile after the image, so the next build keeps each field where it was and older projects keep their data. A field that changes size, or a new field that no longer fits, gives the build a new layout. `core_store_get` and `core_store_set` mask interrupts, so call them from any event. The full rules, which bytes each scope uses and what travels over SysEx and Transfer, are in elekloader's [ADAPTING.md](https://github.com/irpina/elekloader/blob/main/docs/ADAPTING.md) ("Mod storage") and the [core-ar2 README](https://github.com/irpina/elekloader/tree/main/mods/core-ar2).

On modwerk.app each configuration keeps the lockfile of its last build. The next build of that configuration starts from it, so adding or removing a module leaves every other module's fields where projects on the unit expect them. Duplicating a configuration copies the lockfile, and the configuration's JSON backup carries it (the field places only, no project data). A configuration that has never been built, or one shared on the forum, starts from a new layout.

A local image added to a set you already run keeps its saved settings only if it links against the old build's lockfile: without one, `scripts/link-image.mjs` lays the fields out afresh, alphabetically by module, which moved Sample RATE's bit and changed the layout id. Keep each build's lockfile with `--lock-out FILE` and pass it to the next build with `--lock-in FILE`.

Stock's lock saves keep bits 14 to 8 of a lock word, and bits 7 to 1 only in a fine lane: one per track and word, written when that track's fine flag for the word is set (0x40009216). Stock sets the flag on every lock write from the parameter row's +0x14 word (0x400071a6): STA, END, LFO DEP and the machines' tunings have it, sample TUN and FIN do not. So bit 0 is always lost, and a lock's low byte only survives on a row with that flag. A test value that happens to be even hides this: test odd fields. On a unit stock's key table once read pad 1 as held with no pad down, so test pads only where a held pad means something, such as scene and performance mode. `is_key_held` (0x40081c28) maps a key through 0x418d0be0 to a bit of 0x418d1340; the panel scan (0x40081dac) writes that bitmap a row byte at a time, and the panel message parser ORs bits into it (0x40082442) on the path a release can take too. Why pad 1 stuck is not found: a lost release, that path, or the pad's sensor. A held key repeats through `ev_key` with flag 8 set and bit 0 still set, so a tap must ignore repeats, and some keys act at their release, so page tracking has to look at both edges. A module can keep a kit value in an FX word no stock parameter uses (word 29, live kit +0x784): point a hidden id's row at it, with the row's range opened to the whole word, and write through stock's setter (0x400a906c) so the edit stores; the setter lands a moment later, and the word then glides, so don't read it back as an outside change. Stock then saves, copies, pastes and clears it. Only FX words 0 and 29 are unused and saved (stored slots 37 and 20); 38 to 41 are the core's kit-scope mod storage, which the send bus fills. Words 29 and 38 to 41 are the FX track's unused ones (its parameters use 1 to 28 and 30 to 37), but only words up to 37 have a stored slot: the live-to-stored map (0x40007602, table 0x401c5b4c) returns 0 for 38 to 41, and stock's edit-save path (0x400a5692) writes a changed word to that slot unguarded, so on stock a setter edit of word 38 to 41 overwrites stored slot 0, the delay's TIME. The base guards it (base/fxguard.s): the edit save maps 38 to 41 to stored slots 38 to 41, which are the stored kit's mod-storage bytes (core's KIT_SPARE), and writes them with the layout ID and kit generation, so such an edit lands in kit storage and survives a power cycle. Those bits are kit storage, so a module that drives them through the setter must declare them as its own kit field. Per-step locks on these words (base/locks.c, lanes 0x40 to 0x47) carry no layout ID, so a pattern saved with locks on them by another set plays those locks back. Stock's held-trig display, CLEAR LOCKS and other lock users ask a lock by parameter id through three slots of the track's vtable (0x401dcedc value, +4 set, +8 clear; 0x400a9a26 and its neighbours), which map the id to its row's word: when several knobs share one word, answer those ids there, or a lock on any of them inverts and draws the row's knob. A held trig's turn, press and NO + press go through the page view instead (`ParameterPageView`, vtable 0x401cc370, which the FX DIST page uses: slots 0x401cc3ec, 0x401cc3f0, 0x401cc418), with stock's accelerated delta in 8.8 for the turn; stock's versions write the row's word, and for an id with no word they write outside the step. Taking the turn in `ev_enc` instead loses that acceleration. On a held trig stock shows the bar for about 80M, then the lock value and the inversion in one frame, so a `core_params` get should answer the bar only. The page view's FUNC flag to `param_apply_delta` is not the FUNC key: read the key. A parameter's RAM record (0x419a4888 + 84 x id) holds its turn factors at +4 (plain) and +8 (pressed) and its encoder profile pointer at +16 (28 bytes: on, round plain to whole steps, round pressed, then plain and pressed {acceleration, counts a step, units a step}; TUN's 0x4006eb06, STA's 0x4006ead8); every turn of a value, a held trig's lock included, is added at 0x400a88ea (object, id, value, delta) and four 16-byte callbacks from +20 bound to that parameter: copy only the words you mean, never a run of them. Stock's UNDO CLEAR (a second page key + PLAY) needs its last undo record to be that page's clear, and in rytm-emu stock alone never reached it. CLEAR PAGE and its kin take the page key held with PLAY, RECORD and STOP; FUNC + PLAY clears the pattern. Every sound parameter glides to its target at about 22 ms (0x40120cfa: targets 0x8000e5b0 + 84 x track, state 0x8000eeec + 168 x track, 16.16): a module that changes a parameter's meaning together with its value snaps that state, or the old value is heard on the way. An FX trig sets a word's smoother state (0x8000f6cc, a long a word) with its low half 0, even to the same value, so a mark in that low half of a word nothing else reads shows each FX trig with no stock site. In rytm-emu a cold boot takes no `--press` panel keys, and a lock after a reboot needs a stock lock beside it as a control.

## Memory and budgets

- **Shared mod memory:** 128 KiB of DDR (`0x47BE0000–0x47C00000`) for the core and every mod's code and data. A boot-time fill of the whole area was read back intact on a unit.
- **Core image:** core 0.7 is 10,692 bytes `.run` plus 1,368 bytes `.bss` in the shared area, and a 94-byte `.boot` copier (core 0.3: 7,540, 36 and 88). The linker remains authoritative for combined sizes and overlap.
- **Fast SRAM:** none. The core has no `.fast` copy table on this machine.
- **Protected ranges:** none on OS 1.74.
- **Flash:** the main OS must end below `0x300000`; the OS keeps its own stores at `0x300000–0x380000` and `0x380000–0x400000`.

Claim named resources (a SETTINGS row, a SysEx id, a timer) in `platform.claims`; two mods may never claim the same one.

## Toolchain and build

Debian's `m68k-linux-gnu` GCC and binutils for ColdFire (elekloader's default for this machine; set `ELEKLOADER_CROSS` for another prefix such as `m68k-elf-`), and elekloader's builder. Use the exact owner-supplied `Analog-Rytm_MKII_OS1.74.syx`; the builder recognises firmware by hash and changes only the main OS section. From an elekloader checkout, with `core-ar2-0.7.elemod` from the [core-ar2-v0.7](https://github.com/irpina/elekloader/releases/tag/core-ar2-v0.7) pre-release:

```sh
python -m elekloader.sdk.build <module-folder> --stock Analog-Rytm_MKII_OS1.74.syx
python -m elekloader.lint <module-folder>/out/<mod>-<version>-os1.74.elemod \
    --stock Analog-Rytm_MKII_OS1.74.syx --with core-ar2-0.7.elemod
python -m elekloader.patch --stock Analog-Rytm_MKII_OS1.74.syx \
    --mod core-ar2-0.7.elemod --mod <module-folder>/out/<mod>-<version>-os1.74.elemod \
    --out my-build.syx --version XX01
```

A module folder with `build.json` and `modwerk.module.json`, as under `sdk/analog-rytm-mkii/modules/` (`_submissions/` too), has no `mod.json`, so those commands do not take it. Build it with Modwerk's own route instead, which compiles the module with `scripts/build-elemod-packages.mjs`, materializes its recipe against your stock main OS, links it with the core and writes the stock file again with the new main OS section, as the site's browser builder does (the cross toolchain is `MODWERK_CROSS`, default `m68k-elf-`):

```sh
node scripts/link-image.mjs --stock Analog-Rytm_MKII_OS1.74.syx --version XX01 --out my-build.syx \
    --elemod vendor/elekloader/catalog/core-ar2-0.7.elemod --module analog-rytm-mkii:<module-id>
```

Repeat `--module` for several modules, and `--elemod` for a prebuilt package. It prints the flash left (`flashHeadroom`) and the bytes of the 128 KiB shared mod area the set leaves free (`ramSpare`), so you see how close a combined set is before one more module overflows it. Put what your module takes in the manifest's `resources.memoryBytes`: link the base alone, then with your module, and add up how far `ramSpare` and `fastSpare` drop. Every Rytm library module gives it. On the owner's stock 1.74 it reproduces Silent Pad+Trig's PS08 (core-ar2 0.3) byte for byte. It is a local test image: only a unit shows it is safe.

Modwerk's linker covers OS 1.74 (`src/engine/elektron/elemod.ts`), mod storage included. On the owner's stock 1.74 file it links core-ar2 0.3 with each of rytm2_mods v1.2's eleven mods, with the storage mods together, with all eleven, and again from a kept lockfile, byte for byte as elekloader kit 0.7.0 does, and links core-ar2 0.7 alone, with Filter Hz, and with Loop Sync and Retrig Grid from one lockfile as kit 0.7.0 and elekloader at the core's commit do ([verification record](../../../docs/verification/2026-10-27-rytm-core-ar2-pages.md)). In the browser, the Rytm's configuration page checks and builds the Modwerk base's variant the selection needs and the selected library modules from the owner's stock OS 1.74, with elekloader's kit, the base's two packages pinned in `sdk/imports/elekloader-modwerk-base-analog-rytm-mkii-2026-11-05.json` (irpina's 0.3 and 0.7 records stay, 0.7 as the release `machine:base` checks the base against) and each module's source-only package pinned in its own record (`sdk/imports/elekloader-filter-hz-2026-10-23.json`). `src/engine/elekloader/rytm-base.test.ts` builds Filter Hz with Loop Sync, CHORUS alone, and Loop Sync with CHORUS, FLANGER and PHASER through the site's builder from your OS (`MODWERK_RYTM_STOCK`, `MODWERK_RYTM_FX`). Downloads are on since 3 November 2026: the page offers the .syx once the owner confirms they know how to get back to stock. Each configuration keeps the storage lockfile of its last build (Mod storage, above), so a module with storage can enter the library.

## Flash and recover

Send the .syx with Elektron Transfer over USB (MIDI IN and OUT set to the device) and press YES on the unit; it restarts by itself. Restoring the stock .syx the same way returns the unit to stock. If a custom OS will not start, hold FUNC while powering on to open the STARTUP menu, choose TRIG 4 (OS UPGRADE), then send the stock .syx from Transfer's SysEx Transfer Recovery Mode over MIDI DIN; recovery mode does not use USB, so you need a MIDI DIN sender: a USB-MIDI interface, or a serial adapter at 31250 baud as the machine profile describes. Local parsing and link checks do not guarantee hardware safety.
