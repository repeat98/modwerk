# Research, 26 November 2026: a DSP↔SDRAM stream, Midiverb's missing programs, the Midiverb II's LFOs

Three findings that came out of fitting the Quadraverb on FX2. Addresses refer to `origin/base/octatrack-next` at `bd0b40b97` and `origin/main` of the same day; verify before relying on them. Nothing here has run on a unit.

## 1. A module's own audio stream between the DSP and SDRAM

**Why.** One FX2 instance gets at most 15,870 words of DSP memory (`sdk/machines/octatrack/elekloader/dsp.c`, `FX2_BUFFER`). The dynamic loader does not change that: it loads code, and every instance reads its own track's 16K block. The Quadraverb needs up to 31.7K words at half rate. Keeping short delay lines on the DSP and the long ones in SDRAM fits all 90 programs (README, Memory). Midiverb streams program words to the DSP, two a frame, one way and once; no module has a two-way audio channel of its own. Tape Echo moves audio by taking over stock DELAY's ColdFire routine, which has one owner.

**How audio crosses today.** Through the HI08 host port (0x20000000), by eDMA, in a state machine that the frame interrupt (level 5, 0x4000aad0) starts. The table is at 0x400ab61a, and ch7's completion enters it.
- **The block protocol:** ICR ← 0x81; destination (0x6000 | X address); halfword count − 1; host command 0x88 (write) or 0x89 (read); then eDMA in 64-336-byte minor loops.
- **Banks:** the DSP masks the destination with $3fff or $5fff, alternating each frame.
- **Per frame:** 2,752 bytes to core 0, 1,600 to core 1, 1,024 from core 0 and 512 from core 1.
- **Stock DELAY:** its audio comes back in the read-back (64 halfwords a track) and is processed in place by 0x400031a0 during state 5. State 6 returns it to core 0 at X:$x400.
- **What already rides the chain:**
  - the loader's packets (`dl_state7` at 0x40004bc0, and `dl_state3`);
  - USB AUDIO IN, up to 320 bytes a frame to core 0 at $x360.
- **Two documents disagree with the code:** MIGRATION.md:585 and dsp_receiver.asm:8 say stock never pulls from core 0, but it does, at frame entry.

**What the stream needs.**

| | Words crossing per frame, per instance, each way |
| --- | --- |
| Half rate | median 32, worst 160 |
| Full rate | median 224, worst 560 |

Stock DELAY moves about 100 words a frame per track, for eight tracks.

**Proposed design.** Base-owned transfers inside stock's chain, each done stock's way, restoring every TCD field they touch:
- **Core 0:** writes at the shared state-7 scheduler; reads right after stock's frame-entry pull (repointing table word 0x400ab61a).
- **Core 1:** writes at the state-3 entry; reads after state 0 (0x400ab61e).
- **DSP side:** an X mailbox per FX2 position, copied into the module's Y lines in one burst at proc start.
- **Round trip:** about 2-3 frames.
- **Rings:** each track's stock delay ring (0x4f502c10 + track × 1,411,328, uncached, 1.4 MB), through a base take-hook at the seam 0x4000361a. Tape Echo and the stream would share that hook by FX2 id.
- **Declaration:** a feature bit `stream` in `dsp-sites.json`, and a ColdFire table `ot_dsp_streams`. The table declares words a frame each way, ring bytes, and a plan callback that turns the DSP's tap header into aligned ring segments. Admission prices halfwords a frame.

**Order of work.** Each probe is dev-only and on a branch of the cumulative draft #2079.
1. **Probe A:** N extra halfwords a frame to core 0 at state 7, a counter pattern checked on the DSP, and timings.
2. **Probe B:** reads from core 0.
3. **Probe C:** the same for core 1.
4. **Probe D:** an echo through an SDRAM ring, by eDMA, with no CPU copy.
5. The table, the feature bit, the ring take-hook and admission.

**What the probes measure:**
- microseconds per transfer for N = 64 to 2,048;
- frame entry to the state-7 unmask, mean and maximum over at least 30 minutes;
- frame gaps and late entries;
- stalls and eDMA errors;
- integrity;
- the DSP and CPU meters;
- all of it again with USB IN, stock DELAY on eight tracks, and Tape Echo running.

**Risks, most severe first.**
1. A host-port protocol slip stops the DSPs until a power cycle. Causes: a count mismatch, misalignment, an unrestored TCD, or the wrong core selected at state 7.
2. Host-port throughput has never been measured, and state 7 sliding into the next frame causes late entries.
3. Inferred: state 5's transfer must finish before the delay routine does.
4. Mailbox space: core 0's $x320-$x3ff is full with the loader and USB IN. Ledger runs are needed.
5. ColdFire work at interrupt level, the Tape Echo freeze class. Keep the chain code to DMA programming.

The emulators prove bytes and order only, not timing.

**Wear.** RAM only. Modwerk writes the NOR flash only for base updates the owner starts (`flash.c`, two slots). Diagnostics and the boot guard live in battery-backed RAM. Module sets live on the card.

## 2. Midiverb I/II: the 51 missing programs

**Counts.** 225 originals (63 Midiverb, 63 Midifex, 99 Midiverb II without Defeat); 174 ship. Left out:
- Midiverb II 50-69, chorus and flange: the controller patches the program from LFOs (section 3);
- 31 programs over 400 executed instructions a sample (401-558; `generate.mjs` `OVER_BUDGET`).

The generator also shortens 39 programs today: 24 Midiverb, 5 Midifex and 10 Midiverb II. The stream channel would give them back their full length.

**Midiverb is undercharged.**
- On the owner's MKII its core meter rose 17.8 points in use (`evidence/cpu-price.json`, `inUseAdds`). At 45.32 cycles a point (`sdk/cycle-scan/README.md`), that is about **807 chip cycles a sample**.
- It declares 398 executed, charged at 7/4 = 697. The cap is 726 (3,120 − 7 × 342).
- That is about 2.25 cycles per executed instruction, against 1.1-1.4 for stock effects.
- The causes, from the cycle model:
  - every ring read's `y:(r5+n5)` uses an n5 loaded by the instruction just before (an address-register stall);
  - DO costs 5 cycles;
  - each `jmp (r1+n1)` follows the fetch of n1;
  - branches in the halving.
- Today only the base's measured-load admission keeps it in check.

**Where the instructions go** (Midiverb #16, the dearest shipped):
- ring reads: 14 %;
- run setup and dispatch: 19 %;
- the other units with their 3-instruction dispatch: 67 %. Stores cost 9-10 each.

**Plan.**
1. **An instruction diet, bit-exact.** Unrolled runs of 1-7, a fused load+run unit, a fused store+run unit, cheaper stores and hoisted per-call constants. This is modelled to take #16 from 395.5 to about 311.
2. **A stall diet.** Fetch units ahead, Tcc instead of branches, no DO in short runs.
3. **Time it on a dev twin** with `scripts/octatrack-measure.py`, including a hand pass at the dearest program, and declare `--cycles-kind hardware`. That is charged 1:1, so 726 cycles allows about 518 executed if the ratio reaches about 1.4.
4. **The LFO programs** on the DSP, once per call, as Vibrato does: about +12-15 executed a sample.

The ROMs match `generate.mjs`'s md5s, so exact costs come from the generator, not estimates.

## 3. The Midiverb II's chorus and flange LFOs, read from its firmware

`tools/mv2lfo.mjs` runs the Midiverb II's 8031 firmware in this draft's 8051 emulator and measures the LFOs. It uses no table from thement's emulator, which hard-codes them.

**The board, from the disassembly (`tools/dis8051.mjs`).**
- The DSP's program RAM sits behind an address latch at 0xff01 and data at 0xff00 (`MOVX @R0/@R1`, P2 = 0xff). Display and key strobes are at 0xff02/0xff03.
- Keys: row A drives P1.0 low, row B drives P3.1 low, columns read on P1.1-7 (the scan is at 0x564).
- Timer 0 runs every 1 ms (0x68) and multiplexes the display.
- The program number is internal RAM 0x23. The loader at 0x4ce pages the ROM at [0x23] + 0x1c. At boot 0x23 holds 0xff, so it loads page 0x1b, the interpolation table.
- A program change is: 0x23 = p, LCALL 0x49c, back to the main loop at 0x17c.

**The LFO.**
- The patch routine at 0x61f runs once per update.
- LFO 1 is in internal RAM 0x56 (fraction) and 0x57/0x58 (words). LFO 2 is in 0x53 and 0x54/0x55. The op byte is 0x52.
- It patches program bytes 0x05-0x06 and 0x59-0x5e (LFO 1), and 0x5f-0x60 and 0xb3-0xb8 (LFO 2), from the table at 0x1b00 indexed by fraction & 0xf0.
- Per-program setup blocks start at 0xb79, 18 bytes each: centre 0x58/0x55, rates 0x66/0x65, op 0x52.
- Triangle routines are at 0x6cf-0x845 (ceilings 0x3fff, 0x7fff and 0xffff), and sine routines near 0x914 and 0x9f5.

**Open:**
- **What paces the main loop on the hardware.** The 8-sample cadence is thement's figure; the emulator runs the loop free, so periods here are counted in updates.
- **The trigger of 50, 53 and 57** ("Triggered Flange"). Candidate: the edge detector at 0x60f on P3.2, sampled by the timer interrupt.
