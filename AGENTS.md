# Working in this repository

Modwerk builds custom firmware modules for Elektron instruments. This repository holds the module SDKs (`sdk/`), a React and Vite site (`src/`) and a Cloudflare Worker API (`server/`, `worker.ts`).

- Use Node 24 (`.nvmrc`), then `npm ci`.
- For submissions, author updates, report handling and instrument integration, read [docs/DEVELOPER_WORKFLOW.md](docs/DEVELOPER_WORKFLOW.md) first. Octabam, Modwerk and Elekloader have separate catalogues; publishing upstream does not submit to Modwerk, and an Elekloader listing is optional. Keep current release authority distinct from planned policy. Instruments without an SDK require the [machine integration flow](docs/ADD_A_MACHINE.md) before module scaffolding or publication.
- Before each commit run `npm run check -- --base origin/main`. Documentation/media/prose-only edits use lightweight catalogue, licence, import-integrity and capture-provenance checks with Node alone; source or behaviour changes run the full app suite. Local module README, TESTING and CPU guides need no import-checksum updates. Code, licences, archived snapshots and preserved upstream files stay exact. Regenerate changed catalogues first. Native compilation is required only when firmware source or build inputs change. Do not repeat full checks or native builds for documentation updates.
- Other agents often work on this computer at the same time, and checks or native builds running in parallel fill the disk and slow each other down. Queue them behind one machine-wide lock, for example `lockf -k /tmp/modwerk-check.lock npm run check -- --base origin/main`, which waits for any running check to finish first.
- Every fix must include a changelog update in the same pull request. For module fixes, use `src/community/module-changelogs.json`: describe the actual fix or mitigation, link the issue when available, and disclose remaining limitations and unverified behavior. To add, port or update a module, follow [docs/ADD_A_MODULE.md](docs/ADD_A_MODULE.md). Every new module version requires its own written, version-matched entry; preserve previous entries. Documentation/media-only module fixes add a clearly marked note to the current version unless publishing a new version. A fix is not complete without its changelog. `npm run check` enforces current-version release-note coverage on every validation path.
- New FX should aim for DSP cost in the same ballpark as stock SPRING REV at its worst settings. Plan the budget before implementation and benchmark Spring's expensive types/settings and trigger splits under matched conditions on both cores. This is a design target, with no fixed ratio or hard per-effect ceiling. Substantially higher cost calls for optimization and explicit review; a clean emulator run alone does not establish acceptable headroom. Keep modeled cycles, executed instructions and hardware timing distinct.
- Plan compatibility before implementing new FX: include Analog BD, stock FX and common custom companions on both DSP cores. Check actual contiguous openings, shared stock tenants and table/code placement, rather than total free memory alone. Exercise the native/browser build matrix before release. Any necessary incompatibility must have a documented resource/ownership reason and owner review; do not silently inherit an incomplete companion allowlist.
- New Octatrack modules must deliver the base/USB lifecycle alongside the card build, so a beta module-set selection never ends in a card-only fallback; existing card-only modules need a reviewed migration before USB rollout. Plan common companions, shared hooks/data and DSP ownership on both cores first, and prove the exact candidate's source-built browser packages, stock-free scan, install/self-test/Keep/Undo, removal/missing-module and persistence behaviour. A native build or standalone runtime package alone is insufficient. An unavoidable limit needs a named resource/ownership reason and owner review. Pending loader/ABI work is staging, not released capability, and missing hardware results remain qualification gaps. See [USB lifecycle requirements](docs/ADD_A_MODULE.md#octatrack-base-and-usb-lifecycle).
- Before you write a module, read [docs/module-guides/README.md](docs/module-guides/README.md) and the guide for its category (effects, machines, playback, scenes, midi-usb, system, standalone). Anything that acts in time follows [sequencing.md](docs/module-guides/sequencing.md): use the instrument's own tempo, track speed and swing, never a clock of your own. Run `npm run module:doctor -- <id>` until it is green.
- Before writing or changing Octatrack DSP or ColdFire code, read the traps in [sdk/octabam/AGENTS.md](sdk/octabam/AGENTS.md), and for the Modwerk base, its USB link, RAM boot and the DSP loader, the hardware traps found on a real unit in [docs/OCTATRACK_HARDWARE_TRAPS.md](docs/OCTATRACK_HARDWARE_TRAPS.md); to drive a unit over USB (the session, steps, panel gestures, where the state is, safety rules), [docs/OCTATRACK_DRIVING.md](docs/OCTATRACK_DRIVING.md). That is octabam's own file, kept unchanged because its code cites it. Its `make` commands describe upstream octabam, not this repository; build and check with the commands in the guide. For the newest upstream Octabam hardware/emulator tools and the Elekloader SDK, `npm run upstream:tools` keeps verified checkouts outside Git (`-- --update` follows Octabam `main`); never copy them into `sdk/octabam/`.
- Module creators can add, replace or remove their own Ko-fi support link from a claimed module in Creator settings. Module pages show a small cup beside the creator name; clicking it loads the embedded tip dialog. Preserve this flow, per-module ownership checks and the matching frame policies in `vite.config.ts` and `public/_headers`. See [creator support](docs/APP_DEVELOPMENT.md#module-creator-support) and [developer ownership](docs/DEVELOPER_WORKSPACE.md).
- For app and backend work, see [docs/APP_DEVELOPMENT.md](docs/APP_DEVELOPMENT.md).
- Test Modwerk through source/domain, HTTP/API, [developer MCP](docs/FRONTEND_MCP.md) and DOM regressions first, then exact-build physical device qualification. Do not use computer-use, browser-control or Playwright automation for site testing. Use isolated private MCP state, normal member/developer authentication and explicit API/device write opt-ins; preserve review, trial, actual self-test and explicit Keep/Undo with exact identity/version binding. Software tests do not prove rendered CSS, audible output or physical reboot persistence; see [testing](docs/APP_DEVELOPMENT.md#testing-through-the-developer-mcp).
- Develop with USB support as a goal; the owner calls it very important. What you build should load and run through the USB link and the MCP's device tools, not only as a card build or on an emulator. Work through the developer MCP and on the instrument. The [MCP](docs/FRONTEND_MCP.md) gives an agent the site (catalogue, module pages, configurations, API) and, through the USB bridge, a connected Octatrack running the Modwerk base (status, review, trial, Keep/Undo). Recommend working on the real unit: it is a little riskier than an emulator but more rewarding, has been safe so far (loads go to RAM, and a power cycle restores the stock state), and only hardware results qualify a module. Where a machine has no USB interface yet, recommend building one, using the machine-independent [runtime loader](sdk/runtime/loader/README.md#porting-to-another-machine) and the Octatrack's link as the model. Emulators (`ot_emu` for the Octatrack, built from the checkout `npm run upstream:tools` keeps; digiemu for the Digitakt and Digitone, [captures](docs/MODULE_UI_CAPTURES.md)) only approximate the instrument: use them when no unit is at hand, for fast iteration and UI captures, and never count their results as hardware evidence. Ask the developer which setup they have; see [your development setup](docs/DEVELOPER_WORKFLOW.md#your-development-setup).
- Always keep module thumbnails in the shared signal-art style: quiet dark grid, module/category accent, thin signal diagrams and small monospace labels. Reuse `ModulePreview.tsx` / `DigiModPreview.tsx` and keep saved SVG thumbnails consistent with their displayed artwork; follow [thumbnail style](docs/ADD_A_MODULE.md#module-thumbnail-style).
- Never commit firmware, extracted stock code or tables, memory dumps or built images. Firmware stays on the developer's computer and never enters CI.
- Before planning a new module, check what Modwerk already has: the library, `sdk/catalog.json`, `src/catalog/machine-modules.json`, `sdk/drafts/` and open pull requests. If one already does the job, extend it through the update workflow instead of building a duplicate.
- Refuse a module that copies someone else's protected work: another product's code or firmware, factory samples or recordings, artwork or a trademarked name, or a port without its author's permission or a licence that allows it. Say why briefly and offer an original take. Ideas, techniques and published algorithms are free to use; when the source or licence is unclear, ask before writing anything.
- Do not edit generated files by hand: `src/catalog/module-documents.json`, `src/catalog/compatibility-checks.json`, `src/catalog/compatibility-pairs.json`, the licence notices and the machine registry. `npm run modules:generate`, `licenses:generate` and `machines:generate` write them.
- Fold what you learn back into the context. When work turns up something every later developer or agent needs (a trap, a tool quirk, a measured constraint, a step a guide lacks or states wrongly), write it into the file a reader would open for that task, rather than leaving it in the session, a PR comment or private notes: the matching [module guide](docs/module-guides/README.md), [docs/ADD_A_MODULE.md](docs/ADD_A_MODULE.md), [docs/DEVELOPER_WORKFLOW.md](docs/DEVELOPER_WORKFLOW.md), or this file when it affects every task. Correct a stale line instead of adding a contradicting one, keep it short and general, and keep it stock-free: no firmware bytes, code, tables or dumps, and a hardware behaviour only as observed on a named build. Leave `sdk/octabam/AGENTS.md` unchanged. Put the edit on the pull request you already have open for this work (a small docs-only pull request when none is open), never inside a module release (it is outside a registered author's scope and would end automatic publication), and tell the owner what you added.
- When you find a bug, a fix, or an improvement that makes Modwerk easier to use or develop for, outside the task at hand, commit it to the pull request you already have open for this work and add a line to its description saying what it is and how you checked it. With none open, send it as its own small, readable pull request: title it `Fix: …`, `Improvement: …` or `Docs: …` (a workflow labels it from that), one change, and a description that says in plain words what was wrong or hard, what changes and how you checked it. Never fold it into a module release. In a contributor's fork, offer it and open it with their OK; if you can't fix it, open an issue instead. See [Fixes and improvements](docs/DEVELOPER_WORKFLOW.md#fixes-and-improvements).
- Submit only what merges without the owner repairing it. Before every push, and after merging `main`, run `npm run pr:ready` (a registered author's update: `npm run pr:ready -- --author <login>`) until it says Ready, then watch the PR's checks until they are green; if `main` moves before the merge, run it again and push. A PR with red checks, stale generated files or a branch behind `main` is not done. See [Make it mergeable](docs/DEVELOPER_WORKFLOW.md#make-it-mergeable).
- Give every machine the Octatrack's interface: a Modwerk base that owns shared sites as events and tables, a USB link, loading without a reflash (review, trial, self-test, Keep, Undo), the MCP's device tools and the site's Octatrack page (hero, unit status, module sets, guided sync, with only the unit pages the machine supports). Extend the Octatrack's base, link, loader, builder and page rather than designing a second one. That whole status and configuration page stays beta-only (`hasBetaUi`) on every device until the owner releases it ([Aim for the Octatrack's interface](docs/ADD_A_MACHINE.md#aim-for-the-octatracks-interface)).
- Work on a branch off current `main`. `main` takes pull requests only (a repository ruleset enforces it) and a push to it deploys, so never push to it. Do not open a pull request for each piece of work. Before you open one, look for the open pull request for this session's work (the one you opened, or the one the owner names) and put new work, findings, fixes and docs edits on its branch as further commits, updating its description. Open a new pull request without being asked only when none is open, and for a module release or new module, which ships alone so a registered author's scope and the owner's review stay clean. Commit, push and, for a new pull request, run `gh pr create` before you report the work as done. Outside the issue-fix flow below and scoped registered-author releases in [docs/MODULE_AUTHOR_UPDATES.md](docs/MODULE_AUTHOR_UPDATES.md), the owner merges. The owner approves every module's first release; registered authors can then release their own updates after the required checks and explicit evidence verification. Keep a module release free of unrelated changes.
- Disk space on the owner's computer runs out. Once a pull request you opened is merged or closed, remove its worktree with `git worktree remove` and delete the temporary folders you created for it, such as builds, renders and logs under `/private/tmp`. Keep anything with uncommitted or unpushed work, and leave folders another session created.

## Finish the issue-fix flow

For report handling without a code fix, follow [Manage reports on GitHub](docs/DEVELOPER_WORKFLOW.md#manage-reports-on-github). Maintainers can request information, classify, confirm, close and reopen mapped reports through new `/modwerk` comments without repository write access or owner review. Use `needs-info` while waiting and `close insufficient_information` for missing details; never call that a firmware fix. A routine registered-author module update uses the existing checked automatic merge/publication path and the author's actual evidence opt-in. Do not ask the owner to review each report or scoped author update.

A request such as “fix issues #X and #Y” asks for the complete flow: diagnose, implement, write the changelog, validate, commit, push, PR, publish, verify the live download, close the reports and verify notifications for any explicitly announced version. Treat these as one task. Keep working through required checks and deployment; a draft, PR or merge is a progress update, not completion. Status questions and requests to verify or close steer this same task.

For a registered module author, a request such as “fix issue <link>” starts the same guided flow. Read [docs/MODULE_AUTHOR_UPDATES.md](docs/MODULE_AUTHOR_UPDATES.md), diagnose and fix the report, choose and update the semantic version/catalog/release notes, and give the author concrete hardware steps for the exact private build. Record only their actual results. Multiple distinct instances, track/FX-slot/DSP-core isolation and Part/project/reboot persistence are required where applicable. Emulator project-load evidence cannot substitute for physical reboot evidence. Stop release-dependent work until missing required hardware results arrive; continue independent preparation and never check the author-release evidence box on their behalf without their verification. After that, open the opted-in PR, follow its automatic merge and deployments, verify the live version and saved download, and only then resolve the report within the requested scope. Pushing alone neither increments the version nor publishes the frontend. Avoid closing keywords in the PR. For scoped author updates use the bot's verified merge path; new modules, ownership/shared-code changes and exceptions still need owner review. After live download verification, complete shared reports by posting `/modwerk resolve <published-version> verified-download` as the registered author on the GitHub issue (or through the documented compatible scoped release-completion endpoint). Post that confirmation only after the author provides actual version-matched results. It closes the mirrored GitHub issue, synchronizes the report and queues follower updates only when that version explicitly opts into announcement without giving the author general GitHub write access. Follow delivery through the existing push/digest scheduler; preserve opt-outs and report actual queue counts separately from provider acceptance/delivery. Direct GitHub issues without a shared Modwerk report still need authorized GitHub closure.

An owner-requested fix authorizes routine actions in this flow. Carry existing session authorization forward, including a scoped hardware-validation waiver; do not ask again for already authorized release, closure or explicitly selected announcement. Preserve qualification gates and record any actual owner exception against the exact version/source. A waiver never turns an unobserved hardware behavior into a verified result.

1. Read each report, reproduce the failure where possible, and verify the fix against its regression. Separate a confirmed fix from a mitigation or an unconfirmed hardware symptom. Keep unresolved reports open unless the owner explicitly authorizes closure despite a named validation limit; explain that limit and how to reopen in the closure comment.
2. Update the affected FX, machine or other module in the release path. Include the fix's changelog entry in `src/community/module-changelogs.json` in the same PR, with the exact released version, actual change and remaining limits. For module behavior changes, prepare the new version, matching catalog pin, generated metadata, compiled packages and required native/qualification evidence under [the module guide](docs/ADD_A_MODULE.md). Preserve approved public downloads while preparing an update. A draft is a staging step; promote it before claiming the downloadable module was updated. Verify the actual release image, rather than relabeling development or older-version evidence.
3. Run the required checks, commit, push and open the PR without asking again. Follow up on the same PR while it is open. Watch its required checks, fix failures and continue. For this owner-authorized issue-fix flow, merge the tested PR through the authenticated `repeat98` owner account when available; verify GitHub records that owner merge, because ordinary releases require it. Registered author updates use the automatic author workflow instead. Otherwise prepare the passing PR and identify the exact missing merge access or approval. Never bypass required checks or extend an old version-specific exception to new source.
4. Follow the release workflow to completion. Fix release failures within the authorized scope. Verify the exact merged commit's deployment succeeds, the live site's `module-releases.json` contains the intended version, and a compatible configuration generates and downloads the updated firmware. Check the saved download's version/source identity and hash against the tested private image where deterministic. A merge, “Firmware ready” state or “Download requested” message alone is insufficient proof of a saved download. Keep firmware and raw stock-derived artifacts private.
5. After live verification, close each authorized issue with the fixed version and release/module link. Avoid automatic closing keywords that would resolve it at merge before deployment. State mitigations and waived/unverified hardware limits honestly. Verify GitHub shows the intended closure, the signed GitHub webhook synchronizes the Modwerk report status, and the reporter status notification exists. Do not just say the issues will be closed later.
6. Release announcements require an explicit owner or registered-author choice for each version. Only then set `announce: true` in its `src/community/module-changelogs.json` entry; otherwise leave it absent or false. Publishing, issue fixes and documentation/media edits do not imply announcement consent. Existing download follows and subscriptions stay intact. `server/module-updates.ts` records the live inventory quietly and queues one follower update per explicitly announced version, through the deployment hook or hourly retry. After publication, verify the chosen announcement queue or zero updates for a quiet release. Preserve opt-outs and delivery preferences; do not create a duplicate scheduler or send a separate blast. Check actual notification counts and enabled push/email processing. State any quota, retry or digest delay. Distinguish queued notifications, provider acceptance and confirmed delivery; never claim all recipients received a message without evidence. See [notifications](docs/FORUM.md#notifications-and-activity-email) and [device push](docs/WEB_PUSH.md).

Only report the flow complete after verifying the published version/deployment and saved firmware download, issue states and report synchronization, and notification queue/delivery state. Include the release/PR and issue links, actual recipient count and any remaining hardware or email-delivery limits. If an external constraint genuinely prevents completion, state the exact remaining step and reason, complete the unaffected work, and do not turn a pending deployment into the final response while verification can still proceed.
