# Working in this repository

Modwerk builds custom firmware modules for Elektron instruments and the other machines in `sdk/machines/`. This repository holds the module SDKs (`sdk/`), a React and Vite site (`src/`) and a Cloudflare Worker API (`server/`, `worker.ts`). This file holds the rules for every task. The guides it points to hold the detail.

## Commands

Committed skills that load on clone: Claude Code reads `.claude/skills/`, Codex the identical `.agents/skills/`, and any other agent follows `<name>/SKILL.md` when asked. Open a developer's first session with `/modwerk-start` (overview and setup). Then `/modwerk-new-module`, `/modwerk-update-module`, `/modwerk-fix-issue <link>`, `/modwerk-try-on-unit`, `/modwerk-pr-ready`, `/modwerk-review-prs`, `/modwerk-triage-issues`, and the owner's `/modwerk-maintain` ([docs/MAINTENANCE.md](docs/MAINTENANCE.md)).

## Setup and checks

- Use Node 24 (`.nvmrc`), then `npm ci`.
- Before every push, and again after merging `main`, run `npm run pr:ready` (a registered author's update: `npm run pr:ready -- --author <login>`) until it says Ready, then watch the PR's checks until they are green. It fetches `main`, regenerates the catalogues and runs the same `npm run check -- --base origin/main` CI runs; prose-only edits take a lightweight path. A PR with red checks, stale generated files or a branch behind `main` is not done ([Make it mergeable](docs/DEVELOPER_WORKFLOW.md#make-it-mergeable)).
- Do not edit generated files by hand: `src/catalog/module-documents.json`, `src/catalog/compatibility-pairs.json`, the licence notices and the machine registry. `npm run modules:generate`, `modules:pairs -- --write`, `licenses:generate` and `machines:generate` write them.
- Every fix ships with its changelog entry in the same pull request: one file `changelog/<YYYY-MM-DD>-<topic>.md` for the site, app, Worker, SDK or base (never edit `CHANGELOG.md`), or the module's own file in `src/community/module-changelogs/` (`<id>.json`; Digitakt/Digitone `<machine>-<id>.json`) with a version-matched entry written for the people who play the module: at most five short lines on what changed for them ([release notes](docs/ADD_A_MODULE.md#release-notes-required-for-every-fix-and-module-version)). Test evidence and waivers go in the pull request. `npm run check` enforces it.
- Never commit firmware, extracted stock code or tables, memory dumps or built images. Firmware stays on the developer's computer and never enters CI.

## Modules

- Start with [docs/DEVELOPER_WORKFLOW.md](docs/DEVELOPER_WORKFLOW.md): submission, author updates, report handling and your development setup. Octabam, Modwerk and Elekloader have separate catalogues; publishing upstream does not submit to Modwerk. Unlocking a new instrument starts with messaging Jannik Aßfalg on [Discord](https://discord.gg/vzfAdMBtn5), then [docs/ADD_A_MACHINE.md](docs/ADD_A_MACHINE.md).
- Before planning a module, check what Modwerk already has: the library, `sdk/catalog.json`, the machine's module folder, `sdk/drafts/` and open pull requests. If one already does the job, extend it through the update workflow instead of building a duplicate.
- Ask a module's author before you change it. Unless the developer is the module's author or a maintainer named in its manifest, they need the author's OK before any work starts on a module someone else wrote: on GitHub (an issue or comment that @mentions them) or in a message on Discord. Without it, stop and tell the developer to ask first; write no change and open no pull request. Link the OK in the pull request. See [Ask the author first](docs/DEVELOPER_WORKFLOW.md#ask-the-author-first).
- Before you choose how a module hooks in (a key gesture, a page, a menu row, a stock site), look at what the machine's base or core already offers: its hooks, newer upstream core releases not yet pinned, and how the modules already there place their controls. Then work it out with the developer before you build: where a musician looks for the controls, and how the second and tenth module will hook in beside this one. A gesture only one module can hold, such as a second press on a stock page key, is a dead end. On a machine just being unlocked the first modules set the pattern, so take the most care there. Recommend a new base or core hook only when many modules will use it; a site only this module needs stays the module's own declared patch ([Choose how a module hooks in](docs/module-guides/README.md#choose-how-a-module-hooks-in)).
- Refuse a module that breaks the [modding guidelines](MODDING_GUIDELINES.md): copied code, firmware, samples, artwork or trademarked names, a port without permission or licence, an unlock of what a maker sells, one instrument's firmware carried into another, a clone of the maker's other current products, even rewritten, or broken encryption. Say why briefly and offer an original take. Ideas, techniques and published algorithms are free to use; when the source or licence is unclear, ask before writing anything.
- Before you write a module, read [docs/module-guides/README.md](docs/module-guides/README.md) and the guide for its category (effects, machines, playback, scenes, midi-usb, system, standalone), then [docs/ADD_A_MODULE.md](docs/ADD_A_MODULE.md) for the folder, manifest, packages and evidence. Anything that acts in time follows [sequencing.md](docs/module-guides/sequencing.md): the instrument's own tempo, track speed and swing, never a clock of your own. Run `npm run module:doctor -- <id>` until it is green. [sdk/AGENTS.md](sdk/AGENTS.md) has the module rules in working order.
- Build every module to work with everything else. A module installs and runs beside every other module and the base: it never patches a stock site another module or the base patches, it subscribes to the machine's hooks where they exist, and proposes a new one only when several modules will need that site ([Cross-compatibility](docs/module-guides/README.md#cross-compatibility), [Propose a hook](docs/module-guides/README.md#propose-a-hook)). It declares the key gestures and stock screens it takes in `compatibility.uiClaims`, and a deliberate clash in `compatibility.conflicts`, so the configurator never offers both together.
- Refuse a module that depends on another. Every module builds, installs and works when it is the only module chosen, on the stock OS, the base and the shared SDK: no `requires`, no hooks into another module's code, rows, tables or files, no "needs X" rule, no pull request stacked on another module's. Code two modules share goes into the base or the shared SDK first, in its own owner-reviewed pull request, or both features ship as one module, but never two effects ([one effect per module](docs/module-guides/effects.md#one-effect-per-module)). There is no exception.
- Before writing or changing Octatrack DSP or ColdFire code, read the traps in [sdk/octabam/AGENTS.md](sdk/octabam/AGENTS.md), octabam's register [sdk/octabam/docs/TRAPS.md](sdk/octabam/docs/TRAPS.md) and the hardware traps in [docs/OCTATRACK_HARDWARE_TRAPS.md](docs/OCTATRACK_HARDWARE_TRAPS.md); to drive a unit over USB, [docs/OCTATRACK_DRIVING.md](docs/OCTATRACK_DRIVING.md). Leave `sdk/octabam/AGENTS.md` unchanged: octabam's code cites it, and its `make` commands describe upstream octabam, not this repository. `npm run upstream:tools` keeps verified upstream checkouts outside Git; never copy them into `sdk/octabam/`.

## Testing and the instrument

- Develop with USB support as a goal; the owner calls it very important. What you build should load and run through the USB link and the [developer MCP](docs/FRONTEND_MCP.md)'s device tools, not only as a card build or on an emulator. Recommend working on the real unit: loads go to RAM, a power cycle restores the stock state, and only hardware results qualify a module. Where a machine has no USB interface yet, recommend building one ([recipe](docs/MACHINE_RECIPE.md)). Emulators (`ot_emu`, digiemu, rytm-emu) only approximate the instrument: use them for fast iteration and [UI captures](docs/MODULE_UI_CAPTURES.md), never as hardware evidence. Ask the developer which setup they have ([your development setup](docs/DEVELOPER_WORKFLOW.md#your-development-setup)).
- Test Modwerk through source and domain tests, HTTP/API, the developer MCP and DOM regressions first, then exact-build device qualification. Do not use computer-use, browser-control or Playwright automation for site testing; capturing an already displayed page or reviewing supplied images is fine. Software tests do not prove rendered CSS, audible output or reboot persistence ([testing](docs/APP_DEVELOPMENT.md#testing-through-the-developer-mcp)).
- Record only what you observed, on a named build. "Not tested" in TESTING.md is a valid result, and a behaviour a tester reports stays labelled as reported.

## Pull requests

- Work on a branch off current `main`. `main` takes pull requests only and a push to it deploys, so never push to it. Put this session's work, findings, fixes and docs edits on the pull request you already have open, as further commits with an updated description; open a new one only when none is open, and for a module release or new module, which ships alone. Commit, push and `gh pr create` before you report the work as done. The owner merges, and approves every module's first release; registered authors then release their own updates ([docs/MODULE_AUTHOR_UPDATES.md](docs/MODULE_AUTHOR_UPDATES.md)). Keep a module release free of unrelated changes.
- Fold what you learn back into the context. When work turns up something every later developer or agent needs (a trap, a tool quirk, a measured constraint, a step a guide lacks or states wrongly), write it into the file a reader would open for that task: the matching [module guide](docs/module-guides/README.md), [docs/ADD_A_MODULE.md](docs/ADD_A_MODULE.md), [docs/DEVELOPER_WORKFLOW.md](docs/DEVELOPER_WORKFLOW.md), or this file when it affects every task. Correct a stale line instead of adding a contradicting one; keep it short, general and stock-free. A document in `docs/` and this file stay under 32 KB, so make room rather than append, and history goes in a dated record, never in a guide ([where](docs/README.md)). Before every push, say in the pull request what the guides lacked or got wrong and where you fixed it; `npm run pr:ready` and the pull request template ask, and "nothing" is a fine answer. The edit rides on the pull request you have open (a small docs-only pull request when none is open), never inside a module release, and you tell the owner what you added ([Share what you learn](docs/DEVELOPER_WORKFLOW.md#share-what-you-learn)).
- When you find a bug, a fix or an improvement that makes Modwerk easier to use or develop for, outside the task at hand, commit it to the pull request you have open and say in its description what it is and how you checked it. With none open, send it as its own small, readable pull request titled `Fix: …`, `Improvement: …` or `Docs: …`: one change, and a description that says in plain words what was wrong or hard, what changes and how you checked it. Never fold it into a module release. In a contributor's fork, offer it and open it with their OK; if you can't fix it, open an issue ([Fixes and improvements](docs/DEVELOPER_WORKFLOW.md#fixes-and-improvements)).

## Site, machines and operations

- For app and backend work, see [docs/APP_DEVELOPMENT.md](docs/APP_DEVELOPMENT.md). Keep the module creator support flow (the Ko-fi cup, per-module ownership checks and the frame policies in `vite.config.ts` and `public/_headers`) as it is ([creator support](docs/APP_DEVELOPMENT.md#module-creator-support)).
- Give every machine the Octatrack's stack ([recipe](docs/MACHINE_RECIPE.md)): a Modwerk base whose hooks own shared sites, the USB link, loading and base updates without a reflash, the MCP's device tools and the machine page (beta-only, `hasBetaUi`). The base is Modwerk's, started from an upstream core's source; what several modules share (a send bus, an FX list) is the base's. Extend the Octatrack's pieces, never design a second set.
- Running the live site is the owner's work: the complete issue-fix and release flow, mail sendouts, and the locks and disk rules of the owner's computer. They are in [docs/OWNER_OPERATIONS.md](docs/OWNER_OPERATIONS.md); read it when the owner asks for one of those, and not for a contribution. When the owner says "maintain", run the daily pass in [docs/MAINTENANCE.md](docs/MAINTENANCE.md): parallel workers for pull requests, issues, the beta and upstream, then one briefing.
