# Working in this repository

Modwerk builds custom firmware modules for Elektron instruments. This repository holds the module SDKs (`sdk/`), a React and Vite site (`src/`) and a Cloudflare Worker API (`server/`, `worker.ts`).

- Use Node 24 (`.nvmrc`), then `npm ci`.
- For submissions, author updates, report handling and instrument integration, read [docs/DEVELOPER_WORKFLOW.md](docs/DEVELOPER_WORKFLOW.md) first. Octabam, Modwerk and Elekloader have separate catalogues; publishing upstream does not submit to Modwerk, and an Elekloader listing is optional. Keep current release authority distinct from planned policy. Instruments without an SDK require the [machine integration flow](docs/ADD_A_MACHINE.md) before module scaffolding or publication.
- Before each commit run `npm run check -- --base origin/main`. Documentation/media/prose-only edits use the lightweight catalogue, licence and capture-provenance checks; source or behaviour changes run the full app suite. Regenerate changed catalogues first. Native compilation is required only when firmware source or build inputs change. Do not repeat full checks or native builds for documentation updates.
- To add, port or update a module, follow [docs/ADD_A_MODULE.md](docs/ADD_A_MODULE.md). Every new module version requires written, version-matched release notes in `src/community/module-changelogs.json`; preserve previous entries and describe the actual changes and limitations. `npm run check` enforces this on every validation path.
- New FX should aim for DSP cost in the same ballpark as stock SPRING REV at its worst settings. Plan the budget before implementation and benchmark Spring's expensive types/settings and trigger splits under matched conditions on both cores. This is a design target, with no fixed ratio or hard per-effect ceiling. Substantially higher cost calls for optimization and explicit review; a clean emulator run alone does not establish acceptable headroom. Keep modeled cycles, executed instructions and hardware timing distinct.
- Plan compatibility before implementing new FX: include Analog BD, stock FX and common custom companions on both DSP cores. Check actual contiguous openings, shared stock tenants and table/code placement, rather than total free memory alone. Exercise the native/browser build matrix before release. Any necessary incompatibility must have a documented resource/ownership reason and owner review; do not silently inherit an incomplete companion allowlist.
- Before you write a module, read [docs/module-guides/README.md](docs/module-guides/README.md) and the guide for its category (effects, machines, playback, scenes, midi-usb, system, standalone). Anything that acts in time follows [sequencing.md](docs/module-guides/sequencing.md): use the instrument's own tempo, track speed and swing, never a clock of your own. Run `npm run module:doctor -- <id>` until it is green.
- Before writing or changing Octatrack DSP or ColdFire code, read the traps in [sdk/octabam/AGENTS.md](sdk/octabam/AGENTS.md). That is octabam's own file, kept unchanged because its code cites it. Its `make` commands describe upstream octabam, not this repository; build and check with the commands in the guide. For the newest upstream Octabam hardware/emulator tools and the Elekloader SDK, `npm run upstream:tools` keeps verified checkouts outside Git (`-- --update` follows Octabam `main`); never copy them into `sdk/octabam/`.
- Module creators can add, replace or remove their own Ko-fi support link from a claimed module in Creator settings. Module pages show a small cup beside the creator name; clicking it loads the embedded tip dialog. Preserve this flow, per-module ownership checks and the matching frame policies in `vite.config.ts` and `public/_headers`. See [creator support](docs/APP_DEVELOPMENT.md#module-creator-support) and [developer ownership](docs/DEVELOPER_WORKSPACE.md).
- For app and backend work, see [docs/APP_DEVELOPMENT.md](docs/APP_DEVELOPMENT.md).
- Never commit firmware, extracted stock code or tables, memory dumps or built images. Firmware stays on the developer's computer and never enters CI.
- Do not edit generated files by hand: `src/catalog/module-documents.json`, `src/catalog/compatibility-checks.json`, the licence notices and the machine registry. `npm run modules:generate`, `licenses:generate` and `machines:generate` write them.
- Work on a branch off current `main`. Open a pull request for each separate piece of work without being asked: commit, push and run `gh pr create` before you report it as done. Follow-up edits to work that already has an open pull request go on that pull request's branch as further commits, not a new one. Outside the issue-fix flow below and scoped registered-author releases in [docs/MODULE_AUTHOR_UPDATES.md](docs/MODULE_AUTHOR_UPDATES.md), the owner merges. The owner approves every module's first release; registered authors can then release their own updates after the required checks and explicit evidence verification. Keep unrelated changes out of the diff.

## Finish the issue-fix flow

A request such as “fix issues #X and #Y” asks for the complete flow: diagnose, implement, validate, commit, push, PR, publish, verify the live download, close the reports and notify eligible downloaders/subscribers. Treat these as one task. Keep working through required checks and deployment; a draft, PR or merge is a progress update, not completion. Status questions and requests to verify or close steer this same task.

For a registered module author, a request such as “fix issue <link>” starts the same guided flow. Read [docs/MODULE_AUTHOR_UPDATES.md](docs/MODULE_AUTHOR_UPDATES.md), diagnose and fix the report, choose and update the semantic version/catalog/release notes, and give the author concrete hardware steps for the exact private build. Record only their actual results. Multiple distinct instances, track/FX-slot/DSP-core isolation and Part/project/reboot persistence are required where applicable. Emulator project-load evidence cannot substitute for physical reboot evidence. Stop release-dependent work until missing required hardware results arrive; continue independent preparation and never check the author-release evidence box on their behalf without their verification. After that, open the opted-in PR, follow its automatic merge and deployments, verify the live version and saved download, and only then resolve the report within the requested scope. Pushing alone neither increments the version nor publishes the frontend. Avoid closing keywords in the PR. For scoped author updates use the bot's verified merge path; new modules, ownership/shared-code changes and exceptions still need owner review. After live download verification, complete shared reports by posting `/modwerk resolve <published-version> verified-download` as the registered author on the GitHub issue (or through the documented compatible scoped release-completion endpoint). Post that confirmation only after the author provides actual version-matched results. It closes the mirrored GitHub issue, synchronizes the report and queues the existing per-version notifications without giving the author general GitHub write access. Follow delivery through the existing push/digest scheduler; preserve opt-outs and report actual queue counts separately from provider acceptance/delivery. Direct GitHub issues without a shared Modwerk report still need authorized GitHub closure.

An owner-requested fix authorizes routine actions in this flow. Carry existing session authorization forward, including a scoped hardware-validation waiver; do not ask again for already authorized release, closure or notifications. Preserve qualification gates and record any actual owner exception against the exact version/source. A waiver never turns an unobserved hardware behavior into a verified result.

1. Read each report, reproduce the failure where possible, and verify the fix against its regression. Separate a confirmed fix from a mitigation or an unconfirmed hardware symptom. Keep unresolved reports open unless the owner explicitly authorizes closure despite a named validation limit; explain that limit and how to reopen in the closure comment.
2. Update the affected FX, machine or other module in the release path. For module behavior changes, prepare the new version, matching catalog pin and release notes, generated metadata, compiled packages and required native/qualification evidence under [the module guide](docs/ADD_A_MODULE.md). Preserve approved public downloads while preparing an update. A draft is a staging step; promote it before claiming the downloadable module was updated. Verify the actual release image, rather than relabeling development or older-version evidence.
3. Run the required checks, commit, push and open the PR without asking again. Follow up on the same PR while it is open. Watch its required checks, fix failures and continue. For this owner-authorized issue-fix flow, merge the tested PR through the authenticated `repeat98` owner account when available; verify GitHub records that owner merge, because ordinary releases require it. Registered author updates use the automatic author workflow instead. Otherwise prepare the passing PR and identify the exact missing merge access or approval. Never bypass required checks or extend an old version-specific exception to new source.
4. Follow the release workflow to completion. Fix release failures within the authorized scope. Verify the exact merged commit's deployment succeeds, the live site's `module-releases.json` contains the intended version, and a compatible configuration generates and downloads the updated firmware. Check the saved download's version/source identity and hash against the tested private image where deterministic. A merge, “Firmware ready” state or “Download requested” message alone is insufficient proof of a saved download. Keep firmware and raw stock-derived artifacts private.
5. After live verification, close each authorized issue with the fixed version and release/module link. Avoid automatic closing keywords that would resolve it at merge before deployment. State mitigations and waived/unverified hardware limits honestly. Verify GitHub shows the intended closure, the signed GitHub webhook synchronizes the Modwerk report status, and the reporter status notification exists. Do not just say the issues will be closed later.
6. Verify release notifications for eligible downloaders and explicit subscribers. Downloads automatically follow future module versions unless the member opted out. `server/module-updates.ts` polls the deployed inventory hourly and queues one update per follower/version. After the new version is live, use this existing idempotent sync/fanout through authorized operational access, or follow its scheduled run and verify the queue. Preserve opt-outs and delivery preferences; do not create a duplicate scheduler or send a separate blast. Check actual notification counts and enabled push/email processing. State any quota, retry or digest delay. Distinguish queued notifications, provider acceptance and confirmed delivery; never claim all recipients received a message without evidence. See [notifications](docs/FORUM.md#notifications-and-activity-email) and [device push](docs/WEB_PUSH.md).

Only report the flow complete after verifying the published version/deployment and saved firmware download, issue states and report synchronization, and notification queue/delivery state. Include the release/PR and issue links, actual recipient count and any remaining hardware or email-delivery limits. If an external constraint genuinely prevents completion, state the exact remaining step and reason, complete the unaffected work, and do not turn a pending deployment into the final response while verification can still proceed.
