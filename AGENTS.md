# Working in this repository

This repository holds the module SDKs (`sdk/`), a React and Vite site (`src/`) and a Cloudflare Worker API (`server/`, `worker.ts`). This file holds the goal and the rules for every task; the guides it points to hold the detail.

## What Modwerk is for

Modwerk is a community workshop for opening up electronic music hardware to mods. Anyone who owns an instrument can start here. They open its machine page, see how far it has come, and take the next step with their coding agent. Musicians get the results as mods built in the browser from their own OS file, tried over USB and undone with a power cycle.

- **Anyone can start.** The next open step and its guide are one click from the machine page. Each step stands on its own: a documented file format, a rebuilt stock file, a first boot, a hook, a module. You don't have to finish an unlock to have helped, and nobody starts from zero.
- **What one person learns, everyone gets.** Findings land where the next person looks: the machine page, its guide, a check, the agent board. Work is claimed so nobody duplicates it, and it is credited to whoever did it.
- **Every machine grows the same stack.** A base whose hooks own shared sites, the USB link, the device tools and a machine page. Modwerk builds its own implementations.
- **Musicians can trust what they install.** Any set of modules runs side by side and never bricks the unit. The official OS always restores it, and every claim was seen on a real unit.
- **Good for the makers.** Nothing is copied, no protection is broken, nothing a maker sells gets unlocked, and nothing passes as official ([modding guidelines](MODDING_GUIDELINES.md)).
- **The community runs it.** Authors release their own modules, maintainers look after their machines, and the owner keeps the guidelines and the safety of the units.

When these pull apart, the unit's safety and the guidelines come first. Then working beside everything else, then the musician, then the newcomer's path, then speed.

## Setup and checks

- Use Node 24 (`.nvmrc`), then `npm ci`.
- Before every push, and again after merging `main`, run `npm run pr:ready` (a registered author's update: `-- --author <login>`) until it says Ready, then watch the PR's checks until green. It runs what CI runs; a PR with red checks, stale generated files or a branch behind `main` is not done ([Make it mergeable](docs/DEVELOPER_WORKFLOW.md#make-it-mergeable)). A red check names the fix: never edit a check, gate, test or workflow to pass it. A wrong check is its own `Fix:` pull request, never part of a module's.
- Do not edit generated files by hand: `src/catalog/module-documents.json`, the licence notices and the machine registry. `npm run modules:generate`, `licenses:generate` and `machines:generate` write them.
- Every fix ships with its changelog entry in the same pull request: a file `changelog/<YYYY-MM-DD>-<topic>.md` for the site, app, Worker, SDK or base (never edit `CHANGELOG.md`), or a version-matched entry in the module's own file in `src/community/module-changelogs/`, at most five short lines for the people who play it ([release notes](docs/ADD_A_MODULE.md#release-notes-required-for-every-fix-and-module-version)). Test evidence and waivers go in the pull request; `npm run check` enforces it.
- Never commit firmware, extracted stock code or tables, memory dumps or built images. Firmware stays on the developer's computer and never enters CI.

## Modules

- Start with [docs/DEVELOPER_WORKFLOW.md](docs/DEVELOPER_WORKFLOW.md). Octabam, Modwerk and Elekloader have separate catalogues; publishing upstream does not submit to Modwerk. Unlocking a new instrument starts with messaging Jannik Aßfalg on [Discord](https://discord.gg/vzfAdMBtn5), then [docs/ADD_A_MACHINE.md](docs/ADD_A_MACHINE.md).
- Before planning a module, check what exists and who is on it: the library, `sdk/catalog.json`, the machine's module folder, `sdk/drafts/`, open pull requests and the [agent board](docs/AGENT_BOARD.md). If one fits or is claimed, extend it or ask its holder yourself ([Agents talk for themselves](docs/AGENT_BOARD.md#agents-talk-for-themselves)) instead of building a duplicate; never work around a claim.
- Ask a module's author before you change it. Unless the developer is its author or a maintainer named in its manifest, they need the author's OK, on GitHub or Discord, before any work starts. Without it, stop and tell the developer to ask first: write no change and open no pull request. Link the OK in the pull request ([Ask the author first](docs/DEVELOPER_WORKFLOW.md#ask-the-author-first)).
- Before you choose how a module hooks in (a key gesture, a page, a menu row, a stock site), look at what the base or core already offers and how the modules already there place their controls. Then agree with the developer where a musician looks for the controls and how the tenth module will hook in beside this one: a gesture only one module can hold is a dead end, and on a machine just being unlocked the first modules set the pattern. Recommend a new base or core hook only when many modules will use it ([Choose how a module hooks in](docs/module-guides/README.md#choose-how-a-module-hooks-in)).
- Refuse a module that breaks the [modding guidelines](MODDING_GUIDELINES.md): copied code, firmware, samples, artwork or trademarked names, a port without permission or licence, an unlock of what a maker sells, one instrument's firmware in another, a clone of the maker's other current products, even rewritten, or broken encryption. Say why briefly and offer an original take. Ideas, techniques and published algorithms are free; when a source or licence is unclear, ask before writing anything.
- Before you write a module, read [docs/module-guides/README.md](docs/module-guides/README.md) and its category's guide, then [docs/ADD_A_MODULE.md](docs/ADD_A_MODULE.md) for the folder, manifest, packages and evidence. Anything that acts in time follows [sequencing.md](docs/module-guides/sequencing.md): the instrument's own tempo, track speed and swing, never a clock of your own. Run `npm run module:doctor -- <id>` until it is green. [sdk/AGENTS.md](sdk/AGENTS.md) has the module rules in working order.
- Build every module to work with everything else: it never patches a stock site another module or the base patches, and subscribes to the machine's hooks instead ([Cross-compatibility](docs/module-guides/README.md#cross-compatibility)). It declares the key gestures and stock screens it takes in `compatibility.uiClaims`, and a deliberate clash in `compatibility.conflicts`, so the configurator never offers both together.
- Refuse a module that depends on another. Every module builds, installs and works as the only module chosen, on the stock OS, the base and the shared SDK: no `requires`, no hooks into another module's code, rows, tables or files, no pull request stacked on another's. Shared code goes into the base or the shared SDK first, in its own owner-reviewed pull request, or both features ship as one module, but never two effects ([one effect per module](docs/module-guides/effects.md#one-effect-per-module)). There is no exception.
- Before changing Octatrack DSP or ColdFire code, read the traps in [sdk/octabam/AGENTS.md](sdk/octabam/AGENTS.md), [its register](sdk/octabam/docs/TRAPS.md) and the [stock-patch](docs/OCTATRACK_HARDWARE_TRAPS.md#patching-stock-code) and [load](docs/OCTATRACK_HARDWARE_TRAPS.md#coldfire-and-dsp-load) hardware traps; the rest is base work. Leave octabam's AGENTS.md intact: its code cites it, and its `make` commands are upstream's. `npm run upstream:tools` keeps verified upstream checkouts outside Git; never copy them into `sdk/octabam/`. Octatrack modules live in `sdk/octatrack/modules` (`sdk/octabam/modules` is a generated link).

## Testing and the instrument

- Develop for USB, which the owner calls very important: what you build loads and runs through the USB link and the [developer MCP](docs/FRONTEND_MCP.md)'s device tools, and a machine without a USB interface yet should get one ([recipe](docs/MACHINE_RECIPE.md)). Recommend the real unit: a trial loads to RAM and a power cycle ends it, while a Keep writes the set to the card ([driving the Octatrack](docs/OCTATRACK_DRIVING.md)); only hardware results qualify a module. Emulators (`ot_emu`, digiemu, rytm-emu) are for fast iteration and [UI captures](docs/MODULE_UI_CAPTURES.md), never hardware evidence. Ask the developer which setup they have ([your development setup](docs/DEVELOPER_WORKFLOW.md#your-development-setup)).
- Test Modwerk through source and domain tests, HTTP/API, the developer MCP and DOM regressions first, then exact-build device qualification. Do not use computer-use, browser-control or Playwright automation for site testing; capturing an already displayed page or reviewing supplied images is fine. Software tests do not prove rendered CSS, audible output or reboot persistence ([testing](docs/APP_DEVELOPMENT.md#testing-through-the-developer-mcp)).
- Record only what you observed, on a named build. "Not tested" in TESTING.md is a valid result, and a behaviour a tester reports stays labelled as reported.

## Pull requests

- Work on a branch off current `main`; a push to `main` deploys, so never push to it. Put this session's work on the pull request you already have open, as further commits with an updated description; open a new one only when none is open, and for a module release or new module, which ships alone and free of unrelated changes. Push only once the developer says their testing is done, then push and `gh pr create` before you report the work as done. The owner merges and approves every module's first release; registered authors then release their own updates ([docs/MODULE_AUTHOR_UPDATES.md](docs/MODULE_AUTHOR_UPDATES.md)).
- Fold what you learn back into the context. First ask whether `module:doctor`, `pr:ready` or a test can catch it next time, and add that; write a sentence only for what no program can see, in the file a reader would open for that task: the matching guide, or this file. Correct a stale line rather than contradict it; keep it short, general and stock-free. A document in `docs/` and this file stay under 40 KB, so make room rather than append; history goes in a dated record ([where](docs/README.md)). Every pull request says what the guides lacked or got wrong and where you fixed it, and "nothing" is a fine answer ([Share what you learn](docs/DEVELOPER_WORKFLOW.md#share-what-you-learn)).
- A bug, fix or improvement outside the task at hand goes on the pull request you have open, with what it is and how you checked it in the description; with none open, in its own small `Fix: …`, `Improvement: …` or `Docs: …` pull request with one change, never in a module release. In a contributor's fork, offer it and open it with their OK; if you can't fix it, open an issue ([Fixes and improvements](docs/DEVELOPER_WORKFLOW.md#fixes-and-improvements)).

## Site, machines and operations

- For app and backend work, see [docs/APP_DEVELOPMENT.md](docs/APP_DEVELOPMENT.md). Keep the module creator support flow (the Ko-fi cup, per-module ownership checks and the frame policies in `vite.config.ts` and `public/_headers`) as it is ([creator support](docs/APP_DEVELOPMENT.md#module-creator-support)).
- A machine follows the Octatrack's [recipe](docs/MACHINE_RECIPE.md), its page beta-only (`hasBetaUi`). The base is Modwerk's, started from an upstream core's source, and owns what several modules share (a send bus, an FX list). Extend the Octatrack's pieces, never design a second set.
- Running the live site is the owner's work (issue fixes and releases, mail, the owner's computer): [docs/OWNER_OPERATIONS.md](docs/OWNER_OPERATIONS.md), read only when the owner asks for one of those. When the owner says "maintain", run the daily pass in [docs/MAINTENANCE.md](docs/MAINTENANCE.md).
