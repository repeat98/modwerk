# Owner operations

Running the live Modwerk site is the owner's work: the complete issue-fix and release flow, mail sendouts, and the locks and disk rules of the owner's computer. [AGENTS.md](../AGENTS.md) holds the rules for every contribution; this page holds what only the owner's own sessions do. Read it when the owner asks for one of these tasks, not for a module or a site contribution. A request such as "fix issues #X and #Y" follows [the issue-fix flow](#finish-the-issue-fix-flow) below completely.

## On the owner's computer

- Other agents often work on this computer at the same time, and checks or native builds running in parallel fill the disk and slow each other down. Queue them behind one machine-wide lock, for example `lockf -k /tmp/modwerk-check.lock npm run check -- --base origin/main`, which waits for any running check to finish first. There is also one connected Octatrack and one emulator for all of them: one session uses either at a time, and the unit only once the owner says it is free ([driving the unit](OCTATRACK_DRIVING.md)).
- Disk space on the owner's computer runs out. Once a pull request you opened is merged or closed, remove its worktree with `git worktree remove` and delete the temporary folders you created for it, such as builds, renders and logs under `/private/tmp`. Keep anything with uncommitted or unpushed work, and leave folders another session created.

## Email sendouts

- For an email sendout, follow [Preparing an email sendout](COMMUNITY_OPERATIONS.md#preparing-an-email-sendout). Draft and preview revisions are operational work, without app checks or SDK builds; validate any notification-code repair separately.

## Finish the issue-fix flow

For report handling without a code fix, follow [Manage reports on GitHub](DEVELOPER_WORKFLOW.md#manage-reports-on-github). Maintainers can request information, classify, confirm, close and reopen mapped reports through new `/modwerk` comments without repository write access or owner review. Use `needs-info` while waiting and `close insufficient_information` for missing details; never call that a firmware fix. A routine registered-author module update uses the existing checked automatic merge/publication path and the author's actual evidence opt-in. Do not ask the owner to review each report or scoped author update.

A request such as “fix issues #X and #Y” asks for the complete flow: diagnose, implement, write the changelog, validate, commit, push, PR, publish, verify the live download, close the reports and verify notifications for each published version. Treat these as one task. Keep working through required checks and deployment; a draft, PR or merge is a progress update, not completion. Status questions and requests to verify or close steer this same task.

For a registered module author, a request such as “fix issue <link>” starts the same guided flow. Read [docs/MODULE_AUTHOR_UPDATES.md](MODULE_AUTHOR_UPDATES.md), diagnose and fix the report, choose and update the semantic version/catalog/release notes, and give the author concrete hardware steps for the exact private build. Record only their actual results. Multiple distinct instances, track/FX-slot/DSP-core isolation and Part/project/reboot persistence are required where applicable. Emulator project-load evidence cannot substitute for physical reboot evidence. Stop release-dependent work until missing required hardware results arrive; continue independent preparation and never check the author-release evidence box on their behalf without their verification. After that, open the opted-in PR, follow its automatic merge and deployments, verify the live version and saved download, and only then resolve the report within the requested scope. Pushing alone neither increments the version nor publishes the frontend. Avoid closing keywords in the PR. For scoped author updates use the bot's verified merge path; new modules, ownership/shared-code changes and exceptions still need owner review. After live download verification, complete shared reports by posting `/modwerk resolve <published-version> verified-download` as the registered author on the GitHub issue (or through the documented compatible scoped release-completion endpoint). Post that confirmation only after the author provides actual version-matched results. It closes the mirrored GitHub issue, synchronizes the report and queues follower updates automatically without giving the author general GitHub write access. Follow delivery through the existing push/digest scheduler; preserve opt-outs and report actual queue counts separately from provider acceptance/delivery. Direct GitHub issues without a shared Modwerk report still need authorized GitHub closure.

An owner-requested fix authorizes routine actions in this flow. Carry existing session authorization forward, including a scoped hardware-validation waiver; do not ask again for already authorized release, closure or follower notification. Preserve qualification gates and record any actual owner exception against the exact version/source. A waiver never turns an unobserved hardware behavior into a verified result.

1. Read each report in full (`gh issue view N --json body,comments`; `--comments` alone prints only the comments), reproduce the failure where possible, and verify the fix against its regression. Separate a confirmed fix from a mitigation or an unconfirmed hardware symptom. Keep unresolved reports open unless the owner explicitly authorizes closure despite a named validation limit; explain that limit and how to reopen in the closure comment.
2. Update the affected FX, machine or other module in the release path. Include the fix's changelog entry in the module’s `src/community/module-changelogs/<id>.json` in the same PR, with the exact released version and, in at most five short lines for players, what changed for them; test evidence and waivers go in the pull request. For module behavior changes, prepare the new version, matching catalog pin, generated metadata, compiled packages and required native/qualification evidence under [the module guide](ADD_A_MODULE.md). Preserve approved public downloads while preparing an update. A draft is a staging step; promote it before claiming the downloadable module was updated. Verify the actual release image, rather than relabeling development or older-version evidence.
3. Run the required checks, commit, push and open the PR without asking again. Follow up on the same PR while it is open. Watch its required checks, fix failures and continue. For this owner-authorized issue-fix flow, merge the tested PR through the authenticated `repeat98` owner account when available; verify GitHub records that owner merge, because ordinary releases require it. Registered author updates use the automatic author workflow instead. Otherwise prepare the passing PR and identify the exact missing merge access or approval. Never bypass required checks or extend an old version-specific exception to new source.
4. Follow the release workflow to completion. Fix release failures within the authorized scope. Verify the exact merged commit's deployment succeeds, the live site's `module-releases.json` contains the intended version, and a compatible configuration generates and downloads the updated firmware. Check the saved download's version/source identity and hash against the tested private image where deterministic. A merge, “Firmware ready” state or “Download requested” message alone is insufficient proof of a saved download. Keep firmware and raw stock-derived artifacts private.
5. After live verification, close each authorized issue with the fixed version and release/module link. Avoid automatic closing keywords that would resolve it at merge before deployment. State mitigations and waived/unverified hardware limits honestly. Verify GitHub shows the intended closure, the signed GitHub webhook synchronizes the Modwerk report status, and the reporter status notification exists. Do not just say the issues will be closed later.
6. Published module versions automatically notify their followers, including eligible prior downloaders. Update email is enabled by default and uses the existing daily module digest; members can unfollow a module or opt out of update/activity email. No per-release announcement opt-in is required, and legacy `announce` flags do not suppress notifications. Equal-version media or documentation edits do not replay an update, and superseded inventories never announce an older release. Before pushing a module update, the coding agent must tell the maintainer in chat that successful publication will notify followers, including by email according to their preferences; a push alone does not send mail. `server/module-updates.ts` queues one follower update per version through the deployment hook or hourly retry, with missed current versions recovered only through an explicit operator catch-up after the email is approved. After publication verify actual notification counts and enabled push/email processing. Preserve opt-outs and delivery preferences; use the existing daily digest and push scheduler. State any quota, retry or digest delay, and distinguish queued notifications, provider acceptance and confirmed delivery. See [notifications](FORUM.md#notifications-and-activity-email) and [device push](WEB_PUSH.md).

Only report the flow complete after verifying the published version/deployment and saved firmware download, issue states and report synchronization, and notification queue/delivery state. Include the release/PR and issue links, actual recipient count and any remaining hardware or email-delivery limits. If an external constraint genuinely prevents completion, state the exact remaining step and reason, complete the unaffected work, and do not turn a pending deployment into the final response while verification can still proceed.
