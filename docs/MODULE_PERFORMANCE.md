# Performance

How to measure a module before it is listed. The [module guides](module-guides/README.md) hold the rules for every module; `npm run perf:audit` and `module:doctor` judge what you measure here.

A module that is slow, or that only works when it is the only thing running, takes the room of every other module and of the stock instrument. Every new module therefore carries `evidence/performance.json`, a record of three measurements that `npm run perf:audit -- check <file>` judges and `module:doctor` enforces for modules listed from 7 October 2026. Earlier modules keep their [qualification evidence](MODULE_QUALIFICATION.md). Like `fx:audit`, the judgement runs offline and the numbers come from the native harness, which CI never has: a green `npm run check` says nothing about them. Start from `npm run perf:audit -- template dsp` (an effect, machine or other DSP module) `npm run perf:audit -- template coldfire` (a MIDI generator, MIDI effect or other ColdFire code) or `npm run perf:audit -- template key` (ColdFire code that runs only on a key press, below).

New FX should aim for DSP cost in the **same ballpark as stock SPRING REV at its worst settings**. DSP cycles are tightly budgeted, so plan around that reference before implementation and measure as features are added. Benchmark Spring's expensive types/settings, endpoints, moving controls and trigger splits on both cores. Match units, audio buffers, sample/block sizes, core layouts and harness-overhead treatment. This is a design target without a fixed ratio or hard per-effect ceiling. A substantially more expensive design needs optimization and explicit review of the cost and remaining headroom. The complete supported configuration must still fit the instrument's real-time budget.

1. **Cycle count.** The static floor of the worst mode loop (`tools/build/cycle_count.py`: words in the per-sample loop, no contention) and the dearest case you measured, with the knobs moving. Instances multiply: `instancesPerCore` times the static cost must fit what a core can spend (3120 per sample), and a ColdFire module's worst event must fit its deadline. Average or nominal load does not count; this is the same worst case [MODULE_QUALIFICATION.md](MODULE_QUALIFICATION.md) asks for.
2. **A benchmark against stock.** A DSP module is compared with the stock effect closest in function, from `benchmark_stock_dsp.py` (`out/stock_dsp_bench/results.json`, made from your own OS file, so never committed; the record copies only the comparator's figure, the dearest stock figure and the stock image's SHA-256). Up to 1.5x its cost is fine, up to 3x needs a sentence on what the extra cost buys, and above that, or dearer than every stock effect, fails unless `stock.justification` explains it and the owner accepts. A ColdFire module is compared with the stock image under the same flood: `cfmeter.py` reports the longest frame interrupt and the idle time, and the module may add at most 10% of a 362.8 us frame to the interrupt and 10 points of idle time.
3. **A stress run.** A DSP module: the most instances you claim per core, eight tracks, three active LFOs per track and a dozen locked slots per step (`stress_project.py`), rendered for at least 2 s through `dsp_host -guard -dirty` (`pressure.py render`), with no clobber and no hang. Two seconds take about a minute or two in `dsp_host`; keep test runs that short (owner, 15 October 2026). DSP code reached only through stock-code hooks, with no effect id, has no instance for `dsp_host` to render: its record sets `stress.harness` to `ot_emu` and runs the same stress project on the whole built image under the ColdFire port, every track routed through the hooked path, for at least 30 s, with no hang and no late DSP read-back (`guard` and `dirty` stay null). `module:doctor` accepts that only for a module without an effect id. A MIDI module: a flood of notes, CC and clock at the wire rate (about 1040 three-byte messages a second) at 240 BPM or more for at least 10 s, stopping mid-note and changing Part while it runs, with no stuck note, no hang and every dropped message counted and explained.

**A module that runs only on a key press.** ColdFire code with no MIDI path and no work in the frame interrupt (a save, a slice or a lock applied when a key is pressed) runs in the UI task, outside the audio frame. Its record (`template key`) needs no static bound, no stock benchmark and no flood. The dearest press, measured as executed instructions in `ot_emu` or timed on the unit, must fit 26,600,000 cycles (100 ms at 266 MHz, a responsiveness target), and that press, repeated at least 20 times while the sequencer plays with a STOP and a Part change between, must not hang it. `module:doctor` refuses this record for a MIDI or machine module (owner, 5 November 2026).

**A machine that renders on the ColdFire names its CPU price.** The Octatrack base admits a Part's machines against a CPU budget, as it admits effects against the DSP's: a pick past the allowance is refused with a CPU FULL box, and a track past it after a load renders silence, instead of the frame guard dropping renders unannounced. The price is `reserved[0]` of the machine's descriptor (`modwerk_events.h`): the track's worst render in percent of a frame, both passes together, with every voice playing, read with `npm run device -- cpu` on a unit. A machine that names none is charged the base's default; a DSP voice that names none, nothing. A renderer a module writes into stock's renderer table or a track's slots itself is still refused and guarded: the base checks every renderer at the frame builder's two calls, and a stock track that reaches the module's renderer falls back to stock's own when the frame is full.

**A busy unit takes no further machine or module effect.** The prices cover a machine's renders, not what else an installed set costs the ColdFire: modules' hooks, an effect's control code, a DSP voice's glue, a USB recording. So the base also refuses a pick of a module's machine or effect, with the same CPU FULL box and the measured load ("UNIT IS BUSY"), while the CPU meter stands at 85 % or more over its last four seconds. The line comes from 32 units' diagnostics (30 October to 13 November 2026): a five-minute window at 85 % or more had a gap between UI ticks past 100 ms more often than not, and under 65 % one window in twenty did. It reads the moment of the pick, so a Part picked while stopped can still run hot once it plays. Stock's machines and effects and NONE are never refused, so a busy unit can always be made lighter.

**Judge the panel by the CPU meter, not by the frame guard's share.** The panel lags when main's idle time runs out, which the meter measures (`npm run device -- stats`, CUE + PROJ); `guard`'s "in the frame interrupt" is the guarded window only and can move without the panel noticing. On an MKII (13 November 2026) an Euclid in use on one track raised the guard's figure by 10 points while the CPU meter rose 2.5 and the UI tick chain took 4 to 10 % longer. Lowering the guard's share does not buy the panel time either when the cost is not in a guarded render: with FM Synth 0.1.2 installed on no track, a share of 50 % skipped over 20,000 renders a second and the load stayed at 77 %.

**In the frame interrupt, read battery RAM and the bank once a frame.** On the Octatrack one read of the current Part index (`0x100b14cf`, battery RAM) costs about half a microsecond. A test such as "is this track mine" that reads it, the bank pointer and the Part's bytes at every site, for every track, costs points of a frame whether the module is on a track or not: installed on no track with eight tracks playing, POLY8 and FM Synth each added about 8 points of frame interrupt and Repitch 5, in each case mostly one such read (an MKII, 10 November 2026). Nothing below the interrupt runs inside it, so what you read at a frame's first use holds until its exit; the base's FLEX render does that (`machine_registry.c`, `look`). To find such a line on a development base, sample the interrupted PC from a spare timer above level 5 (PIT2, INTC1 source 45, is free): the slow instruction is the one before the PC that piles up. Compare whole builds with `npm run device -- guard`, not two builds' profiles: code placement alone moves the interrupt's share by up to a point.

**The base waits out a frame interrupt that enters late; this is not yet measured on a Modwerk base.** The frame guard bounds how long the frame interrupt runs, not when the next one enters. Upstream octabam measured on an MKII (Sam Banks, 12 and 13 November 2026, octabam `d16d0520`, corrected by `1752f3d4`) that one frame interrupt at START and at a program change runs 475 to 585 µs on every image, so the next enters late: the two entries logged 149 and 155 µs late were followed by a frame exchange that stopped for good (the sequencer holds step 1 until a power cycle), entries less late ran on, and later ones made the DSP skip one frame and run on. So the base keeps each entry's lateness against the DSP's frame grid from DMA timer 3, and an entry more than 110 µs and less than 190 µs late waits until it is 190 µs late, at most 80 µs, before the guard's clock starts (`machine_registry.c`, `mw_frame_enter`; the arithmetic is octabam's, with its correction for the frame after a skipped one). The host test shows the decision and the wait's length, nothing about the DSP. Open: where a Modwerk base's START frame lands is unknown; that the transfer chain is still sending at about 150 µs is upstream's inference; upstream still logged a stall with an entry 209 µs late, outside the window, on a loaded test image; the audio across the skipped frame is not measured; and the self-test's late-frame limit (515 µs between frames) counts a waited frame (553 µs). The assay that would qualify it, on a development base: one first START per power cycle with a 20-channel USB capture opened 2 s before, at least 16 with the wait and 16 with `npm run device -- late:off`, reading `late` after each START (the latest entry, the entries in the window, the waits) and the stall record's frame trace, and listening across the skipped frame. Time added to the frame interrupt can move an entry into the window or out of it, so an A/B that only adds or removes a module says nothing about that module.

**Bound only the module's own code.** A record prices what the module adds: its own code, stack and memory. The stock routines it calls, stock's stack and the stock interrupts are the instrument's, and no module has bounded them. When a number would need that analysis, write "not measured" with the reason and ask the owner the same day, on the pull request or in Discord's dev-support channel before there is one, instead of writing an audit.

The limits are audit defaults, a judgement and not a repository rule: `--usable`, `--ratio-note`, `--ratio-fail` and `--load-fail` move them, and TESTING.md says why. `scripts/perf-audit.test.mjs` proves the judgement on known-good and known-bad records without firmware, so a surprising verdict is as likely to be the measurement as the module. What it cannot tell is whether the numbers are true: the owner reads the commands and reports behind them, and a number nobody measured is "not tested", never a guess.

**One builder for every machine.** A shared elekloader builder is planned to replace octabam's native build and the in-browser elekloader build. The record names no machine, only the unit, so the same record will be written for every machine once the builder lands; until then the Octatrack commands above are the only ones, and a Digitakt or Digitone module states its measured budgets (shared memory, fast SRAM, time at the render hooks) in TESTING.md. Write against the contract and the manifest, not one builder's internals.
