# Performance

Before listing a module, check its measurements with `npm run perf:audit` and `module:doctor`. [Module guides](module-guides/README.md)

Measure the same saved Part stopped and playing, first empty and then with the set installed. Compare module runtime (`profile:3`), CPU (`stats`) and frame interrupt (`guard`). [24-module MKII comparison](verification/2026-11-19-octatrack-idle-dispatch.md) · [Cost of unused modules](verification/2026-11-20-octatrack-unused-module-cost.md)

### What admission and the frame guard are for

The owner's goals (22 November 2026), which every change to admission, the frame guard, the cost table or a module's cost answers to:

- **The general experience comes first.** A refused pick is bad for the player, and so is a stall, a dropped render or a crash. Strike the balance by measuring, not by adding margin.
- **On empty and medium projects, refusals are rare**, Amiga included. Heavy projects and the heaviest modules (POLY8 today) may be refused or drop renders until the guard or stock gets cheaper. A medium project is about eight tracks trigging with three playing samples; a heavy one adds every track on samples, delays open, LFOs and locks.
- **Stock keeps its room.** Modules picked on an empty project must not take what a medium one needs later, so picks are judged against a stock reserve. When a frame overruns anyway, module renders drop first and stock never does.
- **Every figure is measured on a unit:** each module's curve (`first`, then `each`) and its cost at rest (`rest`), and stock's reserve, a track's share and the line where renders start dropping. They travel in the table the site sends, so a cheaper base or a cheaper module raises the room by itself, with no rebuild.
- **A release measures its own cost.** An effect or machine ships with its curve (`device:price -- --write --curve`); `module:doctor` and `modules:check` hold it to that.
- **Installed and unused costs nothing.** A module that nothing uses rests.
- **The refusal box speaks the player's language:** what the module needs, how much of the modules' allowance is used and its maximum, and the CPU meter now. Never a figure that reads as overload at 100 %.
- **The UI stays responsive:** knob turns show on screen within one or two frames of the panel, at any load admission allows.
- **A base ships when these hold on a unit:** empty and medium projects with typical modules almost never refused, and no dropped render on a medium project.

### Build a private Octatrack CPU baseline

Use `build_core.py` to select a private development profile. `octatrack:base` checks the published beta’s identity even with `--out`.

From the checkout root, run `npm ci` on Node 24. Use Python 3.12+, the reviewed `m68k-elf` tools on PATH, the pinned Elekloader from `npm run upstream:tools` and the built Octabam DSP assembler. Set `OT_STOCK` to your OS 1.40C file and `BASELINE_PARENT` to an existing directory outside Git. Each run needs a new output directory.

```sh
export ELEKLOADER_DSP_ASM="$HOME/.cache/modwerk-upstream/octabam/vendor/dsp56300/build/source/dsp_host/dsp_asm"
python3 -B sdk/machines/octatrack/elekloader/build_core.py \
  --stock "$OT_STOCK" --upstream "$HOME/.cache/modwerk-upstream/elekloader" \
  --output "$BASELINE_PARENT/cpu-baseline" --dev --dsp-loader --site-events \
  --table-owners sdk/machines/octatrack/module-adapters/table-owners.json \
  --resident-stock-hooks --resident-on-demand
```

Omit the last two flags for a baseline without resident hooks. Since 0.8 the registry provides `modwerk_machine_assigned` when the resident controller is absent. `sdk/tests/test_machine_events.py` checks both profiles. Record the flags and revision.

For a CPU baseline, run the named development build with the same saved Part, transport state and empty inventory. Stock OS 1.40C has no `stats` meter.

### Measure a module

A module that is slow, or that only works when it is the only thing running, takes the room of every other module and of the stock instrument. Every new module therefore carries `evidence/performance.json`, a record of three measurements that `npm run perf:audit -- check <file>` judges and `module:doctor` enforces for modules listed from 7 October 2026. Earlier modules keep their [qualification evidence](MODULE_QUALIFICATION.md). Like `fx:audit`, the judgement runs offline and the numbers come from the native harness, which CI never has: a green `npm run check` says nothing about them. Start from `npm run perf:audit -- template dsp` (an effect, machine or other DSP module) `npm run perf:audit -- template coldfire` (a MIDI generator, MIDI effect or other ColdFire code) or `npm run perf:audit -- template key` (ColdFire code that runs only on a key press, below).


**A release proves its whole cost on a unit** (owner, 23 November 2026: every refused pick, silent module, stall and crash costs the player): idle, mean, DSP, curve, an admission run and the worst case, each on the version it ships. From 24 November 2026 `module:doctor` and `modules:check` refuse a release without them, whenever its module was first listed ([what a release measures](TEST_PROCEDURE.md#what-a-release-measures)).

**Every release of an effect or a machine measures its instance curve on a unit** (owner, 22 November 2026: every refused pick and every skipped render costs the player). `npm run device:price -- --write --curve T1,T3,T6,T7 --base ID --scene TEXT ID|FILE.mwrm` places the module on one to four empty tracks (machines) or their slots (effects), each picked on an empty pattern (`--pick-pattern`) and read on a medium one (`--measure-pattern`: a trig every four steps on six tracks, two playing samples and the module's four without, about 80 % of a frame with stock alone), and stops once a reading drops renders or passes `--limit` (125 %; lower for a run nobody watches). Not a busy pattern: near the line the guard drops renders and caps the longest frame, so a module reads low there (SYNTIZ 0.1.0: first 19.1 on eight busy tracks, 24.9 on the medium pattern), and stock's own growth is the reserve's. From what the longest frame gained it fits `first` (the first instance on a Part) and `each` (every further one, the steepest step from the third on), on top of `rest`, what the module adds installed on no track or slot (counted from 2 points up; less is the readings' scatter), which the base charges every installed module in the reserve, and writes them to `evidence/frame-cost.json` and the module's line in `sdk/machines/octatrack/frame-costs.json`, which admission charges. A module that writes trigs (VECTOR) leaves them after its trial's rollback, so the tool stops when either pattern's trigs changed: measure it on a scratch pattern.
New FX should aim for DSP cost in the **same ballpark as stock SPRING REV at its worst settings**. DSP cycles are tightly budgeted, so plan around that reference before implementation and measure as features are added. Benchmark Spring's expensive types/settings, endpoints, moving controls and trigger splits on both cores. Match units, audio buffers, sample/block sizes, core layouts and harness-overhead treatment. This is a design target without a fixed ratio or hard per-effect ceiling. A substantially more expensive design needs optimization and explicit review of the cost and remaining headroom. The complete supported configuration must still fit the instrument's real-time budget.

1. **Cycle count.** The static floor of the worst mode loop (`tools/build/cycle_count.py`: words in the per-sample loop, no contention) and the dearest case you measured, with the knobs moving. Instances multiply: `instancesPerCore` times the static cost must fit what a core can spend (3120 per sample), and a ColdFire module's worst event must fit its deadline. Average or nominal load does not count; this is the same worst case [MODULE_QUALIFICATION.md](MODULE_QUALIFICATION.md) asks for.
2. **A benchmark against stock.** A DSP module is compared with the stock effect closest in function, from `benchmark_stock_dsp.py` (`out/stock_dsp_bench/results.json`, made from your own OS file, so never committed; the record copies only the comparator's figure, the dearest stock figure and the stock image's SHA-256). Up to 1.5x its cost is fine, up to 3x needs a sentence on what the extra cost buys, and above that, or dearer than every stock effect, fails unless `stock.justification` explains it and the owner accepts. A ColdFire module is compared with the stock image under the same flood: `cfmeter.py` reports the longest frame interrupt and the idle time, and the module may add at most 10% of a 362.8 us frame to the interrupt and 10 points of idle time. A track machine whose `resources.cpuPrice` is a `machine-render` price is judged against that price instead, since the base books that share of the frame for each track playing it. For a machine, measure the available render time separately in the busiest pattern it supports. [Machine render checklist](module-guides/machines.md#track-machines)
3. **A stress run.** A DSP module: the most instances you claim per core, eight tracks, three active LFOs per track and a dozen locked slots per step (`stress_project.py`), rendered for at least 2 s through `dsp_host -guard -dirty` (`pressure.py render`), with no clobber and no hang. Two seconds take about a minute or two in `dsp_host`; keep test runs that short (owner, 15 October 2026). DSP code reached only through stock-code hooks, with no effect id, has no instance for `dsp_host` to render: its record sets `stress.harness` to `ot_emu` and runs the same stress project on the whole built image under the ColdFire port, every track routed through the hooked path, for at least 30 s, with no hang and no late DSP read-back (`guard` and `dirty` stay null). `module:doctor` accepts that only for a module without an effect id. A MIDI module: a flood of notes, CC and clock at the wire rate (about 1040 three-byte messages a second) at 240 BPM or more for at least 10 s, stopping mid-note and changing Part while it runs, with no stuck note, no hang and every dropped message counted and explained.

**Stamp the record when you measure.** `npm run perf:audit -- check <module>/evidence/performance.json --stamp`, run right after the measurements, writes `sourceSha256`: the hash of the module's source the numbers were taken on (everything but its documents, media, manifest and `evidence/`). `module:doctor` fails a stamp for other source, so changed code needs new numbers, and a record without one for a module listed from 18 November 2026 or a draft judged as a release; earlier records are asked to stamp at their next measurement. Measure, then stamp: a stamp on numbers you did not take again is a false record. An owner's exact-source approval (`sdk/approvals/<id>-build-approval.json`) binds the whole module, its record included, so it stands in for the stamp. With `current-build-hardware` waived, it also excuses a MIDI flood that ran at the audit's rate without a hang but did not count stuck notes or lost messages. It never excuses a measured failure.

**The cycle scan checks what you record.** Instructions are not cycles: a DSP56300 instruction takes 1 to 6 cycles and the
core idles on some sequences (pipeline stalls), so a module's instructions a sample understate what it costs beside stock
(every stock effect runs 1.09 to 1.44 cycles an instruction; the scanned modules 1.45 to 1.92, 19 November 2026). After
measuring, run `node scripts/cycle-scan.mjs record <id>` on your computer ([sdk/cycle-scan](../sdk/cycle-scan/README.md)):
it prices the module's executed path and its stock comparator's from the chip manual and commits
`sdk/cycle-scan/records/<id>.json`. The check in `npm run check` then fails a record whose module source changed since its
scan, and a performance.json that records fewer than 90 % of the instructions the scan saw executing at the dearest
setting. It is a model; the unit stays the judge.

**A module that runs only on a key press.** ColdFire code with no MIDI path and no work in the frame interrupt (a save, a slice or a lock applied when a key is pressed) runs in the UI task, outside the audio frame. Its record (`template key`) needs no static bound, no stock benchmark and no flood. The dearest press, measured as executed instructions in `ot_emu` or timed on the unit, must fit 26,600,000 cycles (100 ms at 266 MHz, a responsiveness target), and that press, repeated at least 20 times while the sequencer plays with a STOP and a Part change between, must not hang it. `module:doctor` refuses this record for a MIDI or machine module (owner, 5 November 2026).

**Every module names its CPU price** (owner, 16 November 2026): `resources.cpuPrice` in `octamod.module.json`, as `{"value", "unit": "percent-of-frame", "measure", "tool", "date", "conditions", "source"}`, measured on a unit. A machine's `measure` is `machine-render`, a whole percent read with `npm run device -- do` and `guard` (below), and its descriptor's `reserved[0]` carries the same number (a ported machine's comes from `"cpuPrice"` in its `machine-ports.json` entry). Every other module's is `frame-interrupt`, the share `npm run device:price -- <id>` reports, to a tenth of a point; with `--write --base ID --scene TEXT` the tool writes that price itself, with its readings in `evidence/cpu-price.json`, and the checks recompute the price from them, so it is never typed. A price and its readings change no module: a published version stays qualified without a new release, as long as nothing else in its folder changed. Set the measured slot (`--slot`, T1 by default) to NONE first and read `ui` again before you record the scene: right after a bank change it can still show the last bank's effects. A pick by the package's name fails where the chooser shows the effect's own name (Ring SC's "RINGMOD SC"); `--fx-name ID=NAME` gives it, and a failed pick writes no price; the base reads no effect or hook price yet, so for those it is a declaration the next base can admit by. `conditions` names the model, the base, what played and for how long, and `source` the file holding the run's output (TESTING.md). `modules:check` (so CI and `pr:ready`) and `module:doctor` refuse a module without one, or a machine whose two numbers differ. The modules listed before 17 November 2026 wait on `sdk/module-cpu-prices-pending.json` until measured; the list only shrinks, and a module that names its price deletes its line in the same pull request. A ported machine's descriptor is generated by `machine_ports.py` from `"cpuPrice"` in its `machine-ports.json` entry.

For a private `.mwrm` file, `device:price` reads the supported FX slots and package name from the file. Give the chooser name with `--fx-name ID=NAME` when it differs. The tool uses the runtime ID to identify a published module even when the file is named after its version. Name an unpublished file after its module ID.

**A machine that renders on the ColdFire names its CPU price.** The Octatrack base admits a Part's machines against a CPU budget, as it admits effects against the DSP's: a pick past the allowance is refused with a CPU FULL box, and a track past it after a load renders silence, instead of the frame guard dropping renders unannounced. The price is `reserved[0]` of the machine's descriptor (`modwerk_events.h`): what one track of the machine adds to the frame interrupt while it plays, in percent of a frame, rounded up (owner, 17 November 2026: its mean cost, not its worst render; the frame guard covers the peaks, and the base adds prices up against the CPU meter, which is a mean). Measure it on a unit: one track on the machine with a trig on every step and every voice it can sound playing, `npm run device -- do 'PLAY w2500 guard w6000 guard STOP'`, the second `guard` line's "in the frame interrupt"; then the same with that track's trigs removed, and take the difference. On an MKII that day, with default sounds, FM Synth 0.1.3 added 4.6 points and SYNTIZ 0.1.0 11.2, while their longest single renders were 26.6 % and 37.6 % of a frame: priced by the worst render, the fourth FM Synth track was refused although eight played at the load of eight sample tracks. `modwerk_events.h` still says "worst render" and names no `reserved[1]`: USB Audio's reviewed recipe hashes that header, so it changes with the next USB Audio release. A machine that names none is charged the base's default; a DSP voice that names none, nothing. A renderer a module writes into stock's renderer table or a track's slots itself is still refused and guarded: the base checks every renderer at the frame builder's two calls, and a stock track that reaches the module's renderer falls back to stock's own when the frame is full. Skip the engine on a track that cannot sound: on an MKII (22 November 2026) an FM Synth track playing no note still cost about 15 frame points, and after a note's release its engine kept running the FM loop at zero gain. FM Synth 0.1.5 ships such a track's silence without its engine, bit for bit what the full path ships, and its test runs both against each other (`test_silence.py`, the full path assembled alone with `FM_NO_SILENT`). On the owner's MKII (23 November 2026) that saving did not show: a track that had played notes still cost about 11 frame points while silent or stopped (#2030), so measure the silent case on a unit too.

**A machine's DSP voice is charged on the DSP's ledger.** A voice that replaces a track's stock source declares its chip cycles a sample (and any per-core engine cost) in its package's DSP header. The base charges it on the track's core beside the effects the bank's Parts name there, 7/4 of it while it is an emulator figure (executed instructions or modeled cycles), so a hardware figure usually buys a lot of room. A bank or project load that needs more room drops voices from that core's last track down: those tracks render silence, with a DSP FULL box, until there is room again (#1542). To measure a voice that cannot be admitted yet, build a development twin with `build_core.py … --dev --measure-voices`, which admits voices without a cycle charge, and read both cores' meters (`stats`) with the voice playing on a Part with NONE in every FX slot, against the same Part on FLEX. Nothing guards the DSP on such a twin. Never ship a package whose price is lowered to get it admitted: a voice priced under its real cost can stop a core's frames.

**A pick that would fill the frame is refused.** The prices bound a Part's renders at their worst. What else an installed set costs the frame interrupt (modules' hooks, an effect's ColdFire work, a DSP voice's glue), and what a machine costs between its worst frames, no price knows. So every pick of a module's machine or effect is judged by the longest frame interrupt of the last four seconds, as the unit would play with the pick on top and what it replaces taken off, and refused with the CPU FULL box at 110 % of a frame (`mw_frame_line`, `status.c`; owner, 22 November 2026: module-heavy Parts dropped renders from about 112 %, stock-heavy ones not until 125 %). The guard drops a render when a frame would run past its share and the credit the frames before it left, so the frames at the top decide, not the mean. On the owner's MKII (base 0.8, 21 and 22 November 2026, a trig every four steps on all eight tracks) of 32 readings of 8 to 30 s none dropped a render with the longest frame from 95 to 125 % (Analog BD at a 61.7 % mean among them), half did from 125 to 130 % and every one past 130 %, at means from 50.7 %. The CPU meter, which judged picks before, had admitted SYNTIZ, Analog BD, FM Synth and Tape Echo past that point (24 to 165 dropped renders each) and refused Amiga and POLY8, which fit. What a pick adds comes from `sdk/machines/octatrack/frame-costs.json`, which the site sends with every module set (MWMS v2, base capability 4096) and the base keeps through a power cycle: for each module its `first`, what one alone on the Part adds to the longest frame (waking from rest included), and its `each`, what every further one adds. A machine the table does not list is charged its meter cost (`reserved[1]`, below) or its price a track; an effect, nothing; either, 3 % more when it wakes from rest. **Stock keeps its room:** a pick is judged as if the Part already played the stock load the pattern that plays asks for, and a queued one (owner, 22 November 2026: against the pattern that plays, not the bank's busiest, which refused every pick in a bank with one stacked pattern; a later switch to a busier one is the guard's): its figure, or once it has played four seconds with these trigs its own stock as measured plus the margin when that is less (how many tracks trig on its busiest step, with samples on all eight: 37 % for none, 64 % for one, then about 5.4 % a track to 101 % for eight, and 2.6 % for each further track that trigs off that step), plus an 8 % margin for what a pattern cannot show (delays waking added 7 % at eight), never under 60 % (owner, 22 November 2026: refusals should be rare on empty and medium projects, while heavy ones may refuse and drop; a project built on an empty pattern keeps room for its trigs), with what the modules it runs cost on top, and every installed module's `rest`, what it adds installed and used nowhere (FM Synth 0.1.4: 20.3 %; a module that rests, about 0), whenever that is more than the unit measures, so modules placed on an empty pattern never take the room its first trigs need. A pick that adds 2 % or less is always made: it is not what fills the frame. A machine's first instance on a track that plays a sample takes 2.5 % off the measured figure and off a measured stock (what that sample's render was worth there), 7 % off the ladder; a further one is charged whole (its trig starts cost about the sample's). What played since the last pick counts when it is more than the kept figure with the picks on top. **A pattern predicted past the ceiling goes without only what it must** (owner, 22 November 2026): when the pattern that plays, or one queued, would with the Part's modules pass 122 %, the Part's module machines go silent from its first frame, dearest first, then effects that subscribe `ev_frame_deadline` bypass dry (its `rest`), dearest first, until it is under the ceiling; no other effect is touched. The screen says PATTERN IS BUSY and names what went, and the log gets a `brake` incident with bit 23 (otherwise such a pattern ran at 130 % with a click every two or three seconds, and once stalled); when the installed modules' `rest` is what leaves no room, CPU FULL says UNUSED MODULES. A machine counts there less the sample its track would play (`mw_track_stock`, 7 %); an effect counts whole. Past the reserve (LFOs and p-locks took a full stock Part to 113 %) the guard drops module renders, never stock's own. **A ColdFire effect bounds itself by the frame's deadline.** Work at IPL 5, an effect's detours in stock's delay routine, is no render the guard can drop: two Tape Echos took a busy Part to 134 to 140 % with every module render shed, and their entries into the late window (owner's MKII, 22 November 2026). The base raises `ev_frame_deadline` at each frame-interrupt entry with the DTCN3 count by which that work must end for the next entry to land no more than 60 µs late; an effect stores it and holds a block (dry, or its ring held) that would run past it. **A hang is never acceptable:** past about 135 % the frames ran back to back and the unit hung twice with no record (owner's MKII, 22 November 2026), and a single frame interrupt of about 465 µs (128 % of a frame) stopped the DSP's frame exchange for good, at a pattern change or in an overload alike (stalls 49 to 52). So no module render may end a frame past 122 % (443 µs, `FRAME_CEILING`), whatever the guard's credit, a DSP voice's ColdFire side included; in a step's frame (one where any track starts a note) each render is judged there by what it, and the work after it, cost in the last step's frame, which is far more than in the frames between (FM Synth's 90 and 80 µs at a pattern's step 1, where it starts its own notes past the base); a render held there is not probed but timed afresh at STOP or a Part change. When the frame interrupt still falls two frames behind, the brake silences every module machine track until STOP or a Part change, and the log records a `brake` incident (`machine_registry.c`). Stopped, the unit is judged by the larger of the share it last played at and its newest reading. Picks made since count on top until four seconds of playing put them in the readings, a machine swapped out and back counts once, and a module that leaves without a pick (a Part reload, a paste) takes its cost off the kept figure at once. What stock may add later, such as a scene that opens quiet delays, is the reserve's to hold, not the measured figure's. CPU FULL is drawn as DSP FULL is (owner, 22 November 2026): what the pick needs, a DSP row for a module that also runs on the DSP, and a CPU row whose solid part is what the unit takes now and whose shaded part is what the pick would add, 100 % being the line, the figure never past it; a module only on the ColdFire gets CHANGE ONE FIRST, or PART IS BUSY when the Part's own sound is what leaves no room. The reserve, a sample track's share and the line also travel in the set (`stock` in `frame-costs.json`) and take the compiled ones' place, so when a base makes stock cheaper, a new measurement gives modules more room without a new base. Stock's machines and effects and NONE are never refused, so a busy unit can always be made lighter, and installing a module is never refused. The meter's own line (85 %, where the panel lags; [record](verification/2026-11-13-cpu-guard-panel-lag.md)) lies past the frame's: Analog BD's Part, whose longest frame was 108.7 %, read 74 % on the meter.

**A machine can name the CPU meter it adds** (`resources.cpuMeter`, its descriptor's `reserved[1]`). The price is a worst-case share of one frame. A machine's renders are frame interrupt time, so what it adds to the meter is close to what it adds to the frame, and the frame check above charges it for a machine `frame-costs.json` does not list. On the owner's MKII (21 November 2026) Grain's 35-point price, charged on top of a Part that played at 43.7 %, refused it, while Grain at its worst settings added 8.9 points on that Part and 16.55 in the matched 24-bit stereo runs. A base that reads `reserved[1]` charges it in place of the price, and an older base ignores it. Measure it on a unit, stopped between arms: the Part with the track on Flex, then the machine on the same track at the settings that cost it most (every voice, the largest grain or pitch, the widest read, the heaviest sample format you can load), each played for seven seconds with `health` read once a second. The middle five readings of each arm give its figure; the meter cost is the largest machine-minus-Flex difference over the pairs you ran, rounded up, with a margin for formats you could not measure. Record every pair in `evidence/cpu-meter.json` (`module`, `pairs` of `{ track, flex, machine, flexReadings?, machineReadings?, conditions }`); `modules:check` recomputes each figure from its readings and refuses a `cpuMeter` below them, one without readings, one on a module that is not a machine, and a descriptor whose `reserved[1]` differs (0 when it names none). A ported machine cannot carry one yet: `machine_ports.py` writes `reserved[1]` as 0.

**The frame share, not the meter, is where renders drop.** The CPU meter is a mean over seconds; the frame guard judges each frame, and once the frame interrupt passes its share it drops a guarded machine's render. Effect work that runs in the frame (Tape Echo's, in stock's delay routine) is never dropped, so it pushes the guard onto the machine tracks: on an MKII (17 November 2026) a third Tape Echo, picked with the meter at about 76 %, made the guard drop 4,782 Amiga renders, about 70 a second, while the meter showed 72 %. That routine runs from the eDMA interrupt with the mask lowered to IPL 5 (`0x40004b0e`), and the chain's last state unmasks the frame interrupt (`0x40004bc2`), so its time also delays the next frame; stock's free-running DTIM3 count (`0xfc07c00c`, 132 MHz) lets such code see a late call without the base. With modules' hooks in the frame, renders dropped from a mean of 50.7 % on one Part and not at 61.7 % on another: what tells them apart is the longest frame (above).

**Judge the panel by the CPU meter, not by the frame guard's share.** The panel lags when main's idle time runs out, which the meter measures (`npm run device -- stats`, CUE + PROJ); `guard`'s "in the frame interrupt" is the guarded window only and can move without the panel noticing. On an MKII (13 November 2026) an Euclid in use on one track raised the guard's figure by 10 points while the CPU meter rose 2.5 and the UI tick chain took 4 to 10 % longer. Lowering the guard's share does not buy the panel time either when the cost is not in a guarded render: with FM Synth 0.1.2 installed on no track, a share of 50 % skipped over 20,000 renders a second and the load stayed at 77 %.

**A module on no track must cost nothing: count what a stock track's path touches.** On the Octatrack the cost of a hook in the frame interrupt is not its instructions but each separate piece of module code or data that a track's path enters, every track and every frame; the readings fit cache misses, since the renders in between evict those lines (not counted on a unit). Installed on no track beside four FLEX tracks playing (an MKII, 14 November 2026), FM Synth 0.1.2 cost 19.0 points of the frame interrupt, POLY8 0.3.1 12.2 and Repitch 0.2.0 5.3, and a build of each with every frame-interrupt site removed read 0.0. What the bisects showed: a three-instruction test inline at the site cost nothing measurable, the same test in a routine of its own about 3 points, POLY8's render wrapper about 5; reading the Part index from battery RAM (`0x100b14cf`) at every site was only 0.6 of POLY8's 12.2, and working out "is this track mine" once a frame for all eight tracks still cost FM Synth 2.2 to 2.5; a machine that declares `RENDER_FLEX` puts every FLEX track nobody owns through the base's frame guard, 6.5 points on four tracks, about 1.6 a sounding track before the module's own code runs; and stock's increment builder (`0x40004100`) runs on every frame's second render of each track, so an `ev_play_increment` subscriber is entered once a track a frame, not only on retriggers and pitch changes. So: at each site test one bit of one data line inline and return to stock, enter a routine only for a track that is yours, work the answers out once a frame (nothing below the interrupt runs inside it, so what a frame's first use reads holds until its exit), and do not declare `RENDER_FLEX` to see tracks you will mostly hand back. With that, POLY8 0.3.3 read 4.9, FM Synth 0.1.3 3.2 and a Repitch draft 3.7; the rest is each module's remaining per-frame entries, and removing it needs the base to call a module for its own tracks only. Measure with `npm run device:price` ([driving](OCTATRACK_DRIVING.md#send-steps)) on a development base, whole builds against each other with the published one in the same run: code placement alone moves the interrupt's share by up to a point. To find one slow line, sample the interrupted PC from a spare timer above level 5 (PIT2, INTC1 source 45, is free): the slow instruction is the one before the PC that piles up.

**Installed and used nowhere, a module costs at most 0.2 points of the frame interrupt, or it rests** (owner, 20 November 2026). The figure is `device:price`'s at-rest reading (the test procedure's step 9): the frame interrupt's share the module adds while the pattern plays, installed and used nowhere, on a development twin of the base, against the same scene without it. That is the one measure the limit is judged on; the record names its base and scene, and a reading on another scene or base is the same measure but must be taken again for a new release. `module:doctor` fails a release from 20 November 2026 above it unless the module is a machine or an effect, which the base rests by itself (#1849), or answers `ev_in_use`; earlier releases are only reported. "In use" is the module's to define and answer: a track runs its effect, one of its settings is not stock's somewhere in the project (Slow LFO: an LFO MULT of 1/2X to 1/8X), or its page is open. On an MKII the 24 packages of the [0.7.10 dispatch record](verification/2026-11-19-octatrack-idle-dispatch.md) cost 6.1 points together while unused, 5.6 of them in seven modules' frame code (20 November 2026).

**A module that no track uses rests.** One that subscribes `ev_in_use` and answers 0 is left out of the hooks [HOOKS.md](../sdk/machines/octatrack/HOOKS.md) marks `rests` (`ev_play_increment`, `ev_voice_bind`, `ev_voice_bind_run`, `ev_tail_kill`), so the frame interrupt never enters its code there; its keys, pages, tables and project-file hooks stay, so its setup still works. The base asks from the UI tick and puts it back from the next tick on, so a note that starts in that gap plays without it: answer for every Part a pattern change could bring in while playing, and start per-track state afresh when it wakes. A machine needs no answer: the base rests a machine's module while no track of any Part of the project, working or saved, is that machine (two scans of the project in a row, about four seconds), so pattern, Part and bank changes never wake it; a pick wakes it before it commits, and a track that names it otherwise (a paste, a load) renders silence until the next UI tick wakes it. A RENDER_FLEX machine never rests. An effect module needs none either: it rests while no slot of the project names its effect id and no live slot runs it, and a pick wakes it before stock writes it. Any other module that does not subscribe never rests. Resting takes out a module's handlers, not its own stock-site detours: on an MKII (17 November 2026, development twin of base 0.7.8, three loops sounding) a test module whose `ev_play_increment` handler spent 400 loop passes cost 12.5 points of the frame interrupt on no track and 1.0 when it answered `ev_in_use` 0. With its own detours resting as well, Repitch 0.2.1 went from 0.8 points on no track to 0.1, and woke and rested again within a UI tick while a pattern played. Its own detours can rest as well (`"rests"` in runtime.json, [HOOKS.md](../sdk/machines/octatrack/HOOKS.md)): stock runs them unpatched until the next UI tick wakes the module, so a detour that keeps stock away from a value only the module adds (Repitch's TSTR 4 in the voice renderer) must stay patched. A data word the module rewrites (a symbol reference, such as a renderer table entry) rests too when its package row in `src/engine/assets/octatrack-module-packages.json` lists it under `"restingReferences"`: the pinned builder flags detours only, so the host wrapper sets the flag, and the loader restores it as it does a detour. A machine that answers `ev_in_use` itself, for what the base cannot judge (FM Synth: GLIDE on sample tracks, legacy marker samples), gives up the base's pick wake: answer nonzero once its `admit_track` has run, since the base's pick calls it just before it asks whether to wake. Before reading a module's cost at rest, check it acts on no track in the scene: a sample can carry REPITCH as its own TIMESTRETCH, so with TSTR AUTO Repitch works on that track (read its playback increment, `0x80004898 + 40 × track + 36`, with and without the module).

**A stall after a long frame can be the next frame's entry, not the load.** At START and at a program change one frame interrupt ran 475 to 585 µs on every image octabam measured, stock included, so the next one entered late (Sam Banks's MKII, 12 and 13 November 2026, octabam `d16d0520`, `trap-late-frame` in its register). Of 33 logged first STARTs, entries 128 to 149 µs late ran on, entries 155 to 223 µs late made the DSP skip one frame and run on, and the two that entered 149 and 155 µs late stopped the frame exchange for good: the sequencer holds step 1, the panel and USB still answer, and only a power cycle clears it. A USB capture added 25 to 30 µs and put that unit on the boundary (5 of 8 first STARTs stalled with one open, none of 13 without); 60 µs added to every frame moved it past and cured it. So time in the frame interrupt can cause or cure such a stall by a few microseconds, and a stall that comes or goes with a module says nothing about the module until the frames before it show how late the last entries were (`diag.h`'s trace, which the owner's diagnostics pull prints). None of this is measured on a Modwerk base: where its START frame lands is unknown, the DSP's side is inferred upstream, and upstream still has stalls outside the window. Modwerk's stalls at a high interrupt share (24 October 2026, [hardware traps](OCTATRACK_HARDWARE_TRAPS.md#coldfire-and-dsp-load); 10 November 2026, FM Synth beside eight FLEX tracks) looked the same and kept no entry times, so they do not tell the two apart. A guard that holds late entries must count a lateness within 20 µs of a whole frame as on time: the wait window's first version did not and made about 150 on-time entries in one run wait up to 80 µs each, so #1510's plan takes the corrected arithmetic.

**The base waits out a late frame entry.** The frame guard bounds how long the frame interrupt runs, not when the next one enters. An entry about 130 to 165 µs late can stop the frame exchange for good (the paragraph above), so the base keeps each entry's lateness against the DSP's frame grid from DMA timer 3 (`machine_registry.c`, `mw_frame_enter`) and holds an entry more than 80 µs and less than 190 µs late until it is 190 µs late, at most 110 µs (from 110 µs until stall 56: an entry the stall trace put 138 µs late read under 110 by this clock, since the trace is stamped later in the frame; a stall now keeps the last eight entries' lateness by this clock, 'MWLR' at 0x100f9710), before the guard's clock starts; the DSP then skips one frame and runs on. On the owner's MKII (base 0.8 twins, 22 November 2026) a pattern change from an empty pattern to a busy one with modules placed stalled on the first switch with the frame ceiling alone (stall 55), on the ninth with the wait alone, and ran twenty switches with both. A held frame comes up to 553 µs after the last, which the self-test allows (`SELFTEST_FRAME_LIMIT`). An entry 190 µs late or later the wait cannot hold: octabam's two such entries (205 and 209 µs) both stalled, so the base counts them since boot (`mw_late_over`), logs them with the `late` incident and on the log's last page beside the skip count, and a trial fails on one; nothing brakes on it. A development base can switch the wait off for a comparison (`npm run device -- late:off`).

**Bound only the module's own code.** A record prices what the module adds: its own code, stack and memory. The stock routines it calls, stock's stack and the stock interrupts are the instrument's, and no module has bounded them. When a number would need that analysis, write "not measured" with the reason and ask the owner the same day, on the pull request or in Discord's dev-support channel before there is one, instead of writing an audit.

The limits are audit defaults, a judgement and not a repository rule: `--usable`, `--ratio-note`, `--ratio-fail` and `--load-fail` move them, and TESTING.md says why. `scripts/perf-audit.test.mjs` proves the judgement on known-good and known-bad records without firmware, so a surprising verdict is as likely to be the measurement as the module. What it cannot tell is whether the numbers are true: the owner reads the commands and reports behind them, and a number nobody measured is "not tested", never a guess.

**One builder for every machine.** A shared elekloader builder is planned to replace octabam's native build and the in-browser elekloader build. The record names no machine, only the unit, so the same record will be written for every machine once the builder lands; until then the Octatrack commands above are the only ones, and a Digitakt or Digitone module states its measured budgets (shared memory, fast SRAM, time at the render hooks) in TESTING.md. Write against the contract and the manifest, not one builder's internals.
