# Forum, accounts and transactional email

The 3 October 2026 owner decision replaces guest participation with verified email accounts. Reading and configuring remain available without an account. Firmware composition requires a verified member account. Reply notifications and private reports live in Your account; there is no separate activity page. Legacy `#activity` links open the account page. Threads, replies, comments, ratings, likes, public bugs and private module reports require registration. Module releases still require owner-merged GitHub PRs; a community account grants no administrator or publication privileges.

## Local draft

Use Node 24 and install dependencies. The preview seed creates a separate local Worker configuration, a random local auth secret, an isolated D1 database, and fictional accounts/discussions. It has no production database ID or mail credentials.

```sh
node scripts/forum-preview-seed.mjs
npx wrangler dev --config .wrangler/forum-preview/wrangler.local.jsonc --local --ip 127.0.0.1 --port 8897 --persist-to .wrangler/forum-preview
```

In another terminal:

```sh
VITE_COMMUNITY_API_URL=http://127.0.0.1:8897/api npm run dev -- --port 5197 --strictPort
```

Open `http://127.0.0.1:5197/#forum`. Sign in with `demo@example.test` / `Octamod local preview 2026!`. These public demo credentials exist only in the local seed, never in migrations or runtime authentication logic. The seed has a fixed `--local` target and accepts no arguments. Never copy its database or SQL to production. Registration/recovery remain unavailable without mail configuration. Automated account tests intercept mail in memory; they never send messages.

## Organization, Shoutbox 8 and the editor

The forum offers General discussion, Introductions, Showcase, Feature requests, Tutorials & guides, Module help, Shared configurations and Bug reports. Existing category values and foreign keys are retained: migration 0027 adds a nullable `section` for the four additional topics. Public responses and account exports expose the effective category. The Topic and Machine dropdowns combine with search; module filters in links remain supported.

Module bugs must use “Report an issue” on the affected module’s page. The forum keeps Bug reports as an archive, but its new-thread API rejects the `issues` category and structured issue payloads. Old bug-composer links open a module picker leading to the dedicated report form. Before a member publishes a module discussion or reply, a modal offers reporting, confirmed discussion posting, or continued editing. Choosing reporting copies the written title and body into the issue form for review; the original draft remains available in the tab until the report succeeds. Configuration details and device/log requirements still apply.

Latest activity and New threads show member-created discussions, ordered by recent activity and creation respectively, with pinned threads first in both. Automatic module home threads live in Module discussions (`#forum?view=modules`, or `view=modules` on the thread-list API). They do not consume member-feed pages or appear in its search results, topic/machine counts or recent replies. Following and Bookmarks are private member views and retain module homes the member has chosen to follow or save. The view tabs and the search, topic and machine filters share one toolbar row. The topic directory shows visible member thread/reply counts, optionally scoped to one machine. Recent replies also excludes opening posts and hidden content. Activity links, including bell notifications, activity email and device push, carry the post and its actual reply page. A link that names the thread's opening post leaves the page at the top; any other post is scrolled to the top of the screen. Posts read as one list with an avatar column on wide screens and full-width text on phones, where the editor toolbar is a single scrolling row. Switching feed views keeps the same header without an All discussions back link; threads, profiles and the composer keep their back navigation.

The forum front page opens with a **Showcase** strip, “Fresh from the community”: cards for the 12 newest visible posts that carry images or sound clips (`GET /api/forum/showcase`, optionally `?machine=`), newest first, each linking to its post on the right reply page. An image fills the card; a sound clip without an image shows a decorative waveform (drawn from the file ID, not from the audio) and plays inline, one clip at a time. A machine's forum page shows the same strip for that machine, and the Showcase topic page opens with the same cards as a wrapping gallery (`?category=` on the API accepts any topic except bug reports). Thread rows mark discussions that carry images or sound clips. Unlike the member feed, it includes module home threads, because a sound demo in a module's thread is exactly what the strip is for; bug reports, hidden posts and threads, and removed files are left out. The strip ends with an invitation to post in Showcase (or to sign up) and is hidden when the deployment has no `MEDIA` bucket.

**Shoutbox 8** is expanded by default as a floating chat panel at the bottom right of forum screens. Minimizing it leaves a small button for reopening the chat. Its panel overlays the page without changing the forum layout, can be minimized or closed with Escape, and stays open while navigating between discussions. Anyone can read; verified, unsuspended members can send plain text up to 600 characters, edit/delete their own messages, and report messages privately. Its latest eight messages refresh every 30 seconds while expanded and the tab is visible; the archive has pages of 30. The service allows six sends per minute and 30 per hour per member, with additional member/IP limits. Chat does not generate notification emails.

The administrator's forum report queue includes chat reports. Hiding/restoring messages and reviewing reports require administrator access and a recorded reason; hidden messages are visible only to administrators. Account exports include only the owner's messages/reports, and account deletion removes their chat messages and report records.

Thread creation, replies and post editing use a visual editor with bold, italic, strikethrough, headings, lists, quotes, inline/fenced code, links and undo/redo. A Markdown toggle permits source editing. Posts still store bounded Markdown text; a React renderer escapes raw HTML, accepts only explicit HTTP(S) links without credentials, and never embeds remote images. Attachments keep using the existing controlled upload path. The editor loads only when a composer is opened.


## Mail and launch setup

Keep domain registration/DNS at Hetzner. A domain-only registration does not include mailboxes. A mailbox subscription is unnecessary for sending account messages. [Resend](https://resend.com/pricing) currently offers a free sending tier of 3,000 emails/month and 100/day; confirm current limits before launch. A receiving support inbox, if wanted, is a separate service. The domain for the Modwerk launch is modwerk.app; its records, order of work and checks are in [DOMAIN_AND_MAIL.md](DOMAIN_AND_MAIL.md), which supersedes the octamod.app specifics below.

1. Verify `modwerk.app` in Resend (the owner selected the root domain in the Ireland region). Copy the exact [SPF/DKIM DNS records](https://resend.com/docs/dashboard/domains/introduction) from that domain's dashboard into the authoritative DNS zone at Hetzner. The selected setup uses a DKIM TXT record at `resend._domainkey` and CNAME records at `rsend` and `send`. Do not replace existing website, inbound MX or root SPF records, and do not invent DNS values. The initial `_dmarc` TXT value is `v=DMARC1; p=none;`; it requests no rejection or quarantine. Review legitimate senders and delivery evidence before strengthening that policy.
2. Create a sending-only API key restricted to `modwerk.app`. Store `RESEND_API_KEY`, `AUTH_SECRET` and `EMAIL_FROM` as Worker secrets with Wrangler's interactive secret input. No credentials belong in the frontend, GitHub Pages variables, commits, screenshots or PR descriptions. Set `EMAIL_FROM` to `Modwerk <accounts@modwerk.app>` once the domain is verified. Disable open/click tracking for verification and recovery emails so action links are not rewritten or tracked. The owner approved enforced TLS on 3 October 2026: delivery must fail if the recipient's mail server cannot accept an encrypted connection.
3. Follow [COMMUNITY_OPERATIONS.md](COMMUNITY_OPERATIONS.md) to verify an encrypted backup/isolated restore and record a D1 recovery bookmark. Apply account migrations 0011–0028 after the main issue-report migration 0010 to the chosen deployment only when deployment is authorized. Existing guest content remains intact. Deploy the API before the account frontend, keeping `REGISTRATION_OPEN=false` until public launch is approved. Login/recovery remain available to existing accounts while new signups are closed. Keep `APP_URL` equal to the frontend origin and `SESSION_TRANSPORT=bearer` for separate Pages/Worker origins. Both Wrangler configurations require `nodejs_compat`.
4. Check real inbox delivery, spam placement, DKIM/SPF/DMARC, duplicate registration, resend, expiry/replay and recovery revocation in a controlled deployment. The local draft does not prove delivery or production capacity. Test password-hashing CPU/memory against the actual Worker plan; the free CPU allowance may be insufficient for scrypt. Do not weaken password hashing to fit a hosting quota.
5. Review the public privacy copy, private account-removal request queue, operator removal/retention procedure, receiving support contact, D1 access/backups, provider logs, incident handling and dependency updates before inviting public registrations. Self-service account deletion requires the current password or a recent social sign-in; shared discussions retain anonymous attribution. Email changes, MFA and a spam challenge remain future work. See [FORUM_LAUNCH.md](FORUM_LAUNCH.md) for evidence and remaining gates.

Transactional mail covers verification and password recovery; activity digests are described under [Notifications and activity email](#notifications-and-activity-email). Optional Modwerk news consent is unchecked at signup and can be withdrawn in account settings; it never changes account access. Further news emails use that opt-in. Every new member receives a separate one-time welcome after verification and social onboarding are complete; it does not change news consent. Verification, recovery and welcomes share the account-mail budget, which leaves plan headroom with 80 sends per UTC bucket and 2,400 per 30-day bucket. These are protective application limits, not an exact mirror of provider billing periods. Provider quotas are authoritative. Failed attempts consume quota to contain retries. Generic registration/resend/recovery acceptance also covers delivery failure/limits to avoid exposing membership; it is not a delivery receipt. The private administrator Accounts tab shows daily accepted, failed and limited counts without addresses, passwords, request bodies, provider payloads or action links. Provider acceptance does not prove inbox delivery.

Before launch approval, credentials can be staged without changing production traffic with `wrangler versions secret put <NAME> --config wrangler.worker.jsonc`. Such a version retains the existing Worker code; it is not the forum release. After deployment is authorized, upload the reviewed forum Worker with `wrangler versions upload --config wrangler.worker.jsonc`, which preserves existing secrets, and inspect the uploaded version with `wrangler versions view <VERSION_ID> --config wrangler.worker.jsonc`. Confirm all three account secrets and the existing admin secret are present, and complete the database/launch checks above before directing traffic to that version.

## Module threads

Every catalog module has one forum thread in Module help, with the fixed ID `module-<community module ID>`. The Worker creates missing threads the first time a forum route is used after a deployment and again in the hourly job, so a newly merged module gets its thread without a manual step. Migration 0023 adds the author row `modwerk`, shown as “Modwerk”: it has no username, sign-in, session or profile and cannot be suspended. The opening post repeats the module's catalog summary and is not editable. Claimed, GitHub-verified maintainers follow the thread when it is created or when they claim the module, and replies appear in their developer workspace. Administrators lock, pin or hide these threads like any other; a hidden module thread is not recreated. Module pages embed that same thread, using the forum post renderer, composer, attachments, reactions, following, bookmarks, pagination and moderation. A reply or edit made in either view appears in the other. The home thread appears in Module discussions and stays directly accessible from the module page. Filtering the main feed by a module lists member-created threads about it. Migration 0028 transfers historical comments into these threads while preserving their authors and dates, then points existing notifications at the posts. The comments table is retained as a read-only archive; legacy comment endpoints read and write the shared forum posts. Published community modules also use a fixed home thread. Module sets do not have separate discussions: use the included module’s thread. Migration 0033 hides and locks previously created automatic set threads while retaining their history. Viewing a set or calling its legacy community API cannot create a thread.

## Profile pictures

Members can set a picture under **Your account → Profile** (migration 0037 adds `users.avatar_id` and `avatar_mime`). The browser crops it to the centre square, shrinks it to at most 512 px and encodes WebP (JPEG where WebP is unavailable), which drops photo metadata; `POST /api/forum/avatar` accepts the raw PNG, JPEG or WebP bytes up to 1 MB, ten times a day, and stores the file in the `MEDIA` bucket under `avatars/<id>`. The ID is random and changes with every new picture, so public URLs (`GET /api/forum/avatars/<id>`, cached for a day) never name the account and old copies stop resolving. The picture is served only while the member is not suspended, so suspension hides it. `DELETE /api/forum/avatar` removes it, and account deletion removes the file with the account. The account export lists the current picture's ID and type. Every place that names an author (thread rows, posts, the Showcase, Recent replies, the Shoutbox, profiles and the composer) shows the picture, or the member's initials when there is none. Without a `MEDIA` binding the picker is hidden.

## Images and sound clips

Threads and replies can carry up to four images or sound clips (decision of 5 October 2026 in [DECISIONS.md](DECISIONS.md)). Members pick files in the composer; the browser compresses them first (images to WebP or JPEG, at most 2048 px, which drops photo metadata; sound to Opus in Ogg at 96 kbit/s, at most five minutes) and uploads each one at once to `POST /api/forum/media` as a raw body. The Worker detects the type from the bytes, accepts PNG, JPEG, WebP, WAV, MP3 and Ogg only (WAV and MP3 arrive only from browsers without an Opus encoder), and allows 5 MB per image, 10 MB per sound clip, and 20 uploads and 100 MB per member per day. The thread or reply then names the upload IDs with optional descriptions; an upload can be attached once, by its uploader.

Files live in the `MEDIA` R2 bucket (`modwerk-forum-media`) and table `forum_media` (migration 0026). `GET /api/forum/media/<id>` serves a file only while its post and thread are visible (administrators also see hidden ones), with the detected type, `nosniff`, `Content-Security-Policy: default-src 'none'; sandbox` and single byte ranges. Hiding a post hides its files; authors can remove their own files from the edit view; administrators can delete a file permanently from the post's moderation menu (recorded in moderation history; it cannot be restored). Account deletion removes the member's files and keeps the post text. The hourly job deletes removed files and uploads not attached within a day from the bucket and the table. The account export lists the member's files (type, size, description, post); the files themselves remain downloadable from their links until removed. Without a `MEDIA` binding the session reports `forumMedia: false` and the composer hides the picker.

Create the bucket once before deploying a configuration that binds it: `npx wrangler r2 bucket create modwerk-forum-media`.

## Notifications and activity email

The owner decided on 5 October 2026 that activity email is on by default with one-click unsubscribe, sent as batched digests, for every activity type below.

One private `notifications` store (migration 0024, which replaces `forum_notifications` and keeps existing rows) feeds the toolbar bell, **Your account → Notifications** and the developer workspace. Entries are created in the same transaction as the activity:

- replies in threads a member follows (authors follow their own threads), and `@username` mentions in new threads and replies (at most 10 names per post; a mentioned follower gets the mention only);
- likes on a member's posts;
- comments, ratings and likes on a catalog module, for its current claimed maintainers, and new bug reports and their replies (unchanged delivery rules);
- status changes on a member's own report, whether changed by an authorized maintainer/administrator in Modwerk or by the signed GitHub webhook;
- new published versions of a module the member follows.

Module pages offer **Get update notifications** and **Following updates · Unfollow**. This follows releases independently of discussion replies. The report form offers a checked release-follow option; declining it leaves an existing follow alone. Migration 0034 follows modules reported by existing verified members, starting at the first observed live version without replaying historical releases. Account export includes these follows; account deletion removes them.

Vite publishes `module-releases.json` with available Octatrack, Digitakt and Digitone module IDs, versions, names and page links. The hourly Worker reads this inventory from `APP_URL`, so a merged PR or failed deployment cannot announce an unavailable release. Semantic version increases trigger one bell event per follower and version; equal versions and rollbacks stay quiet. The first poll establishes a baseline for historical reports. Fanout is bounded and retry-safe, and paused Octatrack modules are omitted. A new release says that an update is available; it does not imply that a particular bug is fixed. Status notifications are inserted atomically with local status changes; repeats and GitHub echoes of a local change stay quiet.

The operator can also announce something to every member. An announcement is a separate record rather than an activity entry: it appears in the bell of every verified member who joined before it was sent, is never mailed, and each member's read state is private. It is sent from the Admin workspace (see [Announcements to every member](COMMUNITY_OPERATIONS.md#announcements-to-every-member)).

Likes and ratings notify once per person and target. Unliking withdraws a notification nobody has read or been emailed about yet. Deleting a module comment deletes its notifications. Entries whose post, thread or comment was hidden or removed, or whose actor is suspended, are not shown or mailed. Nobody is notified about their own activity.

Maintainer events are addressed to the GitHub developer identity, which has no email address. A member account receives them in the bell and by email when it has a GitHub social sign-in for the same GitHub account; both sides are proven through GitHub OAuth, never a typed handle. Without that link they stay in the developer workspace.

The hourly job sends digests. A member gets at most one per 6 hours (default) or 24 hours (their choice), covering entries at least 10 minutes old that they have not read in the bell. Read entries, turned-off topics and entries older than a week are never mailed. Settings in **Your account → Activity email** turn email off or choose topics (replies and mentions, likes on posts, maintainer activity, bug reports/status changes, followed module releases) and frequency; the bell always shows everything. Every digest carries a signed unsubscribe link (`#account/unsubscribe/<token>`, confirmed with a button) and RFC 8058 `List-Unsubscribe`/`List-Unsubscribe-Post` headers pointing at `POST /api/notifications/unsubscribe`, which mail clients call without an Origin or session. The token is an HMAC of the account ID under `AUTH_SECRET`; it can only turn activity email off, and rotating the secret invalidates old links. User content in emails is escaped; links point only to Modwerk.

Activity digests have their own daily cap, `ACTIVITY_MAIL_DAILY_LIMIT` (default 15, monthly cap 30 times that), beside the 80/day kept for account mail, so both fit Resend's free 100/day tier. Raise it after upgrading the Resend plan; account mail keeps its own limits either way. Reaching the cap stops that run and is counted as limited in the Accounts tab; failed deliveries are retried on the next run. Disable open and click tracking for the sending domain in Resend: the privacy notice promises activity email has none. Notifications are kept until account deletion, which removes them and the preferences; account export includes both.

## Security boundaries

All source is assumed public. Security depends on server-side checks, private deployment secrets and maintained authentication code, not hidden frontend controls.

- Better Auth is pinned in the lockfile. It owns salted scrypt password hashing, signed sessions and password recovery. Only the explicitly listed facade routes are exposed: no generic auth handler, social linking or unreviewed plugin endpoint. Passwords are 15–128 characters; no passwords or session tokens appear in API JSON responses or URLs.
- Verification lasts 24 hours, requires the registration password and consumes a server-side hashed token once. Requiring the password prevents a victim from verifying an account pre-created by someone else with a password the victim does not know. Recovery lasts 30 minutes, uses a hashed token identifier, consumes it, verifies inbox ownership and revokes existing sessions and outstanding action links. Requesting links does not sign anyone in.
- Email links use the URL fragment, which is not sent with HTTP requests. The user explicitly submits the form; merely opening a message or link does not verify/reset an account. Action tokens remain sensitive, including in browser history and screenshots until completed.
- Verified, unsuspended membership is checked on the server for every participation write. Author ownership gates edits. Administrator authorization is independent and required for every moderation route; hiding, locking, pinning and suspending are recorded in private history. Suspension revokes active account and legacy sessions.
- Seven-day sessions can be ended individually by signing out, or other devices can be revoked from the account page. Password recovery revokes all sessions. Separate-origin deployments use a signed bearer in localStorage because third-party cookies are unreliable. This exposes it to same-origin JavaScript: XSS and a compromised frontend dependency are session-theft risks. Same-origin fallback uses HttpOnly, SameSite cookies, Secure on HTTPS. Production builds include a CSP meta tag for GitHub Pages, restricting scripts and connections to the app and configured API; Cloudflare also applies its response headers. Inline styles remain allowed for existing layout controls. GitHub Pages cannot enforce frame-ancestors through a meta tag. Do not add third-party scripts or unsafe HTML rendering. Rotating `AUTH_SECRET` invalidates signed credentials/verification links; also revoke stored sessions and action tokens when responding to an incident.
- CORS permits the configured app origin only; mutation requests require that Origin. JSON is limited to 32 KiB (structured device-log reports allow an additional 64 KiB), posts to 12,000 characters and results are paginated. SQL values are bound. Dynamic moderation columns/tables come only from fixed allowlists. Posts render as Markdown with escaped HTML, lists, quotes, code and explicit HTTP(S) links. Executable URLs and embedded remote images are rejected; code remains text and is never executed. Forum attachments are separate from the text and limited to detected image and audio types served from the API origin with a sandbox CSP; SVG, archives, firmware and other files are rejected.
- Persistent D1 limits cover IPs (the trusted Cloudflare connecting-IP header), email addresses and member actions. Keys are time-bucketed hashes. They are pseudonymous abuse controls, not a claim of strong anonymization. Reverse proxies on future self-hosting must strip spoofed forwarding headers. A distributed attacker or a compromised inbox remains a risk; add edge abuse controls if actual traffic requires them.
- Shared configurations accept only name, machine, native module IDs, exact version strings and the stock-FX2 choice (used only on Octatrack). Legacy snapshots without a machine remain Octatrack. They are immutable post snapshots, with explicit local copy/import. Import selects the current approved catalog versions and reruns normal compatibility checks. It never executes a post or downloads firmware. Arbitrary JSON fields, uploads and firmware attachments are rejected; forum images and sound clips are attached to posts, never to configurations. Public prose cannot automatically prove copyright compliance; moderation and contributor responsibility still apply.

## Stored information and operations

`auth_users` holds private email, username and verification state. `auth_accounts` holds credential hashes; `auth_sessions` holds library session records without IP/user-agent values. Public community queries use a separate `users` projection and never return email/password/token columns. Signed bearer verification means the raw database session token alone is insufficient to authenticate.

Posts/usernames/config snapshots and attached images and sound clips are public. Private reports, bookmarks, follows, notifications and moderation history are permission-scoped. New module issue forms publish reproduction details as a GitHub issue that mentions the module’s developers, and the reporter gets GitHub replies and status changes as notifications; without `GITHUB_TOKEN` they post in Bug Reports and notify the current verified, claimed developers in the app instead. Full configuration, build fingerprints and validated logs remain in the authorized private report. Older reports and clients without explicit forum visibility stay private. Public replies notify followed developers through their workspace; resolution/reopening stays synchronized with the report. New account reports include structured machine-specific configuration; Octatrack requires a validated device log or an explicit missing-log reason. Digitakt/Digitone reject log/file uploads. Reporters can explicitly share private reports with GitHub-verified, claimed maintainers and withdraw access. Historical reports stay unshared. See [DEVELOPER_WORKSPACE.md](DEVELOPER_WORKSPACE.md) for login, claims and backend setup. Private reports never open GitHub issues; retries reject them. Migration 0020 records the explicitly requested public forum link without publishing historical reports. Historical guest names are unverified and cannot reserve or claim accounts. Signing in replaces that browser's guest session; there is no automatic migration of private reports by name or email.

Hourly cleanup removes expired action tokens, sessions and throttle rows. Forum content, pending registrations, reports, aggregate mail counters and moderation history persist until operator removal; notifications are limited in the response but are not purged on a retention schedule. Your account accepts private removal requests with the current password and an explicit confirmation; requests remain reversible while pending. Separate administrator review is private and cannot claim completion while credentials/private data remain. Actual removal needs an authorized operator procedure and an agreed public-content handling decision, as documented in [COMMUNITY_OPERATIONS.md](COMMUNITY_OPERATIONS.md); submitting a request never immediately erases data.

Run `npm run check` for ordinary app checks, including authentication/authorization regression tests and a production frontend build. Tests cover verification/recovery, replay/expiry, forged sessions, origin checks, legacy ownership, immutable config validation and moderation. They use synthetic data only. No firmware, emulator, hardware or DSP qualification tests are needed for forum work. Keep the authentication dependency patched and review security advisories; passing these tests is not an independent security audit.

## New-member welcome email

Migration 0029 marks existing completed members as excluded from automatic welcomes and leaves unfinished signups eligible when they complete. The `*/5 * * * *` Worker trigger runs `sendMemberWelcomes`; the hourly cleanup/activity trigger stays unchanged. `WELCOME_MAIL_ENABLED=true` enables the welcome. It uses the approved HTML and text in `docs/news/001-member-welcome.*`, with a welcome footer instead of a news-consent claim. Every verified, active, fully onboarded new member is eligible, regardless of optional news or activity preferences.

A private per-account delivery row and Resend idempotency key prevent repeat sends across logins and overlapping jobs. Failed sends retry every five minutes within the account-mail quota. Uncertain results older than 20 hours move to `review` before the provider’s 24-hour idempotency window ends; verify delivery in Resend before operator intervention. Account export includes the delivery state/timestamps, and account deletion removes the row. Aggregate accepted/failed/limited counts appear under `welcome` in the existing administrator mail API. No addresses, content or provider bodies are logged.
