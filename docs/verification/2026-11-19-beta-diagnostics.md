What the shared diagnostics showed in the 19 November pull (08:03 UTC; 20,504 records from 168 members over 30 days),
read from the 18 November pull (11:34 UTC) on. Base 0.7.9 (`dfa43813`; `c889442d` off, `75fda573` tracks-post) has

Since the 18 November pull: one sync failure (a module-memory refusal, below), two link failures (Windows, idle:

## SC Ringmod refused as "module memory" is a claim meeting a delay buffer

On 0.7.8 (`f04f5e5c`), one unit restored a saved set of 11 modules with SC Ringmod at two starts and refused SC
Ringmod for module memory (loader refusal 2) at the next two; a one-package sync adding it back was refused the same
way. The 16 November record has a second unit with the same shape.

The module pool is not the cause. In the emulator the same set without SC Ringmod (156,364 bytes of packages) used
161,344 of the pool's 786,432 bytes, with 625,088 free in one run; SC Ringmod's package is 2,416 bytes.

SC Ringmod 0.2.1 declares read claims on the base's key bus: Y $7E00-$7FFF on both cores and Y $33DFE-$33FFF in the
shared window. `modwerk_machine_dsp_claims_admit` (`resident_base.patch`) checks a package's claims against the live
and planned delay buffers (`dl_hook_claims_idle`, generated by `resident_placement.py`) and answered a meeting with
`RUNTIME_MEMORY`. A module effect counts its whole 16,384-word FX2 block, because no module had a reviewed buffer
extent (`controller_policy.c`), so a module effect on FX2 of T1 or T5 (block at Y $4000) or T7 (the shared window)
meets those claims. In the unit's log, every start whose FX2 slots all ran stock effects admitted SC Ringmod, and the
refusals began at the start where Air Chorus sat on T5 FX2. Air Chorus's buffer really reaches Y $7FFF, so that
refusal protects the key bus; the name and the advice ("remove a module") were wrong. The second unit's records
were taken minutes after each restore and do not line up, so it stays unconfirmed.

Changes for base 0.7.10: a refused restore records which admission check refused it and the module pool at that
moment (#1772), and a claim meeting a buffer has its own refusal, code 12 "meets a buffer", with E-Verb, Mini Verb,
BBD Delay and Vibrato counting their reviewed buffer extents instead of the whole block (#1776).

## The emulator refuses every package with DSP claims as busy

`ot_emu` (14 October build) never finishes placing DSP code on the 0.7.8 development twin: every boot logs a stall
with the manager in phase 2 (writing). The buffer plan stays open, `hook_buffer_spans` fails, and
`dl_hook_claims_idle` returns -1, which the claims check answers with `RUNTIME_BUSY`. Only packages with claims reach
that check, so an 11-module set with SC Ringmod was refused four times in a row while the same set without it was
kept and restored at three starts. On the unit the same 11 modules were kept on 18 November. Read a busy refusal of a
package with claims in the emulator as the emulator's, not the base's.

## A freeze until a restart while playing on 0.7.9

One unit on `c889442d`, playing, CPU 58 %, eight modules (E-Verb, BBD Delay, LOFI2, Recorder Loop, DirectJmp Kyoti,
Deja Vu, Temp Save, Repitch). Its last keys were PROJ, DOWN, YES, YES four times, the last one followed by PLAY. The
set was restored 8 of 8 at the next start. The same unit froze stopped earlier that night after the same walk. It is
the walk of the stopped freezes the 16 November record reads as likely OS upgrades or USB DISK MODE, but this one was
playing and kept its base.

To confirm: on a unit with base 0.7.9 and that set, play and repeat PROJ, DOWN, YES, YES, and read the log.

## Stalls while a module is bound

Four units in the 30 days pulled, all on bases before 0.7.9, stalled with the manager in phase 3 (binding); two of
them at 95-96 % CPU, one with 16 modules installed, where core 0's last packet was a BIND. Every frame before the
stops was on time, so it is not the late frame entry. None on 0.7.9 yet.

To confirm: bind a module at about 95 % CPU on a unit and read the stall record. The emulator cannot place DSP code
(above), so it cannot show this.

## One stall after a long frame interrupt at low CPU

575 µs, past the 515 µs at which the DSPs starve. It came right after FM Synth was added. A single record; watched
for repeats.
