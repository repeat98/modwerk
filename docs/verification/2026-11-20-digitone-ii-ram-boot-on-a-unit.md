# Digitone II: an image booted from RAM over the development link, 20 November 2026

The Digitone II link's RAM boot (#1821, `sdk/machines/digitone-ii/LINK.md#ram-boot`) on the contributor's Digitone II (@prodbysmolec), OS 1.12, with a MIDI DIN recovery path ready (an MPK49's MIDI OUT to the unit's MIDI IN; notes arrived over it on 20 November).

- **Build:** `npm run machine:base -- digitone-ii --dev`, development package `6f72efd1402dffd76bd0520e26dacfdca96edf1c1fad8ef1fcea84629ba77ba4` (.run 10,389, .bss 10,592 bytes; 18 sites; no jump to an odd address). The pull request's code, with the addresses moved into the recipe, builds `d34296c8…` with the same sections, symbols and relocations (only the build record's source hashes differ). Linked by Elekloader 0.11.0's patcher: with `hello-marker-dn2` 1.0, `.syx` `706347202a44c577ded210d94112efe5da5b94c251986b596b6e60ecc0ec1aba` (flashed); without it, `.syx` `59800fb730582ea3ed881a89eb1b0977be88dd78a19ec11743065030b50f7b50` (booted from RAM).
- **Before the unit:** the gate's CRC, container parse and depacker, compiled for a computer from `link.c`, unpacked the first image's container to the linker's main OS byte for byte.
- **1, flashed:** the marker image over USB (the developer pressed YES): it booted with the marker; `ident` read boot 0. `bootdiag` showed stock's upload buffer as the code expects it after a flash: the struct's length 0x1d57f0 (the container just flashed), "ELE3" at +8, RSR 0x20.
- **2, RAM boot:** `dn2_link.py ramboot` of the image without the marker, no hand on the unit: the upload, then `ramboot`; the unit saved and restarted, and `ident` read **boot 1, booted from RAM, image CRC 6a84376e**, the image's own. `bootdiag`: the mailbox MWBT with its check word, the marks 0x4d57001d (armed, stock's struct at the staged address, its length the host's) and stage 6 (the container copied), RSR 0x20. The screen showed the SYN page without the marker; the developer confirmed it and that the unit played normally.
- **3, power cycle:** the flashed image came back with the marker (`ident` boot 0, the upload buffer empty). Nothing was written to the flash.
- **4, a flash from this base:** stock 1.12 over USB, YES by the developer: it erased, wrote and booted stock normally (the link no longer answered; the developer: "alles gut"). The new site in the upgrade job's path passes a normal flash through.
- **Seen:** RSR read 0x20 after the power cycle too, so on this unit the gate's software-reset check does not tell a power cycle from a reset; the mailbox, gone with the DDR's contents at power-off, is what keeps a power cycle from booting from RAM.
- **Not tested:** cancelling a request by a press or `disarm`, an image that fails a check (the gate then boots the flashed OS), repeated RAM boots, long sessions on an image booted from RAM.
