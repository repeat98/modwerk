# Daily maintenance

When the owner says **maintain**, run this pass. It covers the work that comes back every day: pull requests, GitHub issues, the beta and its diagnostics, upstream projects, and the health of `main` and the owner's computer. **maintain prs** (or issues, beta, upstream) runs one worker only. It is owner work, like [OWNER_OPERATIONS.md](OWNER_OPERATIONS.md); a contributor's session never runs it.

## How a pass runs

1. **Start from the last briefing.** Read the newest `~/.cache/modwerk-local/maintain/<YYYY-MM-DD>.md`: what was waiting on whom, and what the owner decided. Read the repository at `origin/main` or in a fresh worktree; the primary checkout often sits on a stale local `main`.
2. **Start the workers in parallel**, one subagent each where the agent supports it, otherwise one after another: the [pull request worker](#pull-request-worker), the [issue worker](#issue-worker), the [beta worker](#beta-worker) and the [upstream worker](#upstream-worker). Give each its section, the last briefing and anything the owner pasted; Discord messages go to the beta worker. Each returns one line per item: what it is, what it found, what it recommends.
3. **Check `main` and the computer yourself** while they run ([below](#main-and-the-computer)).
4. **Check the workers against each other**, then write one briefing, in chat and to `~/.cache/modwerk-local/maintain/<today>.md`. A claim one worker makes can undo another's draft (one warned of a patch overlap that another's reply walked into; the module's build file settled it), so verify a contradiction before it reaches the owner. Put first anything that can't wait (a bot run or a deadline within the hour), then the real calls, each with a recommendation the owner can answer in a word ("merge #N?", "decline #N?"), then one routine batch the owner approves whole or strikes items from: standard closures with their reasons, and drafts to post. Then what was done and what waits on whom. Tester names and diagnostics stay in that file and the chat, never on GitHub.
5. **Carry out what the owner approves**, in the same session. An approval covers only what it names. First compare each target's last update with the briefing time and read again what moved: authors close, push and open pull requests meanwhile.

A worker may, without asking: read anything, run `diagnostics:pull`, build and test in its own worktree behind the check lock, refresh and fix the branch of a pull request the owner opened (unless another session is working on it), and ask a reporter for missing details. Everything else is a decision in the briefing: merging, closing, review comments and follow-ups to contributors, pushing to a contributor's branch, anything on the unit, production writes, secrets and mail. Drafts for contributors and testers are plain and friendly, in the owner's voice; post each from a file (`--body-file`) in bash, since zsh does not split `set -- $spec` in a loop. Every session on this computer shares one connected Octatrack and one emulator: a worker starts neither `ot_emu` (or digiemu, rytm-emu) nor anything on the unit unless the owner says it is free, and then only one worker at a time.

## Pull request worker

List them with `gh pr list --state open --json number,title,author,isDraft,labels,mergeStateStatus,updatedAt`. The owner's review list is `is:pr is:open draft:false -label:needs-work -label:one-at-a-time`; `pr-triage.yml` labels the rest ([review queue](COMMUNITY_OPERATIONS.md#review-queue-and-saved-replies)). Give every pull request one verdict: ready to merge, needs a refresh, red, waiting on its author, or needs the owner's call, and why.

- **Review** new and changed pull requests. Read the code they touch, not only the diff. Check the rules a contribution most often breaks: a dependency on another module or a pull request stacked on one, an update to someone else's module without its author's yes ([Ask the author first](DEVELOPER_WORKFLOW.md#ask-the-author-first)), someone else's protected work, a fix without its changelog entry, a new Octatrack module without the USB lifecycle, unrelated changes in a module release, hand-edited generated files. Draft the review as comments for the briefing.
- **Refresh** a pull request that is behind or conflicting in its own worktree: merge `origin/main` into it, never rebase (catalogue rows pin the pull request's own commit). Regenerate generated files instead of resolving them by hand: `modules:generate`, `modules:pairs -- --write`, `licenses:generate`, `machines:generate`, and an Elekloader row with `elekloader:update -- --overlay <record>`, never `--library`. Run `npm run pr:ready` until it says Ready. Push it only to the owner's own branch; offer a contributor's refresh in the briefing.
- **Across pull requests:** base event and table indices (the loader refuses a gap, so whichever merges later renumbers and rebuilds), one module version claimed by two pull requests, and additions to a document over its [size limit](README.md).
- **The triage bot** runs at minute 41 of every hour. Preview it with `PR_TRIAGE_DRY_RUN=1 GITHUB_REPOSITORY=repeat98/modwerk GITHUB_TOKEN=$(gh auth token) node scripts/pr-triage.mjs` and say what it would label, comment or close, above all on a pull request whose author the owner asked to wait.
- **Red checks:** read the failing job (`gh run view <id> --log-failed`) and say whether the pull request, `main` or a flaky test is at fault.
- **Follow up** on a pull request quiet since its last request with one short draft; `pr-triage.yml` closes `needs-work` after 14 days.
- **Merge**, once the owner says so: `gh pr merge <n> --squash`, or `--merge` when the pull request's catalogue rows pin one of its own commits. Before a module update merges, tell the owner that publishing notifies its followers. An owner-approved update needs `sdk/<id>-build-approval.json`, which only the owner writes: hand them the record with `sourceSha256` from `moduleNativeSourceSha256` in `scripts/module-qualification.mjs`. Then follow the merge commit's runs (`gh run list --commit <sha>`) to green and, for a module release, check that the live site lists the new version.

## Issue worker

List what is new or changed since the last briefing: `gh issue list --state open --limit 200 --search "updated:>=<date>" --json number,title,labels,author,updatedAt`. Read each one in full with `gh issue view <n> --json body,comments` (`--comments` alone leaves out the body).

- **Sort** each: fixed or answered, duplicate, needs details, confirmed, question or feature, stale. Look for a fix in open pull requests and recent releases, and for a known cause in the [beta findings](OCTATRACK_BETA_TEST_PLAN.md).
- A USB beta report has no device log: look its reporter up in the beta worker's diagnostics pull, and quote nothing from it on GitHub ([reports](DEVELOPER_WORKFLOW.md#manage-reports-on-github)).
- **Ask** for missing details yourself, with `/modwerk needs-info …` or a plain reply. `/modwerk` commands from `repeat98` work only on modules that list repeat98 as a maintainer, and HTTP 200 with `command: denied` means nothing happened. Elsewhere reply plainly and close with `gh issue close <n> --reason completed|"not planned" --comment …`; the signed webhook updates the Modwerk report.
- **Propose closures** as one list, a reason for each. A code fix follows [the issue-fix flow](OWNER_OPERATIONS.md#finish-the-issue-fix-flow) once the owner asks for it.

## Beta worker

- **Pull** with `npm run diagnostics:pull` on Node 24, from a worktree on current `main`: it compares each unit's base with that checkout's `base-binding.json`. It writes every record to `~/.cache/modwerk-local/diagnostics/latest.json` (UTC) and prints a summary (this computer's time). The summary already decodes restore results and leaves out card-build selection checks; it counts restarts per log (a base update can restart the unit's log at start 1, and the earlier log's lines name their base), so trust each count as a floor, not a total. A stall after a session that ended stopped at 95 %+ CPU after PROJ … RIGHT YES with nothing installed is marked likely an OS upgrade or USB disk mode: a hint, not a cause.
- **HTTP 403** means the Worker's `DIAGNOSTICS_READ_KEY_SHA256` no longer matches this computer's Keychain key. The Worker accepts one hash, so `--init` on another computer replaces it; resetting the secret is the owner's call. Auto mode may refuse the pull as a production read; ask the owner to allow it.
- **Report** since the last briefing: active testers and their bases, sync failures and refusals, self-tests, stalls, crashes, unresponsive units, CPU near 100 %, and anything that matches an open issue or finding.
- **Discord feedback** the owner pasted: match the name to a Modwerk username (testers who share diagnostics see "They reach me as @name" in their settings), read their records around the message time, and check the [findings](OCTATRACK_BETA_TEST_PLAN.md) and the stock OS before calling anything a bug. For each message say: bug, stock behaviour, a setting, or missing details, with a draft reply for the owner to post. Agents do not post on Discord.
- **Record** a new finding in the findings log (it is at its size cap, so cut first) or in a dated record in `docs/verification/`. The repository is public: name no tester there (write "a tester", or a letter the log already uses) and keep only the technical facts. Reproducing needs the unit: only once the owner says it is free, one agent at a time, by [OCTATRACK_DRIVING.md](OCTATRACK_DRIVING.md).

## Upstream worker

- **Refresh** with `npm run upstream:tools -- --update`, which keeps the Octabam and Elekloader checkouts outside Git. List the commits since the newest import record in `sdk/imports/` for each project; with none, report "nothing new" and stop.
- **Say** in a few lines what changed and what is worth taking: infrastructure, docs, tools, fixes to modules Modwerk carries. A module or anyone's own work needs its author's permission. This pass vendors nothing; a pick from the briefing becomes its own pull request, re-synced docs a new docs-only record ([imports](OCTABAM_INFRASTRUCTURE.md)).
- Keep the titles, bodies and commits of import pull requests free of the upstream project's name and `#` references, which ping the other repository; the import record and licences carry the provenance.

## Main and the computer

- `gh run list --branch main --limit 10`: the newest Pages and Worker deploys succeeded. A red `main` blocks every pull request, so it leads the briefing.
- `df -h ~`: below about 30 GB free, list what could go and ask before removing anything. A worktree can go when its branch's pull request is merged or closed and it has no uncommitted, untracked or unpushed work and nothing changed in the last two hours (another session may be on it); then builds under `/private/tmp`. `git worktree prune` clears the entries of folders already gone.
